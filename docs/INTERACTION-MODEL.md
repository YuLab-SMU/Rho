## 0. 根本问题：画板上画的 Agent，Rho 里并不存在

把真实运行放在 Paper 的 03b、06 旁边对照，可以看到三处偏差。

1. **画板上的 Agent 动作没有事实来源。** 03b 和 06 画的是 Agent 在表格里按
   p_adj 逐行筛选，进度直接长在列头上。可是 Rho 在表格方面只有读页
   （`data.page`）、比较（`data.compare`）和出图（`data.plot`），没有筛选，也不会
   逐行回报。真实运行里，Agent 先读了 15 次能力目录，然后把 `analysis.R` 从第 1 版改到
   第 9 版，提交了 5 次运行；其中第 3、4 次运行 R 报错，它读 stderr 修好代码，
   再核验产物。之后它摆出图和表，写下 `findings.md`，最后才声明事项。“列内进度”
   没有任何事实能驱动。
2. **工作中的表达依赖 Agent 自愿声明，但它到最后才声明。** `task.map.declare`
   是 #59 和 #60（共 61 次调用，从 #0 编号），那时分析早已全部完成。照现有设计，
   #0 到 #58 期间任务地图一直是空的：Agent 干活的时候，人看不到任何结构，只能在结束后读到一份报告。
3. **防打扰的规则按功能各写一套。** 任务地图用 pin，Agent 的改动合并成一条建议，
   再加 8 秒节流（`src/task-map.ts`）。工作区里“Agent 的焦点只高亮，人打开时才置前”
   这条规则，只写在 `web/workspace.tsx` 的一个 effect 里。布局则靠
   `expectedVersion` 和 `view.protection.set` 防止被覆盖。#54 时，Agent 用
   `replace` 换掉了整个工作区的根节点，而布局这套规则里，没有“Agent 的改动变成
   建议”这一条路。到底谁的注意力优先，系统里没有统一的答案。

所以，一张张修画板（包括刚做的去副标签 A′ 和 06）解决不了问题，那是在给不存在的
行为做精装修。正确的顺序是先定模型，再画。

## 1. 三个问题

### 什么始终稳定（Agent 的任何行为都不会改变它）

- **窗口骨架与位置**：项目和问题的身份，已打开视图的位置和大小，人 pin 住的视图。
- **人的输入现场**：光标、选区、滚动位置、未发送的草稿。人正在编辑的缓冲区里，
  Agent 的修改只以协同编辑的标记出现，不移动光标。
- **对象身份与版本**：视图绑定的是哪个产物的哪个版本，不会被静默换掉。人打开过的
  视图保持自己的版本，跟随也不例外：Agent 的新版本在旁边另开一个视图（焦点用预览位，
  布局用它自己的视图），人的视图上出现“New version”入口，换不换由人决定；两个版本
  并存时，标签用运行号区分。（默认，见[计划](INTERACTION-PLAN.md) S0 的 B。回放选
  “Open run 1's figure at #16, follow”：#28 起人的视图出现 Run 2 的入口，#54 后
  run 1 与 run 5 两个视图并存。）
- **控制入口的位置**：停下、接管、撤消、提问始终在原处，离当前对象只差一步。

### 什么随工作变化（由事实驱动，不需要 Agent 解释）

- **对象状态**：脚本改到了第几个版本；运行是进行中、失败还是完成；产物出现了
  没有、核验通过了没有。
- **Agent 的注意力**：它刚读、刚改、刚提交的是哪个对象。这一点从调用本身推出，
  不依赖声明。
- **关联**：源版本 → 运行 → 产物版本 → 视图，随事实自动连起来。
- **组织**：Agent 声明事项以后，已经发生的事实会被追溯地收进事项，不只是往后归类；
  但只经事项的显式引用，不从标题和摘要推断。

### 什么只在需要时展开

调用明细，被拒的请求和 Agent 的自我修正（本次 7 次），能力目录的读取（本次 15 次），
标识与摘要，完整的 stdout/stderr，以及旧版本。这些内容不是藏起来了，而是一步可达：
从对象的状态处展开，不常驻在屏幕上。

调用这一层收在 Agent 账本里：对象列表底部一行计数（目录读取、被拒），点开是五条投影
Given / Did / Read / Produced / Refused，只从 Rho 自己的记录折出（`src/trace.ts`），
到当前这一步为止。Rho 没记下的身份写“Not recorded”，不用 0，也不从相邻记录猜。
回放 #44 时：Given 12 次目录读取；Did 14 条写和运行；Read 里打开的文档和两页表
是“Not recorded”；Produced 4 次运行；Refused 是 stale 2、condition 1。

## 2. 概念模型：对象是主语，Agent 是作者

界面应该说“analysis.R v6 → 第 4 次运行失败：object 'op' not found”，而不是
“Agent 正在修复错误”。Agent 只在两处出现：一是作者属性（谁改的），二是它主动给出的
解释，并且标明是解释。

| 对象 | 来自哪个事实 | 状态 | 和谁相连 |
| --- | --- | --- | --- |
| 问题 | 任务问题、`questions.md` | 开放、有回应 | 事项、笔记 |
| 源（脚本、文档） | `document.open/edit/save`，以及运行记下的脚本 | 第 n 版、谁改的；第一次因打开或运行出现时就是磁盘上那份，有修改没保存才是未保存 | 用它运行的那几次 |
| 运行 | `action.submit`，加上 Rho 观察到的退出；`lookup/output` 只是读 | 进行中、完成、失败、未知 | 它运行的脚本版本（脚本读的其他文件不记）、产物、同一源的前后尝试 |
| 产物 | 运行的声明，加上 `artifact.check` | 已声明、在盘、已核验、领域未判 | 运行、视图、事项 |
| 视图 | `composition.*` | 绑定某个产物的某个版本 | 产物；谁摆的、是否 pin |
| 笔记 | `annotation.*` | 草稿、有回应 | 对象 + 版本（+ 选中的实体） |
| 问题（question） | `context.create`（浏览器 principal 写入 `questions.md` 并准备上下文）、`context.read` 的回执 | 已准备、已被取用；有回应要等显式关联 | 它被问到的那个产物版本（+ 选中的行）、`questions.md` 的版本 |
| 事项（可选） | `task.map.declare` | Agent 自己定义的词汇 | 只经显式引用：`artifact`（那个文件、那份字节、那次运行）、`view`、`from`；标题里提到的对象不算 |
| 调用 | 经过 Rho 边界的每次操作，或适配器回报的原生活动 | 已返回、被拒、部分、未知 | 它作用到的对象 |

**事项是一个可选的叠加层。** 没有事项时，界面照样能从对象和调用表达工作；有了事项，
再按它的显式引用把对象收进去。带 `artifact` 引用的事项“收集”那个版本、产生它的那次
运行，以及那次运行的源版本；在那个版本的视图上，它显示为 Agent 的说法，和事实分开，
`judgment` 行标为 Agent 的判断，都不用核验的颜色。“发现”不单独成为对象（已定，见
[计划](INTERACTION-PLAN.md)第 4 节第 5 条）。

**解释**（`rho.agent-note` 视图）挂在它的依据见证所指的对象旁：跟随时随对象出现，
人在工作时和其他布局改动一样变成建议。这条规则已定但还没实现：现有记录里没有
任何一条 note，第二份轨迹也没有（Agent 的报告只留在外部对话里）；按“事实先于声明”，
等录到一条再做。

## 3. 表达语法：六个原语

Agent 不能直接调用“表达”。它只能做事，事实自然产生表达。每个原语都要回答五个问题：
谁触发、作用在什么上、怎样算成功、人能不能拒绝、失败后怎样恢复。

| 原语 | 谁触发 | 作用在什么上 | 怎样算成功 | 人能否拒绝 | 失败后怎样恢复 |
| --- | --- | --- | --- | --- | --- |
| **Respond** 对象反馈 | 作用于对象的任何事实 | 对象出现的每个地方：视图、标签、项目页的行、事项卡片 | 屏幕上的状态等于最近一次观察到的事实，并带观察时间 | 事实不能拒绝；关掉视图就不再观察 | 断流时保留上次状态并标为可能过期，再读一次快照，不猜 |
| **Focus** 当前焦点 | 从调用推出（最近读、改、提交的对象），或显式声明；人点击、选择 | 对象上一个“它在这里”的标记；主区跟不跟过去由第 4 节决定 | 人不读文字也能说出 Agent 在处理哪个对象 | 不跟随时，焦点只剩标记 | 对象不可用时，标记落到项目页的对象行上 |
| **Compose** 组织视图 | Agent 摆放、改形态；人拖动、关闭、pin | 视图的出现、位置、形态 | 新视图出现在不打断人的位置；它的来由一看便知（它绑定的产物刚出现） | pin 住的位置不动；人在工作时，Agent 的改动变成一条待定建议 | 组件不可用时保留引用并给出回退显示，不重放 |
| **Connect** 建立关联 | 从事实自动推出；Agent 声明（`item.artifact`、`from` 边）；人的笔记和问题 | 对象之间可以互相到达的路径 | 从产物两步内到达运行和源版本；从笔记或问题到达它锚定的版本 | 关联不会被静默移到别的版本：问题留在被问到的版本上，新版本出现也不移动；移动锚点是人的显式动作 | 来源不可读时说明缺了什么，保留引用 |
| **Reveal** 呈现细节 | 只能由人触发 | 调用明细、被拒请求、自我修正、标识、完整输出、旧版本 | 从任何对象的状态处一步可达，关掉后回到原处 | 不适用 | 不适用 |
| **Revisit** 返回现场 | 人从产物、笔记、事项或时间点返回 | 确切版本 + 产生它的运行 + 源版本，以及当时的布局 | 中断后找得到继续的位置；返回不会重放任何执行 | 不适用 | 内容不可用时如实报告，保留引用 |

和现有代码的对照：

| 原语 | 已有 | 缺口 |
| --- | --- | --- |
| Respond | SSE 事件流和断流处理；`web/execution-facts.ts` 区分已声明、在盘、已核验、领域 | 视图里没有统一的“这个对象刚被谁改过（v5→v6）”标记 |
| Focus | `workspace.tsx`：Agent 焦点只高亮；任务地图有 `focus` | 焦点只能指向已声明的事项，不能从调用推出 |
| Compose | 任务地图的 pin、建议、节流；布局的版本条件和保护 | 两套规则需要合成第 4 节那一套 |
| Connect | 执行面板里的兄弟文件、`item.artifact`、上下文的取用回执 | 没有声明过 `from` 边，所以画不出分支 |
| Reveal | 执行面板、记录和诊断都已收在展开里 | 被拒请求和自我修正没有按对象聚合 |
| Revisit | 来源追溯、兄弟文件跳转、重启后恢复 | 回不到“当时的布局与选区” |

## 4. 注意力规则：一套规则，覆盖地图、布局和视图

界面通过观察判断人处于三种状态中的哪一种，不去问人：

| 人的状态 | 怎样判断 | Agent 的焦点 | Agent 改布局 | 新产物 |
| --- | --- | --- | --- | --- |
| 跟随 | 打开了跟随，且最近没有输入 | 主区跟过去，8 秒内的变化合并 | 应用，8 秒节流 | 出现在对象列表里；Agent 读它时才进入预览视图 |
| 工作 | 正在编辑、选择、输入，或当前视图被 pin 住 | 只在对象上放一个标记 | 变成一条待定建议 | 出现在项目和事项里，不打开 |
| 离开 | 页面隐藏，或长时间没有输入 | 不动 | 变成建议 | 累积起来 |

**升级是打断“工作”的唯一理由。** 只有两种情况：人正在等的那次运行失败了或结果未知；
Agent 发出了需要人来决定的请求。后者目前唯一有事实的是 Agent 的布局（人在工作、离开，
或正看着的视图被 pin 住时），以建议的形式出现。表现形式是在受影响的对象旁放一个
非模态标记，附带继续入口。不弹窗，不抢焦点，不移光标。

**从“离开”回来时**，给一份“你不在时”的摘要：哪些对象改了，哪些运行结束或失败，
出现了哪些产物。不回放过程。什么都没变就没有摘要。

这一节把任务地图已有的 pin、建议和节流推广到全部原语。8 秒沿用
`taskMapLimits.agentFormIntervalMs`，由测试保证两处相等。

回放原型补上了三条规则：

- **一个预览位。** 跟随时，Agent 的焦点只占一个预览视图（斜体标签），下一次移动
  在原位替换它。人打开、选择或 pin 过的视图归人所有，Agent 不会替换、不会换版本，
  也不会关闭，即使它发出的是 `replace`。没有这一条的话，跟随到 #36 时已经堆了 5 个标签，
  其中 2 个是过期的运行。
- **跟随时带到改动处。** Agent 改了源，跟随者的视图滚动到改动的行；在工作的人
  保持自己的滚动位置。
- **没有记录时间的调用按早算。** 节流时，它被放在前一个有记录的时间上，
  不假设实际过去的时间比记录的多。

S1 接入人向 Agent 的往返以后，又补了三条：

- **只有 Agent 的工作移动屏幕。** 每个事实带着做出它的 principal。人或别的 principal
  记下的事（改 `questions.md`、提问、取用）只在对象上更新，主区和 Agent 的标记都不动。
- **问题留在被问到的版本上。** 问题锚定在产物的那个版本（按内容摘要）和选中的行上，
  只在显示那个版本的视图里出现；后来的版本不继承它。从对象列表点开问题，打开的是
  它被问到的版本。
- **取用只是回执。** 问题出现的每一处显示“Fetched by <绑定名> · 时间”，别的都不变：
  不移动主区，不移动 Agent 的标记，不升级，也不声称取用之后发生了什么。没被取用的
  显示“Not fetched”。“有回应”要等 Agent 给出显式关联，现在没有这样的记录。

### 规模与时间

S5 在两份轨迹上定了三条：

- **同一个源的运行是一条链，以最后一次为准。** 对象列表里只列最新一次，更早的折成
  一排运行标记（编号和成败的颜色），点这一排才逐行列出。折叠不藏三样东西：主区正在
  显示的那次、Agent 标记所在的那次、升级给人的那次。第一份轨迹结束时，`analysis.R`
  下面从 5 行变成 1 行加一排标记；在 effects.csv 里工作的人仍然看得到失败的第 3、4 次。
  展开属于 Reveal，不改变注意力状态。
- **摘要按对象合并，运行按链合并。** 同一个源在离开期间有变化的运行合成一行，由最后
  一次领头：成功写核验了几个文件，失败写它自己的报错第一行；更早的几次只剩标记。
  “#30 离开、#57 回来”的摘要从 7 行变成 5 行。
- **占据主区上方的只有两种东西。** 人在等的运行失败或结果未知（升级），以及等人决定
  的 Agent 布局（建议）。目录读取、被拒请求、重试、回执、问题和事项都不会。测试在
  两份轨迹的六种场景里逐步检查。

还没有启用的两条，按“事实先于声明”：

- **久未触碰的对象退到“更早”。** 两份轨迹在 1024 宽下对象列表都不用滚动，没有一份
  需要它，也就定不了阈值：按事实条数算，目录读取会把阈值撑大；按时间算，第一份轨迹
  3.5 小时的间隔会把 `findings.md`（问题的回答）也退掉。阈值等 S6 有真人看过再定。
- **摘要的行数封顶。** 合并之后最长的摘要 5 行，封顶的条数同样无据可依。

这张表本身就是验证材料。拿它问用户“此刻你看到了什么，想做什么”，比比较两张画板有用得多。

回放还暴露了四个缺口，都不在界面层：

1. **问题最后才到。** 问题留在外部 Agent 的对话里，Rho 到 #59 才知道。在那之前，
   标题栏只能显示项目名。
2. **事项没有指向对象。** 5 个事项都只有标题和摘要，没有一个引用运行、产物或源。
   “把已发生的调用追溯地收进事项”无事可收；按文字去猜就是推断，模型不做。
   要做到这一点，`task.map.declare` 需要让 Agent 引用对象（`item.artifact` 已有，
   但这次没用；源和运行还没有）。S3 之后：#63 验收脚本的声明给两项加了引用，回放
   按引用收集；Rho 给 Agent 的任务地图指导里加了“开工就声明、产物核验后立刻引用、
   判断标 judgment”。
3. **Agent 的读操作不是事件。** `data.page`、`action.lookup`、`action.output` 经过了
   服务，但浏览器收不到。要从读推出焦点，服务需要为读发出观察事件。
4. **同样的字节不算新版本。** 三个 CSV 在第 1、2、5 次运行里字节完全相同，只有图变了。
   按内容摘要合并版本以后，对象列表用圆点表示版本数，不需要写“未变化”。

S2 把同一次运行改从 Rho 自己的记录折出来，对照转录又看到四处 Rho 不知道的事：

5. **4 次拒绝没到 Rho。** 7 次拒绝里，3 次 invalid 和 1 次 condition 是 agent 适配器
   在本地按契约拒掉的（Rho-plugins `layered.ts`），Rho 的记录里只有 stale 2、condition 1。
6. **打开了哪个文档、读了哪页表，没有记。** `document.open` 只记返回的版本，`data.page`
   不记资源身份；`action.output` 不记读的是哪条流。
7. **输出文本不在项目记录里。** 退出码和字节数在操作记录里，stdout/stderr 的文本留在
   原生存储，所以从记录折出的升级只能写“Exit 1”，写不出报错第一行。
8. **只留最新一次声明的事项。** 任务地图保留最新的事项和每次声明的回执；Agent 在 #59、
   #60 声明的内容已被验收脚本 18:19 的声明覆盖。

### 第二份轨迹：让失败的检查通过

S4 用真实的 Claude Code（`claude --print`，MCP 只给 rho，授权和第一次相同的 23 个
方法）跑了另一类任务：`check.R` 的检查失败，改 `stats.R` 让它通过，不许改 `check.R`。
提示词只说任务。这次没有转录，回放只用 Rho 自己的记录（`?trace=check`），共 20 个事实。

| 调用 | 实际发生了什么 | 原语 | 跟随时 | 工作时（#10 起读 `check.R`） |
| --- | --- | --- | --- | --- |
| #0–7 | 读能力目录，其中 2 次 stale 后重读 | — | 不变；对象列表底部计数 | 不变 |

两份轨迹下都成立、没有改的规则：一个节奏（跟随者被移动两次，相隔 23 秒；工作者
一次也没有，Agent 只留标记）；被拒的请求不显示，只计数；版本按内容摘要；未记录的
写“Not recorded”，不猜；离开回来按对象给摘要（#11 离开，回来时是 `check.R` v1、
Run 1 completed、`results.csv` 多一个版本）。

因第二份轨迹改了的规则，各有测试和回放步骤：

- **运行的结束是 Rho 的观察。** 第一份轨迹把结束挂在 Agent 的 `action.lookup` 上；
  操作记录里有 Rho 看到退出的时间，结束改成 Rho 的事实（#13），lookup 只是读。第一份
  轨迹从记录折出时，每次运行都比转录早几秒完成。
- **运行带出它的脚本。** 打开没记是哪个文档，`check.R` 第一次出现是在 #12 的提交里；
  运行自己记了脚本和版本，脚本就是对象。
- **第一次因打开或运行而出现的文档就是磁盘上那份：已保存，直到有修改。** 之前
  `check.R` 显示“v1 · unsaved”，`analysis.R` 刚打开时也一样。

第二份轨迹暴露的缺口：

9. **报告里有一个没有运行支撑、而且错了的数。** Agent 从没跑过失败的检查，一次改完
   就提交。它的报告说旧的 `trimmed_mean`“returned 35 instead of 2.5”，按种子文件实际
   返回 2。Rho 的记录里只有一次通过的运行，报告本身留在外部对话里。界面能做的是不替
   它背书：运行和核验是事实，报告是说法；报告里的数要进 Rho，就得引用产生它的运行。
10. **运行不记读了哪些输入。** Run 1 挂在 `check.R` v1 下，让它通过的却是 `stats.R`
    v2：`check.R` 的 `source("stats.R")` 不在任何记录里，从 Run 1 走不到 `stats.R` v2。
    要补，操作记录得写下运行读过的文件和摘要（Rho-core 的事）。
11. **没有任务地图。** Agent 一次也没解析 `task.map.*`，也就没读到 S3 写在
    `rho.task-map` 里的指导。于是把同样的话放进 `rho.workspace`（每个契约都要求它，
    适配器每次解析都把它交给模型），同一任务又录了一次（`work/agent-check-s4b`）：
    Agent 收到了这段话，照样没有声明，这处改动已撤回。事项是否总在最后才声明，两次的
    答案都是“根本不声明”。所以第 2 节“没有事项时照样能表达工作”不是退路，而是常态：
    跟随、工作、离开三种状态都得只靠对象和调用撑起来，两份轨迹也确实做到了。第二次
    的报告写明了自己没先跑检查，没有再给出运行之外的数。
