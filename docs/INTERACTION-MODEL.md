## 0. 根本问题：画板上画的 Agent，Rho 里并不存在

把真实运行放在 Paper 的 03b、06 旁边对照，可以看到三处偏差。

1. **画板上的 Agent 动作没有事实来源。** 03b 和 06 画的是 Agent 在表格里按
   p_adj 逐行筛选，进度直接长在列头上。可是 Rho 在表格方面只有读页
   （`data.page`）、比较（`data.compare`）和出图（`data.plot`），没有筛选，也不会
   逐行回报。真实运行里，Agent 先读了 15 次能力目录，然后把 `analysis.R` 从第 1 版改到
   第 9 版，提交了 5 次运行；其中第 3、4 次运行 R 报错，它读 stderr 修好代码，
   再核验产物。之后它摆出图和表，写下 `findings.md`，最后才声明事项。“列内进度”
   没有任何事实能驱动。
2. **工作中的表达依赖 Agent 自愿声明，但它到最后才声明。** `task.map.declare`
   是 #59 和 #60（共 61 次调用，从 #0 编号），那时分析早已全部完成。照现有设计，
   #0 到 #58 期间任务地图一直是空的：Agent 干活的时候，人看不到任何结构，只能在结束后读到一份报告。
3. **防打扰的规则按功能各写一套。** 任务地图用 pin，Agent 的改动合并成一条建议，
   再加 8 秒节流（`src/task-map.ts`）。工作区里“Agent 的焦点只高亮，人打开时才置前”
   这条规则，只写在 `web/workspace.tsx` 的一个 effect 里。布局则靠
   `expectedVersion` 和 `view.protection.set` 防止被覆盖。#54 时，Agent 用
   `replace` 换掉了整个工作区的根节点，而布局这套规则里，没有“Agent 的改动变成
   建议”这一条路。到底谁的注意力优先，系统里没有统一的答案。

所以，一张张修画板（包括刚做的去副标签 A′ 和 06）解决不了问题，那是在给不存在的
行为做精装修。正确的顺序是先定模型，再画。

## 1. 三个问题

### 什么始终稳定（Agent 的任何行为都不会改变它）

- **窗口骨架与位置**：项目和问题的身份，已打开视图的位置和大小，人 pin 住的视图。
- **人的输入现场**：光标、选区、滚动位置、未发送的草稿。人正在编辑的缓冲区里，
  Agent 的修改只以协同编辑的标记出现，不移动光标。
- **对象身份与版本**：视图绑定的是哪个产物的哪个版本，不会被静默换掉。
- **控制入口的位置**：停下、接管、撤消、提问始终在原处，离当前对象只差一步。

### 什么随工作变化（由事实驱动，不需要 Agent 解释）

- **对象状态**：脚本改到了第几个版本；运行是进行中、失败还是完成；产物出现了
  没有、核验通过了没有。
- **Agent 的注意力**：它刚读、刚改、刚提交的是哪个对象。这一点从调用本身推出，
  不依赖声明。
- **关联**：源版本 → 运行 → 产物版本 → 视图，随事实自动连起来。
- **组织**：Agent 声明事项以后，已经发生的调用会被追溯地收进事项，不只是往后归类。

### 什么只在需要时展开

调用明细，被拒的请求和 Agent 的自我修正（本次 7 次），能力目录的读取（本次 15 次），
标识与摘要，完整的 stdout/stderr，以及旧版本。这些内容不是藏起来了，而是一步可达：
从对象的状态处展开，不常驻在屏幕上。

## 2. 概念模型：对象是主语，Agent 是作者

界面应该说“analysis.R v6 → 第 4 次运行失败：object 'op' not found”，而不是
“Agent 正在修复错误”。Agent 只在两处出现：一是作者属性（谁改的），二是它主动给出的
解释，并且标明是解释。

| 对象 | 来自哪个事实 | 状态 | 和谁相连 |
| --- | --- | --- | --- |
| 问题 | 任务问题、`questions.md` | 开放、有回应 | 事项、笔记 |
| 源（脚本、文档） | `document.open/edit/save` | 第 n 版、未保存、谁改的 | 用它运行的那几次 |
| 运行 | `action.submit/lookup/output` | 进行中、完成、失败、未知 | 源版本、产物、同一源的前后尝试 |
| 产物 | 运行的声明，加上 `artifact.check` | 已声明、在盘、已核验、领域未判 | 运行、视图、事项 |
| 视图 | `composition.*` | 绑定某个产物的某个版本 | 产物；谁摆的、是否 pin |
| 笔记 | `annotation.*`、`context.create` | 草稿、可取用、已被取用、有回应 | 对象 + 版本（+ 选中的实体） |
| 事项（可选） | `task.map.declare` | Agent 自己定义的词汇 | 以上任何对象 |
| 调用 | 经过 Rho 边界的每次操作，或适配器回报的原生活动 | 已返回、被拒、部分、未知 | 它作用到的对象 |

**事项是一个可选的叠加层。** 没有事项时，界面照样能从对象和调用表达工作；有了事项，
再把对象和调用收进去。

## 3. 表达语法：六个原语

Agent 不能直接调用“表达”。它只能做事，事实自然产生表达。每个原语都要回答五个问题：
谁触发、作用在什么上、怎样算成功、人能不能拒绝、失败后怎样恢复。

| 原语 | 谁触发 | 作用在什么上 | 怎样算成功 | 人能否拒绝 | 失败后怎样恢复 |
| --- | --- | --- | --- | --- | --- |
| **Respond** 对象反馈 | 作用于对象的任何事实 | 对象出现的每个地方：视图、标签、项目页的行、事项卡片 | 屏幕上的状态等于最近一次观察到的事实，并带观察时间 | 事实不能拒绝；关掉视图就不再观察 | 断流时保留上次状态并标为可能过期，再读一次快照，不猜 |
| **Focus** 当前焦点 | 从调用推出（最近读、改、提交的对象），或显式声明；人点击、选择 | 对象上一个“它在这里”的标记；主区跟不跟过去由第 4 节决定 | 人不读文字也能说出 Agent 在处理哪个对象 | 不跟随时，焦点只剩标记 | 对象不可用时，标记落到项目页的对象行上 |
| **Compose** 组织视图 | Agent 摆放、改形态；人拖动、关闭、pin | 视图的出现、位置、形态 | 新视图出现在不打断人的位置；它的来由一看便知（它绑定的产物刚出现） | pin 住的位置不动；人在工作时，Agent 的改动变成一条待定建议 | 组件不可用时保留引用并给出回退显示，不重放 |
| **Connect** 建立关联 | 从事实自动推出；Agent 声明（`item.artifact`、`from` 边）；人的笔记 | 对象之间可以互相到达的路径 | 从产物两步内到达运行和源版本；从笔记到达它锚定的版本 | 关联不会被静默移到别的版本；移动锚点是人的显式动作 | 来源不可读时说明缺了什么，保留引用 |
| **Reveal** 呈现细节 | 只能由人触发 | 调用明细、被拒请求、自我修正、标识、完整输出、旧版本 | 从任何对象的状态处一步可达，关掉后回到原处 | 不适用 | 不适用 |
| **Revisit** 返回现场 | 人从产物、笔记、事项或时间点返回 | 确切版本 + 产生它的运行 + 源版本，以及当时的布局 | 中断后找得到继续的位置；返回不会重放任何执行 | 不适用 | 内容不可用时如实报告，保留引用 |

和现有代码的对照：

| 原语 | 已有 | 缺口 |
| --- | --- | --- |
| Respond | SSE 事件流和断流处理；`web/execution-facts.ts` 区分已声明、在盘、已核验、领域 | 视图里没有统一的“这个对象刚被谁改过（v5→v6）”标记 |
| Focus | `workspace.tsx`：Agent 焦点只高亮；任务地图有 `focus` | 焦点只能指向已声明的事项，不能从调用推出 |
| Compose | 任务地图的 pin、建议、节流；布局的版本条件和保护 | 两套规则需要合成第 4 节那一套 |
| Connect | 执行面板里的兄弟文件、`item.artifact`、上下文的取用回执 | 没有声明过 `from` 边，所以画不出分支 |
| Reveal | 执行面板、记录和诊断都已收在展开里 | 被拒请求和自我修正没有按对象聚合 |
| Revisit | 来源追溯、兄弟文件跳转、重启后恢复 | 回不到“当时的布局与选区” |

## 4. 注意力规则：一套规则，覆盖地图、布局和视图

界面通过观察判断人处于三种状态中的哪一种，不去问人：

| 人的状态 | 怎样判断 | Agent 的焦点 | Agent 改布局 | 新产物 |
| --- | --- | --- | --- | --- |
| 跟随 | 打开了跟随，且最近没有输入 | 主区跟过去，8 秒内的变化合并 | 应用，8 秒节流 | 出现在对象列表里；Agent 读它时才进入预览视图 |
| 工作 | 正在编辑、选择、输入，或当前视图被 pin 住 | 只在对象上放一个标记 | 变成一条待定建议 | 出现在项目和事项里，不打开 |
| 离开 | 页面隐藏，或长时间没有输入 | 不动 | 变成建议 | 累积起来 |

**升级是打断“工作”的唯一理由。** 只有两种情况：人正在等的那次运行失败了或结果未知；
Agent 发出了需要人来决定的请求。表现形式是在受影响的对象旁放一个非模态标记，附带
继续入口。不弹窗，不抢焦点，不移光标。

**从“离开”回来时**，给一份“你不在时”的摘要：哪些对象改了，哪些运行结束或失败，
出现了哪些产物。不回放过程。

这一节把任务地图已有的 pin、建议和节流推广到全部原语。8 秒沿用
`taskMapLimits.agentFormIntervalMs`，由测试保证两处相等。

回放原型补上了三条规则：

- **一个预览位。** 跟随时，Agent 的焦点只占一个预览视图（斜体标签），下一次移动
  在原位替换它。人打开、选择或 pin 过的视图归人所有，Agent 不会替换，也不会关闭，
  即使它发出的是 `replace`。没有这一条的话，跟随到 #36 时已经堆了 5 个标签，
  其中 2 个是过期的运行。
- **跟随时带到改动处。** Agent 改了源，跟随者的视图滚动到改动的行；在工作的人
  保持自己的滚动位置。
- **没有记录时间的调用按早算。** 节流时，它被放在前一个有记录的时间上，
  不假设实际过去的时间比记录的多。

## 5. 用真实运行回放这套规则

这次运行用的是 `datasets::airquality`，问题是“温度对臭氧的影响里，有多少是真的”。
下表把 61 次调用按对象归在一起，对比人在“跟随”和“工作”两种状态下屏幕上各发生什么。

| 调用 | 实际发生了什么 | 原语 | 跟随时 | 工作时 |
| --- | --- | --- | --- | --- |
| #0–7 | 读能力目录，其中 1 次 stale 后重读 | — | 不变 | 不变 |
| #8–10 | 打开、修改、保存 `analysis.R`（v2） | Respond、Focus | `analysis.R` 置前，改动处带作者标记 | 项目里那一行变成“v2 · Agent” |
| #11–15 | 第 1 次运行完成，4 个文件核验通过 | Respond、Connect | 运行挂在 v2 下面，产物出现 | 同左，但不打开 |
| #16–18 | Agent 读 effects、tests 两页 | Focus（由读推出） | effects.csv 进入预览视图；tests.csv 落在同一节流窗口内，被合并掉，不显示 | 对象列表里出现 Agent 标记 |
| #19–28 | 改到 v4，其间 3 次请求被拒（2 次修改、1 次提交）；第 2 次运行完成并核验 | Respond、Connect | 被拒的请求不显示 | 同左 |
| #29–36 | v5；第 3 次运行失败：`unexpected ')'` | Respond，人在等时升级 | 运行变成失败，stderr 第一行在旁边 | 只有人在等这次运行时才标记 |
| #37–44 | 被拒 2 次后改出 v6；第 4 次运行失败：`object 'op' not found` | 同上 | 两次失败串在同一个源的尝试链上 | 同上 |
| #45–52 | v7 到 v9；第 5 次运行成功并核验 | Respond、Connect | 尝试链收起：5 次尝试，以最后 1 次为准 | 同左 |
| #53–54 | Agent 用 `replace` 摆出图和效应表 | Compose | 应用；人的视图不被关闭 | 一条建议：显示 temp-effect.png 和 effects.csv |
| #55–57 | 写 `findings.md`（问题的回答） | Respond | `findings.md` 置前，作为问题的回答 | 问题那一行显示“有回答” |
| #58–60 | 声明事项和问题 | — | 问题出现在标题栏；5 个事项作为 Agent 的说法单独列出 | 同左 |

这张表本身就是验证材料。拿它问用户“此刻你看到了什么，想做什么”，比比较两张画板有用得多。

回放还暴露了四个缺口，都不在界面层：

1. **问题最后才到。** 问题留在外部 Agent 的对话里，Rho 到 #59 才知道。在那之前，
   标题栏只能显示项目名。
2. **事项没有指向对象。** 5 个事项都只有标题和摘要，没有一个引用运行、产物或源。
   “把已发生的调用追溯地收进事项”无事可收；按文字去猜就是推断，模型不做。
   要做到这一点，`task.map.declare` 需要让 Agent 引用对象（`item.artifact` 已有，
   但这次没用；源和运行还没有）。
3. **Agent 的读操作不是事件。** `data.page`、`action.lookup`、`action.output` 经过了
   服务，但浏览器收不到。要从读推出焦点，服务需要为读发出观察事件。
4. **同样的字节不算新版本。** 三个 CSV 在第 1、2、5 次运行里字节完全相同，只有图变了。
   按内容摘要合并版本以后，对象列表用圆点表示版本数，不需要写“未变化”。

## 6. 怎样验证

| 问题 | 在回放里怎样判断 |
| --- | --- |
| 不读解释，能否知道 Agent 在操作什么？ | 随时暂停，问“它在做什么”。答案应来自对象状态，例如“在改 analysis.R”“第 3 次运行失败了” |
| 能否找到结果的来源？ | 从 temp-effect.png 两步内到达第 5 次运行和 `analysis.R` v9 |
| 能否在对象上直接提问？ | 在 effects.csv 里选两行提问，笔记锚定在那个版本上，之后看到“已被取用” |
| 能否不让 Agent 打扰自己？ | 人在编辑 `findings.md` 时发生 #54，布局不变，只多出一条建议 |
| 中断后能否找到继续的位置？ | 在 #30 离开、#57 回来，摘要列出 v5–v9、两次失败、一次成功、图和回答 |

## 7. 现有画板与下一步

- 03b、06、A′ 作为“表格插件能做什么”的假设保留。只有当 Tables 插件提供筛选操作，
  并逐行回报进度时，“列内进度”才有事实来源。这是插件的能力问题，不是外壳设计的问题。
- 回放原型已经做好（`npm run prototype:replay`）：61 次调用经过 `express()`，可以
  在“跟随、工作、离开”之间切换，也可以随时点开、选择、pin、接受或忽略建议。
  它用 Rho 的样式变量另画了一个外壳，没有接现有的 WebUI 组件；规则本身已经可以给
  真正的外壳用。
- 下一步：让真实的人看着这次回放完成第 6 节的五个问题，记录卡在哪里；再把服务的
  事件流接成 `Fact`，让同一套规则驱动 WebUI。
- 待定：
  1. 跟随状态的默认值。
  2. 判断“工作”状态的阈值。
  3. Agent 的读操作要不要算进焦点（涉及噪音和隐私）。
  4. 8 秒节流是否同样适用于视图。
