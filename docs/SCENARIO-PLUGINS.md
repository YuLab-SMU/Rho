# 复杂场景插件：运行机制、上下文与工作绑定

> 性质：设计研究，尚未形成插件 API 或实施方案
>
> 日期：2026-09-06
>
> 来源：本轮关于远程主机交互、核心 runtime、用户信息、Agent 协助和工作组合的讨论
>
> 范围：本轮只整理文档。这里的插件系统、通道抽象与工作组合机制不属于当前 Rho Next 的实施目标，也不增加它的完成条件。

## 讨论从哪里开始

远程运行的讨论一度落到了“支持 OpenSSH 还是 Server Manager”上。这容易使组件围绕连接工具增长：每遇到一种新工具，就增加一个 provider 分支、一些专用配置和一套说明。

用户关心的是连上以后能怎样工作。连接可以来自已有配置、用户脚本、外部工具或专用适配；用户可以更换入口。命令执行、输入输出、工作目录、运行环境、文件和作业的交互仍应有一致的约定。

这带出了一个更广的问题：复杂场景中，哪些部分需要稳定的执行代码，哪些条件由用户提供，哪些信息可以观察得到，Agent 又能补齐什么？插件如何把这些部分接起来，而不把每一种工作方式写进核心？

本文把已确认的方向和设计推论分开。连接方式由用户选择、核心运行机制需要确定性、本课题暂不实施，是本轮已经明确的边界。后文的组合视图、插件形态和接口方向仍是候选，不能据此宣称功能已经存在。

## 核心代码应该稳定什么

核心 runtime 在这里指 Rho 的可靠执行机制：校验明确的请求，管理输入输出和执行生命周期，处理取消，确认结果，在效果无法确认时保留不确定性。科学领域中已经明确的规则也需要可测试的代码实现，例如如何解释环境验证结果、识别原生作业回执。

这些机制需要独立于当前模型、当前提示词和某个用户的连接习惯运行。修改一个 Skill，不应改变 Operation 的幂等和终态语义；切换连接工具，也不应要求重写 Slurm 的状态解释。

沿用现有分工：领域 Handler 解释结果，Foundation 保证提交纪律。详见[系统宪章](NEXT-SYSTEM.md)。本研究不另造生命周期、权限审批或运行记录系统。

变化较多的条件适合通过配置、观察和绑定传入，包括工作空间、目标主机、工作目录、环境选择、输入位置、资源约束和采用的方法。数据化表达也有边界：不能把本应由代码校验的执行规则退化成一段“请务必正确处理”的提示词。

## 先分清几个容易混用的概念

Work 表示要完成的工作，可以包含 Goal、Task 及它们的依赖。这里并不假设一个 Task 只能服务一个 Goal。

Space 提供上下文和作用域，可以对应项目、分析区或文稿区。它不必是 Task 的父节点。本文的 Space 也不等同于 Rho 当前名为 Workspace 的实时 R 会话，不要求为此重命名现有模块。

Skill 说明处理某类工作的办法，包括需要哪些信息和能力。Capability 是可调用、可校验的接口。一个 Skill 可以需要多个能力，也可能有几种可行方法。

具体 Runtime 提供实际运行能力，例如 R session、进程执行器或 Slurm。它们的生命周期不同，不必共享一个进程模型。主机是承载环境，一台主机可以同时提供多个 runtime；连接只是到达它们的一条路径。

Actor 是参与者，包括人和外部 Agent。Surface 是这些参与者看到和操作工作的入口。界面上的组合视图不因此获得独立的事实权威。

这些概念用于解释关系，不是要求立即建立同名的类、表、crate 或全局 ID。版本和身份仍优先引用真实系统；连接句柄属于运行中资源，不能作为持久化的任务成功证据。

## 用户、Agent、插件和 runtime 怎样交接

| 参与方 | 主要提供或处理什么 | 交给下游的内容 |
| --- | --- | --- |
| 用户 | 目标、输入位置、使用的空间或主机、资源预算，以及需要人决定的取舍；自主选择连接方式 | 意图、约束、已有配置和必要选择 |
| Agent | 理解目标，使用 Skill，查找配置、探测环境、提出方法，询问仍缺失的决策信息 | 有依据的建议，以及参数已经明确的请求 |
| 场景插件 | 声明所需条件，发现和验证环境，适配原生工具，解释执行结果和恢复条件 | 可发现的能力、具体输入契约、运行观察与结果 |
| 核心 runtime | 机械校验、执行控制、输入输出、取消、结果提交和恢复纪律 | 能追溯到 Operation 的实际结果或明确的不确定性 |

用户不应被要求手填所有技术参数。R 版本、当前目录、调度器是否存在，通常可以查询；预算、是否更换目标、数据能否离开当前位置，常常需要用户判断。插件应帮助 Agent 分清这两类缺口。

Agent 的协助也可以发生在插件开发时，例如编写适配脚本、整理参数说明、设计验证案例。生成的代码仍需验证，不能因为出自 Agent 就被当成核心已经支持的机制。

运行期的任务分解、方法选择、参与者安排和 Agent harness 继续属于外部 Agent 平台。Rho 可以提供当前可用能力、绑定和缺失条件，不因此接管对话、规划或行为循环。

## runtime 实际需要哪些信息

runtime 需要一份已经足够明确、能够机械校验的执行上下文。下面是信息类别，不是新定义的请求 schema；现有 Invocation、Operation 和领域契约仍是当前实现的依据。

- 目标与作用域：实际目标、使用哪个运行实例、在哪个项目或目录中操作，以及必要的原生身份核对。
- 交互入口：可使用的通道或运行句柄，以及该入口真实支持哪些交互。
- 动作与参数：选定的 capability、契约版本、标准化参数和输入引用。
- 环境与资源：实际工作目录、环境选择、必要的环境参数、资源限额和截止条件。
- 前置条件：本领域能够验证的条件，例如 session identity、文件内容或环境锁的摘要。
- 结果与控制约定：怎样接收输出、何时能确认结束、如何请求中断、失联后保留哪些原生引用。

OperationId 和可信调用者身份由已有执行边界绑定。调用端仍需提供并保留 client_request_id，让同一请求的重试沿用它；应用可以代用户生成，无需用户手填。这不改变现有幂等协议。凭据通过原有连接或凭据机制使用；配置和运行记录可以引用凭据来源，不复制密码或令牌。

runtime 不需要读完整对话来猜工作目录，也不需要从 Skill 的叙述中猜某个参数。缺失条件应能被准确报告。Agent 据此继续查找或提问，不能靠 runtime 静默换主机、扩大资源或再次执行来补救。

### 信息来自哪里，也影响怎样使用

用户选择、实际观察、Agent 建议和确定性推导要能区分。它们不必进入四个数据库，但不能混成同一种“已知事实”。

例如，用户指定 YuLabServer 是选择；查询得到的 Slurm 版本是观察；建议使用批处理是 Agent 的判断；根据已确认参数形成命令参数向量是推导。建议可以调整，观察可能过期，某些选择改变后需要重新核对绑定。

来源、观察时间和完整性可以沿用现有 Observation 语义。无需为了这项研究增加平行的审计流水线。

## 连接开放，交互约定仍要明确

用户可以提供已有连接、连接工厂、命令或脚本入口。新增连接方式所需的适配尽量留在接入边缘，不让核心按产品名称不断增加分支。

接入边缘需要诚实描述能提供什么。例如：

- 是否能启动命令并取得真实退出结果；
- 是否支持持续 stdin、独立的 stdout/stderr、二进制传输或 PTY；
- 能否读取和写入文件，如何处理路径和权限；
- 中断作用于本地连接进程、远端进程，还是调度器作业；
- 断开后还能否通过原生引用重新查询工作。

这些问题的答案可以不同。只有合并终端输出的通道，不能宣称自己提供了独立 stderr；只有 SSH 客户端退出码时，也不能把它无条件当成远端程序退出码。

我们还没有决定最小通道 API。进程流、请求/响应和文件传输是否需要拆成几个小接口，应由实例验证，暂不规定一个所有连接都必须实现的“大接口”。

当前更值得研究的交互包括命令与会话、流式输出、文件与产物访问、运行环境观察，以及长任务的查询、取消和恢复。它们可以共享 Operation 主线，同时保留 R session、普通进程与 Slurm 作业各自的原生含义。

## Space 与 Binding 能带来什么

讨论中的“工作组合”更接近一组当前有效的关系。比如一个任务位于 analysis 空间，采用某个 Skill，选择某个 R runtime，由一位用户和一个 Agent 参与。它们不必形成永久所有权。

空间层级、任务依赖、能力需求是不同的关系。空间可以是树，任务依赖可以是图，Skill 与 runtime 可以通过所需和提供的 capability 对应。暂时没有理由把它们合成一棵树，也没有理由为了表达它们先建图数据库。

对 Rho 来说，当前有效组合首先应是一份可解释的解析视图：

```text
当前空间、工作引用、显式选择、已有配置、运行观察
                         ↓
           可用能力、当前绑定、来源与缺失条件
                         ↓
                明确的执行请求
                         ↓
                  现有 Operation
```

解析可以先做确定性的事情：查找配置、应用明确覆盖、验证所需能力、报告冲突和过期观察。选择研究方法、把工作交给哪个 Agent，仍是参与者的决策。

“当前绑定了什么”和“建议改成什么”应分开呈现。目标掉线时可以报告绑定失效，不应静默把运行移到另一主机。修改未来的绑定也不应重写已经运行的任务；在途工作保留自己的目标、Operation 和原生引用。

### 作用域不能使用一条笼统的继承规则

Skill 的可发现性、默认参数和运行位置建议，可能适合由父空间提供。显式选择、覆盖和禁用的优先级需要说明；冲突应可见。

凭据、授权范围、活跃连接句柄和正在运行的任务状态，不随空间层级自动继承。Space 不是授权凭证，也不是另一套运行状态 owner。某个工作空间能发现一项能力，并不证明当前调用者能执行它。

有效组合可以从已有配置、能力注册和运行观察中解析得到。只有确实需要保存的用户选择才考虑持久化，不预先复制 Goal、Task、参与者和 runtime 的全部状态。

## 对插件系统的启发

一个复杂场景插件可能需要同时提供方法说明和确定性的执行实现。两者应能分别检查和演化。

方法说明面向人和 Agent：这个场景要问什么、查什么、有哪些选择，什么时候需要人判断。执行实现面向 runtime：接受哪些输入、调用什么能力、如何识别结果、无法确认时留下什么。前者可以辅助形成请求，后者负责守住可执行契约。

插件还需要表达条件缺口，例如工作目录尚未验证、缺少所需 runtime、当前通道不支持独立 stderr、环境观察已过期。这比统一返回“执行失败，请重试”更有助于协作。

以下几种形态都值得考虑，尚不选择其中一种作为统一格式。

### 复用已有能力的方法包

当新增内容主要是领域方法时，Skill 和少量参数说明可能已经够用。它调用现有 capability，返回原来的 Operation 和产物引用，不需要新增执行器。

需要避免把确定性的输出解析和成功判定全部交给模型。遇到这类需求，可以补一个小的执行实现，而不必把整个方法包升级成工作流引擎。

### 提供运行适配的场景包

当原生协议或结果语义尚未被支持时，插件可以提供可测试的适配实现，配上环境发现、输入契约、结果解释和 Skill。连接入口由调用环境供给，场景代码集中处理连上以后的行为。

例如 Slurm 场景应关心提交参数、原生 JobID、队列与 accounting 的观察、取消回执和未知结果的核对。SSH 配置工具的名称不应成为这些规则的一部分。

### 使用外部 helper 的集成包

某些场景可能更适合在用户环境中运行一个确定性的 helper，通过明确协议交换输入输出，继续复用已有 Operation。helper 可以使用当地已有工具，不要求全部逻辑都进入 Rust 核心。

这需要解决协议版本、输出边界、退出语义、分发和资源清理。运行在另一个进程或另一台主机上，不自动构成安全沙箱。helper 也不等于一个会自主规划的 Agent。

配置声明、运行适配和方法说明可以随同一个插件交付，但具体包格式、加载方式、ABI、SDK 与发布渠道尚未决定。也不要求所有插件都提供上述内容。

## 用 YuLab 场景检查这些想法

用户已经给出 YuLabServer 作为连接参考，并接受首版使用原生用户权限、无文件/网络沙箱。用户没有因此指定产品只能采用某个连接管理器。

讨论起初来自只读诊断：连接曾超时，后续成功并观察到 Slurm 19.05.2 和可用分区。原计划使用的 `scancel --ctld` 未出现在服务器的帮助列表中。这说明连接成功之后，命令兼容性和实际作业交互仍需验证。后续实施与验收进展只在[原台账](NEXT-SYSTEM.md)维护，不在这份研究笔记中另列状态。

未来可以沿着这个实例讨论：用户选择入口与工作目标；Agent 借助方法说明补齐可观察条件；插件检查实际目录、工具与资源条件；runtime 收到确定的请求；结果引用原生 JobID、输出和观察。中途断线时，保留原 Operation 的未知结果，随后核对 scheduler，不能悄悄重提作业。

这条过程应允许换一种连接入口，同时保留同一套场景交互规则。能否做到，需要实例证明，不能仅凭一个通用接口的名字判断。

## 和现有 Rho 的关系

目前已有 [RemoteExecutor](../crates/execution/src/remote.rs) 和 [SlurmRuntime](../crates/execution/src/slurm.rs) 等领域端口；[Host](../crates/host/src/lib.rs) 的默认装配仍使用具体 SshRemote，Slurm 原生调用也位于 [SSH adapter](../crates/adapters/ssh/src/slurm.rs) 中。这些事实说明当前已经有部分边界，但还不能据此声称本研究中的灵活接入和组合解析已经实现。

现有五端口、Capability Registry、Operation、Query、领域提交和原生事实引用仍应复用。研究不要求恢复旧插件体系、旧数据资产、审批模型或 Evidence 数据库。

首版采用原生用户权限的选择，不能被解释成“任意插件天然安全”。机械校验、调用者范围、输出上限和真实故障语义继续保留。将来如果要运行不可信插件，需要单独确定威胁模型和实际隔离机制。

## 留待后续研究的问题

- 最小交互契约应该覆盖什么？哪些能力需要拆开，才能避免只支持部分能力的通道被迫伪装支持全部？
- 用户怎样供给已有连接或连接工厂？怎样保持连接生命周期与远端工作生命周期独立？
- 插件怎样表达“可发现的事实”“用户必须决定的选择”“可以使用的默认值”，以及它们的来源和有效期？
- 不同 Space 中的覆盖、禁用和显式绑定怎样处理冲突？插件升级后，已有绑定和在途工作怎样保持可解释？
- 只提供 Skill、提供本地适配、提供外部 helper 的场景，哪些发布和调用约定可以共用？
- Agent 协助生成的配置或适配代码，经过什么验证才能进入执行？哪些验证必须完全不依赖模型判断？

若另行立项，可以先用同一个场景、两条不同连接入口来检验边界，再观察信息补齐、通道缺失、断线和取消的行为。这里没有排期、开发清单或已通过的验收结论。

本轮交付到这份研究文档为止。插件加载器、SDK、通道实现、Space/Binding 解析器、工作图存储和 Agent harness 的实施均不启动。Rho Next 的当前进度与剩余验收只在[原台账](NEXT-SYSTEM.md)维护，不由本文另开一套目标。
