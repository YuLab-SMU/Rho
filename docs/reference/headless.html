Rho local backend ​

Rho selects nine independent capability packages: annotations plus documents, files, R, requirements, tables, media, charts and Agent. Shared contracts contain generic envelopes/service ports and ordinary-file primitives. Each resource/requirement/script schema belongs to its provider through a pure ./contract entry; contracts has no format registry, capability state or catalog. Rho retains its selected schema snapshot and checks provider parity without importing absent implementations. The reusable backend exposes /api/v2 to calling clients and the project-scoped stdio MCP adapter. Its sole registered execution action is r.execute: an explicit project script, requirements, arguments and output declarations. Agents normally use their native tools under existing permissions. Select managed execution only for a concrete need for continuity or a retained application run. r.execute accepts user-written R; the R action catalog does not restrict methods. Activity observation remains independent of managed execution. Analysis recipes and scientific checkers are external consumers, excluded from the application and Plugins npm packages. The browser consumes the same public capabilities. See extraction and extraction acceptance. The split acceptance records the independent package boundary. The 0.4 boundary review records the follow-up decoupling. The public contract lists each owner’s HTTP operations. Current browser behavior is documented in Frontend.

Headless collaboration extension ​

Collaboration documents project capability configuration, shipped Skills, live MCP filtering, conditional structured compositions and undo, explicit view protection, caller/view/shared selections, document/table-anchored feedback, explicit replies, context delivery facts, DOM-free snapshot/event coordination and explicit format-3 archives. These are additive capabilities of the single served contract. Workspace exports older than format 3 reject collaboration state they cannot represent. The new annotations owner requires Documents and optionally Tables for entities. Service --plugins remains a finite allowlist; project configuration cannot expand it. Missing browser renderers do not disable the headless protocol.

Install and start ​

The selected baseline is macOS arm64, Node 22.22.3 (engine range >=22.22.0 <27; the suite and the installed check also passed on Node 24.22.2 and 26.13.0), npm 10.9.8, Python 3 with fcntl, and Rscript 4.5.2. Windows x64 was checked with Node 22.23.4 and Rscript 4.5.1; its writer lock needs no Python, and there rho.cmd starts Rho, and Ctrl+Break on its console or rho --stop stops it in order. The unsigned npm package @rho-workspace/rho contains Plugins and one digest-checked Core binary for each of macOS arm64, Linux x64 and arm64 and Windows x64; CI installs it on each. R and any project-selected packages are external prerequisites, and so are the Agent clients: conversations drive the person's installed Claude Code or Codex. The service, documents, declared files and saved resource readers work without R. An unavailable Rscript returns an unknown dependency probe and prevents managed R execution. Other platforms are unverified.

sh
npm install -g @rho-workspace/rho
rho --root /absolute/projects --state-dir /absolute/service-state

Create the allowed projects directory first. Keep service state outside projects.

A person who has no folders to name runs the package with no arguments instead (from 0.5.4; 0.5.3 prints its usage and exits 2):

sh
npx @rho-workspace/rho

That start uses ~/Rho/projects and ~/Rho/state, creates both, ships the example project on a new state, and prints — after the machine line — the address to open, the two folders, and whether the Agent client and R were found, so a missing one is read at startup rather than discovered later. It opens the address in a browser when stdout is an interactive terminal. Every flagged start keeps the output it had; no argument used to print this page and exit 2.

Startup prints the loopback URL and private connection-file location, never the credential. Opening that URL in a browser on the same machine is the access: the service answers a same-origin request from loopback as the local person, with the reviewed browser scope, no link, no code and no expiry. rho --pair still mints a one-time link when a tab must be narrower — one folder below the service root — or must expire; that link is a credential and is only as good as its five-minute window and single use. A credential that is present must still be valid, so an old link never silently widens to local access; a same-origin request that carries no credential is the machine's own. Host and Origin are checked on every request, and a browser request marked as coming from another site is refused.

A start without --port takes the port this state's last start had, so a bookmarked address and every Agent connection still reach it after a restart; only when another program holds that port does it take a new one, and then each Agent connection file in the state that named the old address is rewritten to the new one, keeping its token. --port 0 always takes a new port. A selected port that is in use is refused with the port named, never replaced. A second start on a state that is already running is refused with the running service's address.

rho --stop [--state-dir DIR] (~/Rho/state without the flag) stops the service that holds that state as Ctrl+C does, from any program. On Windows no signal reaches a console program from another process, so an Agent that started Rho in the background had no orderly way to stop it (episode). The command leaves service.stop in the state folder, which the running launcher takes within half a second, then waits until the state's writer lock is free and the process that served it, named in connection.json, has ended. It prints {"stopped":{"state":…}}, and the service's own output ends with its {"shutdown":…} line. It exits 1 when nothing holds that state, or when the service there is an earlier version that never takes the request (after 10 s, removing it). A start removes a request no service took. The {"shutdown":…} line names what stopped the service (by: rho --stop, SIGTERM, SIGINT or SIGBREAK) and when (at).

--background added to a start runs the same start detached, with its output in <state>/rho.log; the previous start's log becomes rho.previous.log. The command returns once the service prints its ready line, which it prints first, then the process and the log, and exits 0. When the service ends first it prints the service's output and exits with its code; after 60 s without a ready line it says so and exits 1, leaving the service starting. A state that is already running is refused before anything is started. On Windows the service runs under cmd.exe with a console that shows no window, so the console programs it starts share that console; the service is outside the job that ends cmd.exe when the command returns (episode). rho --status [--state-dir DIR] prints one JSON line: whether a service holds that state, its address and process, whether the address answers, the log, a note on how the last service ended (in order, with its by and at, or without a shutdown line), and the other services that announced themselves on this machine. rho --install-skill DIR copies the Agent Skill the package ships into DIR, refusing a folder that holds another skill, and rho --version prints the version.

rho open [FOLDER] (the current folder without it) uses the running Rho that already has the folder as a project, else the one for --state-dir (~/Rho/state), which it starts with --background on --root (~/Rho/projects) and any start flags given when nothing runs there. It opens the folder as a project where it is and opens <url>/#project=<id> in the default browser (--no-browser skips that; --json prints one line). Its text reply says what to tell the person, that Rho is a page in their browser, and how an Agent works there. To open a folder outside the projects folder it calls project.open with the folder's full path, which only the state's operator credential may do: the folder becomes a project of the local person's tab alone (selectedProjects, as a folder chosen in the system dialog), kept across restarts. A tab or an Agent still names folders inside its root. An earlier Rho refuses the full path, and the command says how to proceed (episode).

rho tool index|resolve|call|read [INPUT | -] --as NAME [--project FOLDER] serves an Agent whose client cannot load the MCP server in the current session. It grants the project to session NAME as rho connect does (the same NAME keeps the same credential), starts rho --mcp on that grant for one call, and prints the tool's JSON reply, exiting 1 on an error reply. rho tool list prints the four tools' input schemas. Work done this way is the Agent session's, as over MCP.

--port, --rscript, --core, --plugins and --limits are explicit operator selections; RHO_RSCRIPT, RHO_CORE_BINARY and RHO_PYTHON select equivalent runtimes. A Core override is outside bundled digest verification. A source checkout has no bundled Core: packaging supplies one per platform under vendor/core/PLATFORM/, and startup selects this machine's (darwin-arm64, linux-x64, linux-arm64, win32-x64) by its recorded digest. A package without this platform's Core refuses to start and names the platforms it carries. Without a Core binary on PATH, the workspace and native Agent tools still start. Explicit managed operations and Host activity require --core/RHO_CORE_BINARY or a bundled Core. An explicitly selected missing binary or invalid bundled artifact still fails startup; no alternate executable silently replaces it. Execution acceptance needs an explicit Core selection. General project diagnosis does not treat absent R as a broken workspace; diagnosis for the managed run-r intent does. Core uses the canonical project path plus /.rho/host.sock; macOS permits at most 103 UTF-8 bytes. A longer path fails before Host startup. A Windows Host serves a named pipe instead, with no such limit.

--plugins documents,files selects only those owners; --plugins "" selects none. The default selects all nine. The allowlisted package identities and exact 0.4.0 versions are checked before wiring their typed service ports. Files is required by R object reads and resource resolution; Requirements is required only by the r.execute action. Buffer execution also requires Documents. Files is required by Tables/Media; Tables by Charts. Agent context requests need only the sources they actually use. Missing/incompatible packages and missing required services report unavailable; nothing is installed implicitly. capability.list returns selected package availability and only the available owners' actions/entries. unavailableActions names missing action providers. Selecting only Files/R retains r-objects and object reads without Requirements, Documents or an R installation; managed R execution stays unavailable. Wire API 2.0 and action/view 0.2.0 remain stable.

Owner removal preserves retained request identities, bytes, drafts/undo and layout references. Existing accepted intent delivery returns its original record; new work requiring an absent owner is unavailable. Metadata snapshots and workspace save retain persisted facts even with no plugin selected. Byte exports need Files. Restores report each missing owner/conflict and retain the verified source archive for an explicit later import; they do not install providers. Typed readers validate their own semantics when selected; raw bytes stay usable. Document/resource reads and provider reselection start neither R nor a Host. An explicit requirements.check runs its bounded Rscript probe.

Exact Host and supplied Origin are checked. The bearer credential is project scoped for external callers. CLI shutdown stops only Hosts started by this service and reports confirmation separately. Existing Hosts keep their owner.

Connect your own Agent ​

The project's Agent → Agents tab offers one prompt for any Agent that can configure and run a local stdio MCP server. The prompt names the project and gives one command:

sh
rho connect "/absolute/project folder" --as NAME

The Agent puts a short, stable name for itself in place of NAME.

Each Rho started from the command line writes a note in ~/Rho/running/: its state folder, address and process ID, with no credential. It removes the note when it stops, and a note whose process is gone is ignored. RHO_RUNNING_DIR moves that folder.

Without --state-dir, rho connect asks each running Rho with a note, and the Rho on ~/Rho/state, which of them holds the folder. It refuses when more than one does. The prompt adds --state-dir only for a Rho that has no note and does not use ~/Rho/state, such as one started by a program rather than the CLI.

When the first rho on the service's PATH is not this installation, or cannot run, the prompt starts the command with this Node and cli.js instead. The build marks dist/cli.js executable, so a source checkout linked onto PATH keeps working.

rho connect finds the innermost project holding the folder, grants it to the named Agent and tells the Agent the rest in its reply:

  • the MCP server to add, and the ready entries below;
  • to keep the entry private and out of version control;
  • to call rho_index and check the project ID.

--json prints the --grant reply instead. The command refuses, without a grant:

  • a missing or placeholder name (exit 2);
  • a folder that is not a project, or a state folder no Rho has used (exit 1);
  • a folder that more than one running Rho holds (exit 1);
  • no running Rho, naming the last address it knows (exit 1).

session.instructions is a read-only operation for the local browser or operator. It returns the prompt and the command, without credential contents. Reading or copying starts no Agent, grants no access and edits no client configuration. The Agent uses its own supported configuration mechanism and writes its own entry; the ready entries only spare it the search. The connection episode records the actual clients checked and the limits.

The running service's operator connection also grants one project to a named Agent directly, which setup prompts gave before rho connect:

sh
rho --grant /absolute/service-state/connection.json \
  --project-id EXISTING_PROJECT_ID --session my-agent

--project-id selects an already registered project, including one chosen outside the service's projects folder. The older --project PROJECT_FOLDER form remains available for a folder relative to --root; select exactly one form. Choose a stable session name for each Agent and reuse it on retry. Without --session, the legacy default is claude-code.

The JSON reply supplies mcp.name, mcp.command and mcp.args for the Agent to register in its own client. rho --mcp FILE serves that project grant on stdio with rho_index, rho_resolve, rho_call and rho_read. Connection files are credentials; keep their contents out of prompts and projects. The reply also holds ready entries for the clients whose own mechanism has been used with Rho: claude and codex (their mcp add commands), opencode (the project's .opencode/opencode.json and the entry to merge) and dsh (the DeepSeek Harness profile patch and the entry to append). The bridge sends its MCP client's clientInfo name and version as x-rho-client; Rho keeps it with the grant and shows it as client in the snapshot's agents, ignoring anything that is not short printable text.

Repeating the same grant keeps a valid credential with the same project, methods and profile; changing scope, expired access or stale connection data requires a fresh one. A client may need to reload its tools or open a new session. A saved entry alone does not verify a connection: call rho_index in that client and check its project scope. The page observes grants and actual calls separately and does not claim that an old successful call means the Agent is online now.

The existing --agent claude-code|codex shortcut and session.connect remain available. They use those clients' own mcp add commands (Claude Code in the project folder, Codex in user configuration). They are no longer the page's setup workflow. A stopped service is reported with exit 1; an unknown CLI option exits 2 with usage.

Agent 0.4.11 provides persistent Claude and Codex ACP entries and retains each tool step's human title, ACP category and one identifying input (command, file path, pattern or query; bounded). Since 0.4.17 a command also keeps its exit code and the last 20 lines it printed (at most 2 KiB), and Rho records when each step started. Since 0.4.23 a command keeps the Agent's own few words on what it is for (purpose, from Claude Code's Bash description; one line of at most 200 characters) when it gave them. Other tool output is not kept, and a message that is full gives up a command's output first. The Agent panel selects a backend for a new conversation; existing records retain their choice. --claude PATH / RHO_CLAUDE selects the native CLI; its existing provider/model configuration is used. The four Rho MCP tools retain a project grant, while native tools follow the selected Agent's own permission policy. A native permission request displays only its offered choices to this machine's browser. It adds no Rho approval to an already authorized operation. --agent-backend claude-cli / RHO_AGENT_BACKEND selects the old per-message driver for new conversations; existing records keep their original backend and session identity. That driver now keeps native tools and configured MCP servers, with native permission settings; it no longer disables built-in tools or forces dontAsk. Rho MCP calls keep their existing grant. The noninteractive CLI cannot answer a new native permission prompt; use ACP when interactive permission choices are needed. Configuration changes do not migrate sessions. See the ACP episode for limits and recovery semantics.

--agent-backend codex-acp selects Codex as the service default; --codex PATH / RHO_CODEX optionally selects its native CLI, otherwise codex on PATH, just as --claude / RHO_CLAUDE or claude on PATH selects Claude Code. The pinned official adapters (@agentclientprotocol/codex-acp 2.3.0, written against Codex 0.164.0, and claude-agent-acp 0.97.0) drive that installed client; the packed application omits their optional bundled native clients. Native provider configuration stays with Codex (CODEX_CONFIG and its native config); Rho does not copy Claude credentials to Codex. The Westlake acceptance harness supplies an isolated native configuration with tools.update_plan.enabled=true and features.apply_patch_freeform=true. This enables real tools, not synthetic plans. Rho sets no step cap (maxAgentTurns, Claude's maxTurns) and no message wall time (turnWallMs) by default; a --limits file can set either under conversations. Output, line and record limits still apply, and the person can stop a message at any time. A new Claude Code session opens in Auto unless the person chose a mode in Rho or their Claude settings name one; a model without Auto runs in Accept edits with the adapter's warning. Codex's adapter already opens in its own auto-review mode. ACP cancellation confirms the turn, not every native job.

Any other Agent that speaks ACP v1 runs through the generic driver, with no adapter of its own. conversation.agents.add adds one for new conversations in every project, given its program (on PATH or a path) and arguments, such as ["hermes", "acp"]. Rho starts it once in the project, as conversation.settings.check does: a session is opened, what the Agent offers is read and the session is removed; no message is sent. The Agent is kept as acp:<name> only when it answered; otherwise the reply is the Agent's error, or the last line it printed when it exited first. conversation.settings.read lists the added Agents (added) and, from PATH, the Agents with a known ACP command that are installed and not added (installed; Agent's knownAcpAgents). conversation.agents.remove takes one out of new conversations. Each conversation records the command it started with, so it continues with the same Agent. --acp-command '<argv JSON>' / RHO_ACP_COMMAND still names one ACP Agent at start (acp); without it, dsh acp is used when Harness's acp profile is installed. A Harness session in the folder continues only through Harness's own ACP command, named at start or added. See the episode.

Named workspaces and selected source folders ​

The browser can create a named workspace from one or more natively selected source folders. Its random ID and private owner-state/working directory are independent of the display name and source locations. Source content stays in place. project.source.pick returns a caller-bound receipt; project.createWorkspace consumes receipts with a retained change identity; project.source.add adds a further native choice to an authorized project. Legacy single-directory APIs and original managed operations retain their identities and behavior.

Source entries have stable IDs and canonical roots. Files resolves references @<sourceId>/<relative-path> inside the chosen folders; Documents uses that port for its existing buffers and actual write conditions. Saved R script snapshots can use the same resolver. project.entries lists the project's own directory together with those source folders as @<sourceId> entries, so a project made from source folders is not an empty listing; descending one of them lists that folder under the same reference, and project.openFile accepts it. A source that moved or disappeared is reported instead of followed. Plain relative paths and generated outputs belong to the workspace directory; no implicit union, file copying, symlinks or change of native working directory is performed. Callers must choose explicit sources and inputs. The existing macOS socket-path bound still applies to an actual execution. Native folder selection is platform-specific; source references do not expand scope.

Public contract and client ​

RhoClient is a Node caller: it uses filesystem-backed connection/intent files. It has no generated method-specific types. Its event method returns a raw stream. The separate @rho-workspace/rho/observation transport entry provides DOM-free HTTP/SSE parsing and snapshot-first reconnect reconciliation without Node files. Browser consumers should use the versioned HTTP/SSE boundary.

protocol/index.json publishes requests, responses, typed errors, events and resource declarations, one hashed file per operation under protocol/operations/. protocol.describe returns the same contract. Operations use authenticated POST /api/v2/{operation}, returning {apiVersion:"2.0",ok:true,value} or {apiVersion:"2.0",ok:false,error}. Documents, resources, compositions and event cursors have independent versions.

import { RhoClient } from '@rho-workspace/rho';
const rho = await RhoClient.fromFile('/absolute/service-state/connection.json');
const project = await rho.call('project.create', { name: 'my-project' });
const check = await rho.call('requirements.check', {
  projectId: project.id, requirements: []
});

Execute an explicit project ​

Retain the exact input and identity before delivery. A saved script uses {kind:"disk",path,digest}; an unsaved script uses the exact buffer version.

js
const document = await rho.call('document.open', {
  projectId: project.id, path: 'analysis.R'
});
const intent = await rho.retainOperation('/absolute/caller/intent.json', {
  projectId: project.id, action: 'r.execute', actionVersion: '0.2.0',
  input: {
    script: { kind: 'buffer', documentId: document.id, version: document.version },
    args: [], requirements: [], artifacts: [], completion: null
  }
});
const accepted = await rho.call('action.submit', intent);
const observed = await rho.call('action.observe', {
  projectId: project.id, operationId: intent.operationId
});

The first R argument is a new output-directory path; the script creates it. Further arguments are literal strings or {resource:{id,version}}, resolved to frozen resource bytes after project/freshness checks. The code snapshot, arguments, requirements and artifact declarations stay with the original request. Literal R arguments retain the native program's OS authority.

Artifact declarations contain path, kind and format. Paths stay inside that run's output directory. A completion filename is relative to the run directory, beside its artifacts directory; the public plan returns the full project-relative plan.completion. This keeps transport evidence outside a producer's immutable artifact inventory. Its optional JSON shape is:

json
{"schemaVersion":1,"complete":true,"artifacts":[
  {"path":"output.txt","bytes":3,"sha256":"<64 hexadecimal characters>"}
]}

The producer or explicit project consumer writes that declaration. Registration can expose partial files before it exists. artifact.check verifies exactly the declared files and their bytes. It never runs scientific checkers or interprets their results. A project may run its checker through another r.execute and publish a separate report resource.

Same operation ID and identical input return the retained record; changed input conflicts. On lost delivery, look up the original identity. Explicit retry uses the original frozen code/Core identity; only a retained not-sent request may start its missing owned Host. Observation never recovers a runtime. Core CLI exit 0/1/2/3/4 retains its documented success/rejection/usage/unavailable/ uncertain-delivery meaning. Completion, byte integrity, domain checks and model judgment stay separate. Cancel acknowledgement is followed by native observation before confirmed stop/process-group release.

Resources, shared buffers and entries ​

A CSV or JSON-row table declares its columns, each type and CSV null encodings. Declare a unique nonempty string key and namespace for entity interaction, or key:null for ordinary unkeyed reading. 001 and literal NA remain strings unless that column explicitly declares them missing. Sorting and filtering never create entity IDs. data.plot takes numeric x/y field names and reports deterministic sampling. Comparisons require both versions, keys, namespaces, numeric fields, mapping:"equal-string" and join:"left"|"inner"|"full". The project owns whether that mapping is scientifically meaningful.

Media is explicitly PNG/JPEG/SVG/PDF with provider-declared page/dimension facts. Original bytes and versions remain readable; rectangle context validates page, units and bounds. Rendering, raster decoding, zoom and accessibility are UI work. An object is an explicit JSON exported-snapshot with classes/provenance. Batch Rscript supplies no live R variables or R-memory recovery.

Registered UI contracts include rho.editor, rho.table, rho.scatter, rho.media and rho.object, version 0.2.0. Availability is reported by the selected owner entry; rho.object currently has no browser renderer. The owner validates props and resource roles; scatter requires explicit numeric x/y and an entity key. Rho persists the chosen bindings and layout intent.

Document edits reject stale versions, surrogate splits and invalid Unicode. Human and Agent share content and undo. Save checks the expected buffer version and actual base disk digest immediately before replacement; this is not a filesystem CAS against outside writers. A kernel writer lease protects each project. Acknowledgement follows fsync, rename and directory fsync.

External Agent and compatibility ​

The stdio MCP entry exposes only granted methods and injects the credential's project. The private descriptor includes apiVersion:"2.0". Before managed delivery it fsyncs a write-once original identity/input record; changed reuse conflicts. RHO_MAX_AGENT_INTENTS defaults to 256 per project/session; exhaustion preserves prior intents. Only turns started by Rho automatically capture explicit file locations and final identified changes; reads do not backfill. conversation.read.evidence records captures, pending/interrupted/unavailable states and omissions. Buffer and disk bytes have separate provenance. A capture is an observation, not proof of process input/output. The browser Review/Graph and offline export share the Graph derivation of retained reported/named/observed relationships.

Local-browser-only evidence.preview takes an annotation ID; evidence.export also requires the preview's digest and an original exportId. It writes a new exports/ID directory with static index.html, original selected bytes and the final evidence.json. It does not include full conversation/tool output or discover unstated dependencies. rho --verify-evidence PATH checks it without starting Rho. A complete package can contain explicit missing analysis evidence. This read-only format does not restore a workspace or run an analysis.

File descriptions while a message runs ​

While a message started in Rho runs, its project is compared with the start every describe.everyMs; each changed file that has rested settleMs is read for facts and recorded in conversation.read as the message's descriptions, bound to the digest of the bytes read (the same digest Files gives a kept version). Each file is then described in one sentence by the person's own Claude Code with no tools (Agent's describeFile), using the model the conversation uses. A text file is described from its facts and first lines. A PNG, JPEG, GIF or WebP figure is sent as an image when models.dev lists the model as taking images; otherwise, and for a PDF or another binary file, it is described from what made it: the command that wrote it, the lines of the scripts that command ran around where the figure is named, and the Agent's last words before it (strategy context, with from naming the scripts and why saying why the image was not sent). A model that refuses the image is given that context once, and the message's later figures are not sent as images. A binary file with nothing in the record that made it keeps its facts. A later version with the same facts keeps its sentence.

Each sentence names its model, the version it read, its strategy and its cost: Claude Code's own figure when it knows the model's list price (reported), else the tokens it reports at the price models.dev lists (estimated, naming the listing used), else unknown with Claude Code's guess named. The message's descriptionSpend counts its calls, their dollars and how many were estimated or unknown; it is not part of the session cost the Agent reports. Rho keeps the models.dev catalog in models-dev.json in its state folder and reads it again once a day.

conversation.settings.update with describe: { enabled: false } switches describing off for every conversation of the person: facts are still read, and no model is asked. Codex sessions and a service started without a named Claude binary record facts only. A description still being written when Rho stops reads back as unknown. Facts are observations; a sentence is generated and checks nothing.

Decisions on an answer and the Console ​

conversation.decide is local-browser-only. It records accepted or needs-changes (a note is required) on one finished message of a conversation started in Rho. The decision holds the exact resource versions that message kept (results); a file changed later is not covered by it. A request is retried under its changeId. A different intent under the same identity is a conflict. A later decision names the one it supersedes, and every earlier decision is retained. Agent grants exclude it.

Console 0.1.0 runs a person's shell commands in the project folder. console.run and console.stop accept only the local browser principal. An operator credential or Agent grant cannot use them, while console.list and console.output can be granted to read the record. Each command keeps its text, folder, changeId, who ran it, pid, start/end, exit code or signal and bounded output in .rho/plugins/console/ in the project. Stop signals the command's process group, then kills it after a grace period. After a restart, a command still alive reads continuing and a vanished one unknown. Neither is run again.

Live R and Python sessions (Notebook) ​

Notebook 0.1.0 (@rho-workspace/plugin-kernel) keeps one live R session and one live Python session per project, in the project folder, shared by the person and their Agent. kernel.run queues a cell in its language's session and starts the session when none is live; waitMs waits up to maxWaitMs for it to end. Since Notebook 0.5.3 a cell may name interpreter, a program in a folder of the project such as an environment's .venv/bin/python; the project keeps it for that language's later sessions, and a session in which only that caller ran cells starts again with it, while one where anyone else ran a cell is refused. Each session and each cell records the program (relative to the project when it is in it) and the version that ran it. kernel.read returns the sessions, their variables and the cells, and never starts a session. kernel.inspect returns one value of a live session as its session describes it: its kind (table, model, vector, list, function, value or other), class, size and facts, a page of its rows, elements or parts, the code that reaches it and each part (path names parts by position), and the cell it was read after. A table sorts by a column on request; a model gives its fit and coefficients. It answers none without a live session, busy while a cell runs or waits, missing, timeout, failed or ended, and never starts, waits for or changes a session; a cell asked for during a reading waits for it. kernel.plot returns one kept plot as PNG bytes. kernel.interrupt names a cell: a running cell is stopped with SIGINT and its session and values stay; a waiting cell is not run; an ended cell is returned unchanged. kernel.stop names a session and ends it (SIGTERM, then SIGKILL after stopGraceMs); its running cell ends with an error and its waiting cells are not run. Agent grants receive run, read, inspect, plot and interrupt; kernel.stop accepts only the local browser principal. These operations do not wait in the project's request queue (only their activity record does), so a run waiting for a long cell holds no read and no interrupt.

A cell keeps its changeId per caller: the same identity returns the same cell and never runs it twice. Cells run one at a time per session, in the order they came, and record who ran them (by), their purpose, code, printed output, messages, warnings and error in the order printed, plots, and how they ended: done, error, interrupted (with who asked and when), not-run or unknown. R output reaches Rho as it is printed; each answer about a cell follows a numbered mark on standard output, so it lands after the text printed before it. After each cell the session lists its variables (type, size, one-line summary; Python leaves out modules and imported classes and functions), and the cell names the values it made or changed (defined) and, when neither list was cut, removed (removed). R draws on one device that stays open for the session, as the console's does: a later cell can draw over an earlier cell's plot and reports the plot it changed, and each page a cell starts is kept (a sourced script with two plots has both). Python closes its figures after each cell. State lives in .rho/plugins/kernel/ in the project. Variables live only in their process: when Rho closes, its sessions end, and the next start records each as rho-closed, a running cell as unknown and a waiting one as not-run. Nothing runs again. Rho-started sessions are told to run exploratory code there and to keep the code results rest on in scripts.
