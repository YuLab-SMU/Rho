## Result and review

Boundary teardown, heartbeat maintenance and both reconciliation passes now run
their existing plugin services on the application's shared `StoreExecutor`.
They construct plugin context from the lane's last fully committed identity and
do not acquire `WorkspaceBrokerLane` for plugin-only work. When recovery
actually moves or purges a project file, reconciliation alone briefly acquires
the lane to advance and persist the authoritative Broker project revision,
releases it, and reruns the plugin service on the worker with the new identity.

The Agent contribution adapter owns a cloneable handle to the same executor and
no longer opens a SQLite connection per tool invocation. The required
reconciliation, teardown, heartbeat and retention call families are generic
over `StoreConnection`; method bodies, SQL, lifecycle ordering and owned-Store
callers remain unchanged.

The held-lane regression proves heartbeat, shutdown teardown and no-file-change
reconciliation complete while a second Workspace lane acquisition remains
blocked. All 71 plugin tests pass persistence failure, lifecycle recovery,
grant/replay, crash, guest and A/B isolation cases; retention passes 2/2 and the
complete desktop matrix passes 351 tests with the suite's 21 explicit ignores.
The 193-command inventory is unchanged.

Review found no command name, JSON, schema, permission, grant, guest ABI,
project identity, version, NEWS or release change. Initial Workspace bootstrap
still owns its not-yet-published Broker and Store locally; actual Workspace R
dispatch remains serialized by `WorkspaceBrokerLane`. Remaining broad backend
composition and synchronous non-plugin adapters stay tracked by AM-F-0002 and
AM-F-0003.
