## Decision And Scope

`0.4.0-dev.43` is the immutable published proving release for the stable
promotion. Stable `0.4.0` rebuilds the same reviewed application behavior from
a fresh protected-main commit with stable SemVer metadata. It must not reuse,
rename, replace, or resign any dev.43 artifact or evidence.

Supported release and updater targets are exactly:

- `windows-x86_64`: two-stage Authenticode-signed NSIS installer;
- `darwin-aarch64`: Developer ID signed, notarized, and stapled app/DMG; and
- `linux-x86_64`: final AppRun-patched and Tauri-signed AppImage.

The candidate and publication workflows derive GitHub prerelease state from
the exact SemVer identity. Stable `0.4.0` must create a Draft with
`prerelease=false`; admission, immutable snapshot, and publication must all
preserve that value. Development versions continue to require
`prerelease=true`.

## Stable Update Channel

After publication, both the normal and Tauri stable manifests select exact
`0.4.0`, expose all three platforms, and bind their URLs, hashes, signatures,
release time, and source commit to accepted evidence. The development channel
also selects `0.4.0` because it is newer than dev.43, allowing existing
development installations to cross onto the stable release. Stable clients
never receive a prerelease.

Pages deployment verifies exact generated bytes for the download page and all
present development/stable manifests after CDN propagation. The Stable block
must contain Windows, macOS, and Linux downloads. A missing, partial, stale, or
channel-mismatched manifest fails publication verification.

## Trust And Acceptance

macOS trust remains Developer ID plus Apple notarization. Windows uses the
existing SignPath Free Trial self-signed certificate and must remain labelled
as not publicly trusted; stable product identity does not imply SmartScreen
reputation or SignPath Foundation acceptance.

The owner's stable publication instruction is the human GO authorization for
this bounded release. It is conditional on the exact protected-main six-leg
source matrix, three successful platform candidate jobs, generated passed
candidate/native-updater acceptance, immutable 16-asset Draft audit, protected
publication, and independent live HTTPS verification. Any failed gate returns
the exact candidate to `NO-GO`; no manual reviewer environment gate is added.

## Non-Goals

- no application behavior, persistence, schema, R package, credential, or
  scientific workflow change;
- no reuse of dev.43 artifacts, signatures, hashes, or acceptance records;
- no claim of publicly trusted Windows signing; and
- no stable publication by directly editing a GitHub Release outside the
  protected candidate/publish workflows.

## Verification And Stop Points

1. Synchronize stable version/release metadata, SemVer-derived release state,
   stable Pages verification, tests, documentation, and reviewed notes. Stop
   after complete local affected validation.
2. Pass six protected PR legs, merge the exact reviewed SHA, restore the
   default-branch ruleset, and pass exact-main CI. Stop before candidate build.
3. Build one exact three-platform candidate and verify all 16 Draft assets and
   machine-readable evidence. Stop with the Draft unpublished if any mismatch
   exists.
4. Publish without rebuilding, verify the public non-prerelease Release, then
   verify Stable/Development download blocks and both Tauri manifests live.

## Version And Definition Of Done

Application version metadata advances from `0.4.0-dev.43` to `0.4.0`. The
`rho.bridge` and `rho.agent` package versions remain unchanged because their
package contracts do not change. `NEWS.md` and `.github/release-notes/v0.4.0.md`
record the stable distribution.

Done means exact protected source, Windows/macOS/Linux candidate evidence, a
public `v0.4.0` Release with `draft=false` and `prerelease=false`, three stable
downloads, exact three-target stable and development Tauri manifests, no

## STABLE-040-P1 Pages Fixture-Guard Repair

The first post-release Pages run `32089427072` failed before generation. The
legacy acceptance-fixture guard treated the permanent, valid
`updates/tauri/development.json` left by dev.43 as an unknown fixture file.
That invariant was correct before permanent native manifests existed and is
now stale.

The bounded repair permits only the two normal permanent directory shapes:
`development.json`, or `development.json` plus `stable.json`, when no fixture
marker exists. It continues to reject unknown files, marker-bearing active
fixtures, partial marker layouts, altered fixture hashes, and baseline drift.
Regression tests cover both allowed permanent shapes and an unknown-file
failure. This internal publication-tooling repair does not change application
bytes or version metadata; no new application version is required.
