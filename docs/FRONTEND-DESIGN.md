# Rho 前端设计指导

版本：2026-10-25 · 状态：新选定的设计指导，供后续设计与实现使用。

Rho 应当让研究者直接看见对象、理解变化、继续工作。代码、表格、图和文字是界面的主体；导航、Agent 和执行信息围绕这些内容提供帮助。界面要有清楚的主次、稳定的空间关系、足够的阅读密度，以及经得起长时间使用的细节。

本文补齐前端的视觉方向、布局、组件、状态、内容和验收方法。文中的尺寸、配色和版式是 **Rho 自己选定的起点**，参考资料为判断提供依据，不代表 Nielsen、Karri Saarinen 或 Apple 为 Rho 指定了这些值。产品界面使用 English；本文和用户内容可以使用中文，用户原始 Unicode 必须保留。

本文规定后续交付应达到的目标，**不声明当前前端已经达到这些目标**。现有能力与限制见 [Frontend](FRONTEND.md)，行为契约见 [Interaction guidance](INTERACTION.md)，当前证据见 [Status](STATUS.md)。2026-10-25 撤回的设计稿、旧版式和旧验收尺不恢复为要求。本次文档也不引入新的执行、授权、比较或决策 API。

## 1. 设计依据与取舍

| 参考 | 采用的判断原则 | 在 Rho 中如何落地 |
| --- | --- | --- |
| Jakob Nielsen | 状态可见、符合用户语言、用户控制、一致性、预防错误、减少记忆负担，以及帮助恢复。 | 每个对象有清楚的身份和状态；操作后有可理解的反馈；返回、撤销、恢复有实际路径；错误说明受影响的工作和下一步。[十项启发式原则](https://www.nngroup.com/articles/ten-usability-heuristics/) |
| Karri Saarinen | 为具体工作设计 AI 所处的结构；质量来自贯穿设计与工程的判断和细节投入。 | Agent 围绕选中对象、相关证据和实际结果工作。设计者与开发者共同检查完整流程，持续解决层级、对齐、文案和手感问题。[Design for the AI age](https://linear.app/now/design-for-the-ai-age)、[Why is quality so rare?](https://linear.app/now/why-is-quality-so-rare) |
| Apple | 有明确目的，尊重用户控制，使用熟悉的交互，适应不同使用环境，清楚组织内容并照顾细节。 | 建立稳定导航、明确控件、可读内容和连续的状态变化；让不同输入方式与窗口尺寸都能完成工作。[Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles) |

这些原则发生冲突时，先保护事实与用户工作，再保证主要任务可完成和内容可读，然后优化效率与视觉表现。信息完整不等于把所有细节同时摆在屏幕上；将来源、技术记录和次要操作放入可发现的详情入口，仍须保留直接访问能力。

采用参考资料时要说明适用范围。Apple 的原生材质、平台控件和点数单位有各自环境；Rho 当前是浏览器应用，按 Web 的实际输入、缩放和可访问性条件设计。Linear 的视觉外观也不直接成为 Rho 的样式。本文的目标是形成适合研究工作的界面判断。

## 2. 整体气质与信息层级

整体应当安静、清晰、精确。研究内容可以密集，界面的解释和操作应当有秩序。用户进入工作区后，先辨认自己正在看的对象和数据，再找到当前动作，随后理解状态，最后按需查看技术细节。

| 层级 | 内容 | 视觉处理 |
| --- | --- | --- |
| 主体 | 代码、数据、图、研究文字、比较中的差异 | 获得主要面积；正文清晰；数值与关系可直接阅读。 |
| 当前任务 | 对象标题、选区、主要动作、正在回答的问题 | 靠近主体；标题与选择关系明确；当前动作有克制的强调。 |
| 支持信息 | 项目位置、保存状态、运行阶段、相关结果 | 较低视觉权重；位置稳定；真正影响下一步时提升。 |
| 追溯细节 | 完整路径、资源版本、请求标识、校验和、原始日志 | 在有名称的详情中完整展示和复制；不能用随机标识代替对象名称。 |

当前浏览器闭环证明了部分功能可以完成，但暴露了需要纠正的设计问题：导航与状态栏层层堆叠；操作普遍具有同等边框和强调；比较两侧的表头及首行错位；文件名和技术标识争抢注意力；窄窗口仍让用户在过窄的区域来回寻找数值。后续设计必须针对这些实际问题交付变化。

留白用于分组和阅读。五行表格下方保留空白是正常的；为了填满屏幕添加卡片没有价值。需要修正的是内容被挤到很小区域、工具栏占据大量高度、相关内容彼此分离，或没有主次的空白分布。

<a id="workspace-layout"></a>
## 3. 信息架构与工作区布局

### 3.1 导航分工

沿用真实的项目、文件、工作区和执行对象。项目导航回答“在哪里”，工作区回答“正在看什么”，局部工具回答“对这个对象能做什么”。同一个层级不在多个位置重复展开。

| 区域 | 承担的工作 | 设计要求 |
| --- | --- | --- |
| 项目导航 | 项目切换、Overview、Files、Activity、设置和工作区入口 | 保持顺序稳定；当前项可辨认；可折叠。执行日志和插件命令不各自扩张成新的一级导航。 |
| 工作区标题区 | 当前工作区、必要的返回关系、工作区级动作 | 项目名称不重复铺满多行；低频管理操作进入菜单。 |
| 对象标签与工具区 | 当前对象、切换、对象动作、选择状态 | 标签可识别类型和名称；保存状态贴近文档；只展示与当前对象有关的工具。 |
| 主内容区 | 阅读、编辑、选择、比较 | 优先获得空间；滚动属于实际内容容器；不被长消息或工具栏推离视线。 |
| 按需打开的辅助区 | Agent、来源、运行详情、关联内容 | 有明确标题、关闭和返回；宽度不足时转为可切换视图；关闭不终止后台任务。 |

应用启动页以打开最近项目和选择项目为主。项目 Overview 展示继续工作的入口、现有工作区和有意义的最近结果；以内容的可识别性决定密度。Files 保留路径与文件层级，Activity 保留时间与运行关系，设置按配置对象分组。这些页面共享排版与组件，但不用同一种大卡片模板强行容纳所有内容。

### 3.2 工作区的常态

新工作区以一个主要阅读或编辑对象为起点，已有工作区优先恢复用户安排。相关结果可以并排，Agent 可以按需打开，布局来自具体任务和用户选择。没有常驻三栏的产品要求。对当前任务没有作用的面板应当容易收起，用户安排的受保护视图仍遵循现有布局契约。

桌面常态以一层工作区上下文和一层对象工具组织内容；标签可以与对象标题协调，但不再逐项增加项目、工作区、Agent、状态、选区、来源的整行顶栏。两层是默认构图预算，不是忽略长标题、可访问性或必要警告的硬性高度限制。新增加一条常驻栏时，必须说明它服务的独立任务及为何不能放在现有区域。

以下示意表达目标层级，**不是已实现界面或像素稿**：

```text
Project navigation | Air quality / Analysis                         Agent
                   | analysis.R  [Monthly ozone]  notes.md    Filter  ...
                   | Original complete cases · 5 rows
                   |
                   | Month       n       Mean ozone (ppb)
                   | May        24                 24.125
                   | ...
                   |
                   | [Selected: May]       Ask about selection
```

示意中的方法和行数是内容说明，不另设一条有背景、边框和按钮的工具栏。选区信息可以贴近内容或放入固定的局部区域，位置取决于是否遮挡数据。它不应让整个工作区在每次选择时上下跳动。持续反馈、来源详情和运行记录通过其对应入口打开，不全部留在主阅读路径上。

### 3.3 布局尺寸起点

桌面导航展开宽度以 216–248 CSS px 为起点；需要辅助阅读时，辅助区以 320–400 CSS px 为起点。可用主内容宽度决定是否展开这些区域。不能让一个 360 px 的 Agent 面板挤压到只剩不可读的表格。

窗口分隔使用细线和明确的拖动命中区，拖动时才加强反馈；也提供菜单或键盘可用的调整方式。面板嵌套层级要能被理解，同一分隔不叠加外框、内框和阴影。布局调整后保留焦点、选区和阅读位置，具体权限与持久化条件继续遵循 [Interaction guidance](INTERACTION.md#rules-for-workspace-changes)。

<a id="type-and-density"></a>
## 4. 排版、间距与密度

Apple 的排版指导强调可读字号、适当字重和用字体建立层级；Rho 在 Web 中采用下面的具体起点。[Typography](https://developer.apple.com/design/human-interface-guidelines/typography)

### 4.1 字体层级

界面优先使用系统无衬线字体及系统 CJK 回退，代码使用成熟的等宽字体栈。每一类内容的字重、行高和标点规则保持一致。不要为了“精致”大量使用细字重、全大写标签或低对比小字。

| 用途 | 默认 CSS 字号 / 行高 | 字重与用途说明 |
| --- | --- | --- |
| 项目或页面标题 | 22 / 30 px | 600；只出现在页面级上下文，工作区不重复一个巨大的页面标题。 |
| 面板或对象标题 | 15 / 22 px | 600；长名称允许可控换行或完整查看。 |
| 界面正文、输入、Agent 回答 | 14 / 21 px | 400；较长阅读内容可用 15 / 24 px。 |
| 数据表 | 13 / 20 px | 400；表头 500；行列密集时仍保持数值可辨。 |
| 次要说明 | 12 / 18 px | 400；不用来承载主要判断或唯一的错误说明。 |
| 代码 | 13 / 20 px | 等宽；允许用户放大；保留缩进、Unicode 和行号关系。 |

数值列使用等宽数字并按数值对齐。小数显示、科学计数法、日期和单位由内容语义决定；界面排版不能擅自舍弃精度。只要取了展示精度，就应能获得原值，并说明显示与原值的区别。

上述值用于默认密度。较大文本设置、中文组合输入、较长翻译或触控环境需要改变行高和控件高度。内容不得因固定行高被裁掉。默认不把必要信息缩到 12 px 以下来换取空间。

### 4.2 间距与行密度

使用 4、8、12、16、24、32 px 的间距序列形成一致节奏：4–8 用于紧密关联项，12–16 用于局部分组，24–32 用于不同阅读区域。优先通过对齐和间距表达关系，必要时加分隔线。

桌面普通控件高 32–36 px；常规表格单行以 32 px 为起点；密集表格可以采用 28 px 行高，但必须保留键盘选择和足够的点击范围。多行文本自然增高，不压成一条省略号。触控呈现采用至少 44 px 的常用操作命中区，作为 Rho 的易用性目标。可访问性标准及例外另见[可访问性要求](#accessibility)。

同一工具栏的控件共享基线和高度；两侧比较区域共享标题节奏；表格表头、数值与说明的边界对齐。不能通过每个组件单独添加任意 padding 修补全局布局。

<a id="color-and-material"></a>
## 5. 颜色、材质与图标

### 5.1 基础视觉方向

采用浅色中性工作面和一种克制的蓝色交互强调。色彩主要帮助辨认选择、焦点和真正重要的状态。图中的科学编码保持独立，图例、单位和类别归属由图形 owner 负责。界面整体不以某种执行状态色铺底。

下面是新的语义色值起点，后续应映射到现有 CSS 变量接口，而非在每个插件内重复硬编码。颜色模式若扩展为深色，必须独立设计和验证，不能简单反色并宣称完成。

| 语义 | 起始色值 | 使用边界 |
| --- | --- | --- |
| 页面底 / 内容面 | `#F5F6F8` / `#FFFFFF` | 用很小的明度差区分导航背景与工作内容。 |
| 主要文字 | `#20242C` | 标题、正文、数据。 |
| 次要文字 | `#566171` | 来源摘要、稳定状态、说明；仍须可读。 |
| 交互强调 | `#3459C4` | 主动作、链接、焦点；白字主按钮使用此底色。 |
| 选择底色 | `#EDF2FF` | 配合边缘标记或选中语义；不只靠底色表示选择。 |
| 结构分隔 | `#DDE1E7` | 装饰性分组线；不独自承担识别输入框、选择或焦点的责任。 |
| 控件边界 | `#7C8798` | 需要边界才能辨认的输入控件，避免过浅的轮廓。 |
| 成功 / 警告 / 错误文字 | `#24634B` / `#805B08` / `#B33A3A` | 与状态文字或图标同时使用；成功不等于科学结论被验证。 |

按 WCAG 相对亮度公式检查，主要文字、次要文字与强调色在白底上的对比度分别约为 15.55:1、6.28:1、6.23:1；控件边界在白底上约为 3.64:1。这只验证了列明的色对。hover、选中、透明度、图上文字和所有实际组合仍需逐项验证；本表不构成整站可访问性通过声明。

颜色应有一致含义，并提供颜色以外的信号。这是 Apple 色彩指导和 Web 可访问性要求都强调的方向。[Color](https://developer.apple.com/design/human-interface-guidelines/color)

### 5.2 形状与表面

常用控件圆角以 6 px、菜单和浮层以 8 px 为起点。圆角用于柔化边界，不能让每一行文字都变成胶囊。普通面板依靠排版和分隔线组织；阴影集中用于真正浮起的菜单、弹层和拖动反馈。

工作内容保持不透明、稳定的阅读底面。装饰性透明、模糊和渐变需要有可验证的作用，否则不加入研究工作面。避免多层卡片套卡片、全屏大圆角容器、每个状态一枚彩色徽章，以及用粗重边框强调所有按钮。

### 5.3 图标

使用同一套来源明确的图标，常规尺寸 16 px，必要时 20 px；保持一致的笔画、光学重量和对齐。熟悉且空间受限的操作可以只用图标，但必须有可访问名称、可发现的提示和清楚的焦点状态。陌生的研究操作用文字说明。省略号菜单收纳低频操作，不能成为关键下一步的唯一且不可发现入口。

<a id="components"></a>
## 6. 公共组件与交互状态

公共组件要共享视觉与输入规则。按钮是否突出由当前任务决定，不能因为来自不同插件就各自争取主按钮样式。Apple 对按钮和工具栏的建议提供了参考：突出主要动作，明确标签，主动减少拥挤。[Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)、[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)

| 组件 | 设计要求 |
| --- | --- |
| 主按钮 | 同一局部决策区域通常只有一个；使用实色强调。没有明确主动作时不必强设。运行中不因文本增长撑开整行。 |
| 次按钮与轻量动作 | 常用次动作采用中性边界或轻量文字；hover、按下、焦点均可辨认。布局工具不与科研主动作竞争。 |
| 危险动作 | 使用明确动词和目标；确认仅用于确有不可逆后果或授权缺口的情况。既有 Agent 授权不新增 Rho 审批。 |
| 菜单 | 分组围绕任务；展示当前选择、可用性和真实快捷键。打开后焦点可移动，关闭后回到触发点。 |
| 标签页 | 当前标签、键盘焦点、未保存、运行状态各有不同表示。溢出仍能切换；关闭与切换的命中区分开。 |
| 输入与表单 | 持久标签、输入示例、就地验证；错误不清空输入。占位文字不替代标签。数值输入说明范围和单位。 |
| 选择摘要 | 用对象名称、行键、列名或代码范围描述；可展开来源，支持清除或重新选择。多选显示数量和可查看明细。 |
| 状态 | 默认是文字、图标或小型标记。只有实际可操作时才使用按钮外形；信息状态和操作入口分开。 |
| 提示与通知 | 短暂成功反馈靠近操作；需要处理的错误持续可见；全局通知仅承载跨区域事件，不能遮住编辑器和主要动作。 |
| 对话框 | 用于确需集中处理的短任务；标题、说明、主动作、取消关系明确。长篇 Agent 输出和日志放可持续阅读的视图。 |
| 空态 | 说明这里会出现什么，并给出一个实际可执行的下一步。区分无数据、筛选无匹配、尚未运行、无权限和加载失败。 |

每个可交互组件至少考虑默认、hover、键盘焦点、按下或选中、禁用、忙碌、错误的适用状态。禁用不是解释：关键操作不可用时，附近说明原因以及如何解除。已有内容加载更新时保留旧内容与更新时间，并明确其是否仍代表当前结果。

<a id="research-content"></a>
## 7. 代码、表格、图和文档

### 7.1 代码与文档

编辑器保持代码区域稳定，工具栏只留下当前任务常用动作。保存状态贴近文件身份；外部写入冲突在该文档范围解释。复用成熟编辑能力，保留选择、撤销、查找、缩进、Unicode、组合输入和多视图共享缓冲区，不用外观统一为理由重做一套文件状态。

普通文档以适合阅读的行长呈现，长段落不铺满超宽窗口；代码和数据视图按其结构使用更大横向空间。编辑与预览切换不丢位置。只读结果与可编辑源文件要能分辨，避免用户以为修改了源数据。

### 7.2 表格

列头可读、数值右对齐、文本按阅读方向对齐，单位出现在列名或紧邻说明中。排序方向、筛选条件和选中范围应能分别识别。必要时固定列头和关键标识列；长表使用适当的渲染策略，不能改变实际行数或让读屏器失去定位。

默认使用轻量水平分隔或足够行距，按比较需要决定是否增加纵向线。不要让网格线比数据更突出。截断列名时提供完整读取和合理调整方式；表格水平滚动留在表格区域，操作和上下文不随之丢失。

`NA`、缺失、零、空字符串和无穷值保留区别。小数、极小概率值和科学计数法不能为整齐而被显示成有误导性的零。显示筛选后的行数与总数时，要依据实际已知范围；局部加载不能伪装成完整结果。

### 7.3 图

图的标题、坐标、单位、图例和来源需可读。并排比较保留图的宽高比；可比较坐标尺度须由领域语义确认，不能仅为外观统一而自动重设。选择标记与科学颜色编码分离，局部选中不改变整张图的数据含义。

现有静态 PNG 只能提供其真实支持的查看、缩放和关联操作；不得绘制看似可选中数据点的假控件。交互式选点、刷选和可访问描述由相应组件声明并实现。图加载失败时保留对象名称、来源和恢复入口。

<a id="agent-context"></a>
## 8. 选中对象、提问与 Agent

### 8.1 先让用户认出提问对象

选中 May 行后，用户应当看见类似 `May · Monthly ozone · Original complete cases` 的上下文。完整锚点保留资源、版本、实体键等实际信息，默认呈现用研究者能辨认的名称。相同文件名来自不同结果时，必须显示足以区分的来源。

`Ask about selection` 靠近选区或稳定的局部工具区。输入框携带可检查的上下文摘要，允许用户编辑问题；选择变化不能悄悄改变已经提交的问题。输入焦点和选择高亮是两个状态，要在配色和形状上区分。

问题较短时可在局部展开，持续对话或长解释使用辅助阅读区。展开不遮住被问的关键值，不把比较另一侧推出对齐位置，也不在每次选中时强制打开整块 Agent 面板。

### 8.2 Agent 面板的结构

面板先展示当前问题与对象关系，再展示事实明确的进展和回答，最后列出相关结果与操作。详细工具调用、请求标识和原始输出可以展开。历史任务可返回，新的消息到达时保留用户正在阅读的位置，并提供新内容提示。

当前集成使用外部 Agent。复制文本的动作必须写成 `Copy request`；复制成功只表示剪贴板操作成功。不能显示成已经发送，也不能把上下文读取或执行结束当成 Agent 已回答。若后续接入原生发送，须由实际传输与回执能力支持新的状态。

回答与产物保持直接联系：使用 `Monthly ozone · Ozone available`、`Ozone by month` 等有意义的名称，完整文件名和版本在详情中可见。结果条目提供明确的打开入口；后续若实现集中 `Compare results` 入口，应把两份准确资源一起带入，而不是让用户从一串哈希按钮猜测配对。

### 8.3 自动变化的边界

新的回答可以提示有结果可看。替换、移动、隐藏当前视图仍遵循已授权的布局范围、保护条件和实际条件写入；不能用“Agent 认为更好”扩大权限。输入期间不抢焦点，不折叠正在看的内容，不更换当前选中的版本。

结果已打开不代表结论被采纳。没有持久决策 owner 的地方，不能添加一个只改变颜色的 `Accepted` 按钮来假装完成研究判断。研究者可以在现有笔记中记录判断；未来决策能力要另行定义其真实语义。

<a id="comparison"></a>
## 9. 结果比较

比较是一项完整阅读任务。用户需要知道两边是什么、为什么不同、哪些值变化、能否继续追溯和返回。仅把两张表拆成两个窗口，还不能满足这些需要。

### 9.1 共同上下文与成对版式

比较区域顶部用一个共同标题说明对象和变化问题，例如 `Monthly ozone — missing-value rule`。两侧用明确名称区分 `Original · Complete cases` 与 `Updated · Ozone available`，同时保留各自文件名、资源版本和运行来源的详情入口。`Updated` 只描述这次操作的结果，不自动表示更正确或全局最新。

共同操作放在比较层；只作用于一侧的筛选与查看动作留在该侧。两侧标题区、方法说明区、列头和首个数据行对齐。不要把仅一侧的长回答、多个打开按钮或布局控件塞在表格上方，导致用户每比一个值都要跨越不同高度。

```text
Monthly ozone — missing-value rule                    Details  ...

Original · Complete cases       Updated · Ozone available
monthly-ozone.csv               monthly-ozone.csv

Month     n   Mean (ppb)        Month     n   Mean (ppb)
May      24       24.125        May      26       23.615
June      …            …       June      …            …
```

示意中的三位小数只是展示精度，原值必须可获得。该布局是后续设计目标；现有应用的真实能力是打开准确版本并由用户分屏，尚不能据此宣称已提供统一比较组件。

### 9.2 对齐必须有语义依据

能按月键配对时，匹配由相应表格或比较 owner 的真实能力提供；行缺失、重复键、排序不同和不兼容模式必须有说明。没有可靠映射时保留独立表格，并明确 `Rows are not aligned`；不能按视觉行号伪造对应关系。

联动滚动、共同排序、差异高亮和差值列都属于需要实际支持的能力。只在拥有明确映射和来源时提供；尚未实现时不能展示假开关。相同颜色的高亮必须表示相同含义，数值变大或变小不自动涂成“好”或“坏”。

### 9.3 将变化说清楚

在已经验证的 airquality 示例中，May 的样本数从 24 增至 26，均值从 24.125 变为约 23.615385 ppb。界面应让人直接看到这两个量的变化，并理解它们与缺失值规则的关系。数值差异来自结果与检查；科学上应采用哪种规则仍需研究判断。[实际证据](BASE-R-EPISODE.md)

有可靠 owner 结果时，可提供简洁的变化摘要并链接到对应行。Agent 的解释标明为回答，不能冒充确定性的差异计算。完整运行日志和校验和保留在详情，不挤占成对阅读区域。

### 9.4 返回与窄屏

退出比较后回到原对象、选区与阅读位置。宽度不足时优先收起不必要的辅助区域；仍无法读清两侧时使用保留两份身份的切换视图。可以提供 `Original` / `Updated` 切换和始终可见的方法摘要，而不是强行保留两条极窄表格。不同呈现不改变资源绑定或用户已保存的布局事实。

<a id="episode-states"></a>
## 10. 完整流程的屏幕状态

以真实 base-R 工程作为第一组设计对象。以下每个状态都应有可审查的界面说明或原型，后续实现需在真实浏览器中逐项检查。表中是应呈现的用户体验，缺失能力仍按其实际 owner 补齐。

| 状态 | 必须让用户理解 | 主要呈现与下一步 |
| --- | --- | --- |
| 打开原结果 | 看的是哪次结果、使用了什么规则 | 有意义的标题、表格和来源摘要；可读代码或选中行。 |
| 选中 May | 当前选中了哪一行、属于哪个版本 | 不遮挡数值的选区标记与摘要；`Ask about selection`。 |
| 写问题 | 问题将携带什么上下文 | 可编辑问题、明确上下文、真实提交或外部交接动作；取消后可回到对象。 |
| 等待外部 Agent | 已复制、已读取、执行中或已回复中的哪一种事实 | 就地状态、已有内容、可查看的实际进展；避免虚假的发送与完成。 |
| 新结果到达 | 哪个问题有了回答，哪些资源可以打开 | 回答、结果名称、准确来源；保留旧结果和未保存笔记。 |
| 比较 | 两份结果的规则、对应关系与变化 | 对齐的可读内容、方法标签、详情入口；继续查看或回到原对象。 |
| 断连 | 观察中断，执行结果可能仍未知 | 持续提示、最后观察信息和 `Reconnect`；保留可用内容与输入。 |
| 恢复连接 | 现在观察到的仍是同一请求 | 更新事实，显示未完成或已完成的实际状态；不替用户新建执行。 |
| 保存冲突 | 内存内容与文件已有不同变化 | 保留双方可用内容，说明冲突和实际支持的处理选项；不静默覆盖。 |

另外需要覆盖：没有数据、筛选无匹配、结果部分到达、结果损坏、插件缺失、无权限、名称很长、说明多行、多个问题并存。加载、成功、失败不能是同一张理想截图只换一个小图标。

<a id="recovery"></a>
## 11. 断连、错误与恢复

连接中断使用工作区可见且不遮挡内容的提示，例如 `Connection lost. Showing the last observed state.`，附 `Reconnect` 和必要的最后观察时间。保留可读结果、已确认的内容和未保存输入。恢复观察不以新请求重跑工作；提示不能用一个假的成功状态覆盖未知结果。

局部错误放在受影响的对象或操作附近；只有整个应用无法继续时才采用全页错误。错误应说明发生了什么、影响哪部分工作、哪些内容仍在，以及现在可以做什么。原始错误码、堆栈和诊断标识放在可复制详情中。

运行完成、文件完整性、领域检查和研究者判断分别表达。可以在默认视图先显示最相关的一项，其余从 `Result details` 查看；发现校验失败或领域检查失败时应提升相应问题的可见性。不能汇总成含义不明的绿色 `All good`。

重试按钮必须说明重试的是保存、读取、连接还是执行。未知提交结果先查询原请求；只有已有契约与授权支持时才采取相应恢复动作。关闭标签页、取消请求、确认停止和关闭 Host 是不同操作，不共用含糊的 `Stop`。

<a id="responsive"></a>
## 12. 响应式与布局连续性

布局判断基于每个内容区域的可用宽度、文字长度和当前任务。视口断点是检查场景，不是足以决定所有布局的规则。Apple 的布局指导强调对齐、分组及在窗口和文字大小变化时保持可理解的关系；下面是 Rho 的应用方式。[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)

| 检查情境 | 呈现要求 |
| --- | --- |
| 1440 px 宽桌面 | 主内容与必要辅助区域可以共存；比较两侧可读；大屏不扩大所有控件和留白。 |
| 1024 px 常规窗口 | 优先保护内容；视需要收起导航或辅助区；常用操作仍可发现。 |
| 768 px 窄窗口 | 允许单一主要内容区；比较以实际可读性决定并排或切换；表格不被常驻侧栏压窄。 |
| 390 px 小窗口 | 单个主要对象、明确返回和对象切换；输入与主要动作完整可达；允许表格局部横向滚动。 |
| 320 CSS px 等效宽度及放大文字 | 普通说明、表单和导航能重排；二维内容使用明确的局部访问方式；不裁掉动作与输入。 |

缩放、折叠导航和临时单视图呈现不应悄悄提交一个新的持久布局。用户明确拖动或安排视图，才按现有条件写入契约处理。恢复较宽窗口时，应恢复合理的展示关系，而不是新建重复视图。

长名称优先保留能区分对象的部分，并提供完整名称；危险操作和关键状态不省略到无法识别。表单在窄屏按阅读顺序排列，文字放大后允许按钮和说明自然换行。横向滚动不能成为阅读普通说明段落的前提。

<a id="accessibility"></a>
## 13. 键盘、输入与可访问性

可访问性从结构与状态设计开始。目标为适用的 WCAG 2.2 AA 要求；没有完整审查记录时只报告已验证项目，不宣称整体符合标准。

- 普通文字与背景对比度至少 4.5:1；符合标准定义的大字号文字可采用 3:1。必要的控件识别与状态边界与相邻颜色至少达到 3:1，并按标准适用范围判断。装饰性分隔线不能替代必要边界。[文字对比](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非文本对比](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- WCAG 2.2 AA 的目标尺寸规则为至少 24 × 24 CSS px，并有间距、行内等规定例外。Rho 常用触控目标采用前述 44 px 易用性起点；这是项目选择，不是把 Apple 的点数换成 CSS 像素。[Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- 普通内容在 320 CSS px 等效宽度可重排。数据表等具有二维意义的内容有适用例外，不能据此让整个页面横向溢出。[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- 导航、菜单、选区操作、对象切换、布局和恢复必须有键盘路径。焦点与选中态分开；焦点可见且不会被粘性工具栏或弹层完全遮挡。拖拽有可用替代方式。普通控件焦点环以 2 px 实线、2 px 外偏移为起点，按相邻颜色和裁切条件验证。[Focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- 采用语义正确的标题、按钮、标签、表头和关联说明。虚拟化表格说明已加载范围与总量的已知情况；读屏器能理解当前对象、行列和选择。频繁的执行输出不逐条打断朗读。
- 保留浏览器原生缩放、文本选择、复制和合理快捷键习惯。检查 200% 文字放大，关键操作仍可完成；另行检查重排条件，不把一次缩放截图等同于全部可访问性验证。[Resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)
- 验证中文 IME 的组合、候选、确认和撤销。输入法确认键不触发发送或运行；光标、选区和焦点在面板开关、返回和恢复时有明确归属。
- 尊重减少动态效果设置；不用闪烁、颜色或动画作为唯一提示。tooltip 在键盘路径上可访问，关键解释不能只在 hover 时出现。

键盘与辅助技术需要实际使用检查。自动化名称检查、对比度扫描和 DOM 结构检查只是部分证据。Apple 的可访问性指导也强调可感知、可适应和多种使用方式。[Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

<a id="feedback-and-motion"></a>
## 14. 反馈、加载与动效

动作有即时可感知的局部反馈，后台工作有稳定位置的状态。仅在确定总量和实际完成量时显示百分比；否则使用已知阶段和最后反馈。断连时停止把无法观察的工作表现成持续取得新进展。

保留已获得的部分结果。更新时可以显示局部加载状态，不要清空整个页面再显示骨架。占位结构与即将出现的内容相近，避免结果加载后控件位置大幅跳动。需要用户处理的失败持续存在；复制等短反馈可以消退。

动效主要解释展开、关闭、位置变化或按下反馈。普通过渡以 120–180 ms 为起点，尊重减少动态效果；高频输入、数值变化和表格浏览避免反复动画。运行状态不使用无意义的舞动、彩色光晕或庆祝效果。Apple 对动效的建议同样强调目的、简短和可选择性。[Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

<a id="product-writing"></a>
## 15. 产品文案

文案明确对象和动作，采用 sentence case，使用稳定术语。按钮用 `Open result`、`Copy request`、`Reconnect`、`Save changes` 等实际动作；状态用可核实的事实。长解释先讲影响与下一步，技术原因按需展开。Apple 的写作指导支持清晰、与情境相符的语言及一致的表达方式。[Writing](https://developer.apple.com/design/human-interface-guidelines/writing)

| 情境 | 推荐呈现 | 需避免的问题 |
| --- | --- | --- |
| 复制外部 Agent 请求 | `Request copied` | 写成 `Sent` 会误报传输事实。 |
| 新结果 | `Monthly ozone · Ozone available`，附文件名与详情 | 用请求哈希做主要按钮，用户无法辨认内容。 |
| 保存冲突 | `This file changed on disk. Your edits are still here.`，附真实可用的处理动作 | `Save failed` 没有说明影响，也没有保留工作的承诺依据。 |
| 观察中断 | `Connection lost`、`Reconnect` | 无证据写成运行失败，或用 `Retry` 隐藏是否会重跑。 |
| 执行结束 | `Run completed`，独立展示检查事实 | 用 `Verified` 同时概括文件完整、领域正确和科研采纳。 |
| 关闭视图 | `Close view` | 暗示停止后台执行。 |

保留必要的专业名词、文件扩展名和单位。名称的友好呈现不能改变真实资源身份；时间和“最新”必须有明确参照。错误说明避免责怪用户，空态给出可操作的下一步，不写夸张宣传或笼统的 AI 承诺。

<a id="ownership"></a>
## 16. 应用与插件的设计分工

Rho 负责导航、工作区、窗口、共享操作、通用状态表达和视觉基础。插件负责其内容语义、科学结果、专业控件以及可提供的交互能力；Core 负责执行事实。颜色、排版、通用按钮和焦点规则通过应用提供的接口协调，不能依靠针对每个插件内部 DOM 的全局补丁维持外观。

插件视图应融入相同的表面、文字和工具节奏，避免自行重复项目标题、全局 Agent 栏和工作区导航。需要不同密度或专业交互时说明实际原因，并验证键盘、选择、焦点和错误处理。成熟组件可以沿用其可靠交互，通过受支持的主题和样式能力适配，不为统一外观损坏编辑、图表或表格行为。

视觉指导不授予新 API。统一比较、语义配对、图上选点或持久研究判断若需要新能力，先明确消费者、owner 和公开边界；缺失能力在设计与状态记录中标出。外观可以先形成完整目标，但实现必须报告实际到达的位置。

<a id="delivery"></a>
## 17. 设计和开发如何交付

### 17.1 先定义完整状态，再做细节

每项前端工作沿用 [Development](DEVELOPMENT.md#write-an-interaction-episode) 的流程 brief，并补上视觉阅读顺序、主要动作、内容极值和目标呈现。设计至少涵盖常态、输入、等待、结果、错误和返回中适用的状态；涉及比较时同时说明两侧内容如何对应。

小改动可以直接在实现中设计并审查。影响整体层级或多状态流转的改动，先形成可查看的版式与关键状态，再通过原型或实际界面检查过渡。只画一个整洁的空态或成功页不够；必须放入真实代码、表格、较长回答、长文件名和错误信息。

### 17.2 交付给实现者的内容

交付物应让另一位开发者能判断主要区域如何组织、什么应突出、状态如何变化、窄屏如何处理。包括适用的布局说明、组件状态、语义 token、文案、输入行为、数据与来源边界，以及待补齐的真实能力。无需为每个 patch 建立新的文档或审批仪式。

对数值基线的偏离可以接受，但要有具体任务或可访问性理由。同样，全部使用规定 token 也不能证明界面质量。设计审查必须看整体构图、内容阅读和连续使用；发现失衡时应调整组合方式，而不是只微调一个颜色。

### 17.3 实际浏览器检查

实现后在实际浏览器逐步操作，保存适用状态与观察记录。先检查主要阅读路径、点击和输入，再检查等待、错误、窄屏及恢复；检查放大文字、长内容和键盘路径。自动截图可以记录结果，不能代替看图和真实操作。

视觉改变若影响插件容器、共享工具栏或数据区域，要重新检查相邻状态和尺寸。浏览器、功能、可访问性、视觉审查、用户可用性和科学判断分别记录，限制写清。仅交付文档时只验证文档，不冒充新的产品证据。

<a id="acceptance"></a>
## 18. 验收与当前整改顺序

### 18.1 四类判断分别成立

| 判断 | 需要的证据 | 不能替代它的证据 |
| --- | --- | --- |
| 功能与行为正确 | 实际 owner 契约、真实对象和浏览器操作，包含失败与恢复 | 理想状态的设计图。 |
| 视觉与细节合格 | 对完整状态的人工审查：层级、对齐、密度、可读性、组件一致性、文案与反馈 | CSS token 命中率、无溢出断言、截图已生成。 |
| 目标用户可用 | 研究者在说明范围内完成任务的观察；记录错误理解、停顿、求助和恢复 | 开发者熟练操作，或一位评审觉得好看。 |
| 科学结果可采纳 | 对应领域检查、方法与研究判断 | 执行完成、图表能打开、Agent 自称正确。 |

可访问性另行记录其测试范围，并贯穿上述界面交付。当前 base-R 闭环保留原有功能证据；**它尚未获得本指导下的视觉验收，也没有研究者可用性结论**。

### 18.2 视觉审查要回答的问题

评审应先指出屏幕的主要内容、主要动作和阅读顺序，再检查实际构图是否支持这三者。需要写出具体观察，例如“比较左侧比右侧多两行工具，首行相差 80 px，无法直接扫读”，而不是“感觉不够高级”。修改后检查问题是否消失，以及是否破坏相邻状态。

以下缺陷阻止相应界面以“设计完成”交付：主要对象或下一步无法辨认；必要内容被裁切或遮挡；常态工具栏无规则换行导致主体跳动；比较制造错误对应或视线持续跨越错位区域；焦点不可见；状态虚报；同一操作的名称和反馈相互矛盾。整体缺乏层级、控件全部同权重和阅读密度明显失衡，也需要明确整改，不能用功能通过关闭问题。

主观细节判断应保留理由和任务情境，可以迭代。没有必要把每个偏好变成禁止合并的像素规则；明确的可见缺陷、事实误导和可用性问题则必须处理。

### 18.3 后续实现顺序

先以 airquality 闭环为一组完整屏幕重做：压缩重复顶栏，建立对象与任务的层级；统一基础排版、控件与选区表达；整理问题和外部 Agent 交接；让新旧结果具备有意义的标签、成对版式和窄屏路径；最后验证断连、冲突、返回及未保存内容。

这组流程形成可复用的导航、对象头部、工具、状态和内容容器后，再覆盖项目入口、文件、Activity、设置及各插件的真实内容与异常状态。每次修改回到实际 owner，并记录缺失能力。后续具体进度与未完成项只在 [Status](STATUS.md) 维护，本文保持为设计依据。
