# Rho 下一版本整体设计

本文件汇总 2026-10-01 的设计讨论，作为下一版本的方向依据。
源码已按核心、官方插件和应用组装拆为本地仓库；能力目标不因源码拆分而自动实现。
当前实现与验证结论见 [Status](STATUS.md)，当前机制见 [Architecture](ARCHITECTURE.md)。
这里区分已经收敛的设计原则、分阶段范围和仍需验证的工程选择，不把目标写成现状。

## 产品目标

Rho 是可操作的科学计算工作区。研究者与外部 Agent 能读取真实文件、连接计算环境、
执行分析、检查对象与产物，并在用户操作、计算和外部修改持续发生时继续工作。

首批服务 R 科研工作。R 是分析引擎，通过普通插件接入；Host 的身份、生命周期、
路由和操作机制不依赖 R。以后可以接入 Python、Julia，但不提前统一所有语言的对象模型。
默认交付完整的 R 工作区，与核心保持通用并不冲突。

下一版本的开发交付单位是无界面的能力：接口、数据、行为和可验证结果。
API、CLI 或 MCP 可以完成一段工作，就能独立验收这项能力。前端作为消费者单独开发，
无需为每项能力先制作面板、调整布局或启动浏览器。

## 开发判据

每项工作先写一个用户动作和可观察的完成条件，再决定是否需要新接口或新结构。
先用现有公开能力尝试完成动作并核对真实结果；已有有效证据可以复用。
失败在哪里，就修哪个 Owner 的最小缺口。未搭好集成环境不等于能力缺失。

成熟通用能力默认复用。自研前必须说明现成方案不能满足的必要需求；通用性、优雅程度和
潜在未来需求不单独构成重构理由。Rho 的新增投入集中于代码、计算会话、结果和研究判断的连接。
以后需要编辑器界面时，文本模型、撤销、搜索、选区等优先由成熟组件承担。

新增状态模型前，说明现有文件、Git、Operation 和已有工具为何不能承担。
外部调用方直接修改磁盘文件，不因此需要编辑器缓冲区、独立文档身份或另一份内容历史。
Git 可承担文件历史，但不自动解决未保存缓冲区和并发覆盖；工具名称也不能证明内存开销、
原子性和文本保真。大小限制需要说明保护的资源、能否配置和超限行为，不机械继承旧常量，
也不承诺无限容量。文件保存细节尽量封装在 Files 内，不以此扩建 Core 或文档平台。

## 核心与所有权

| 层次 | 负责什么 | 边界 |
| --- | --- | --- |
| Host | 项目与调用者身份、权限校验、包与实例生命周期、能力发现和路由、Operation、通用资源访问 | 不解释 R 对象，不规划 Agent 工作，不实现领域业务 |
| 领域插件 | 原生资源、领域状态、前置条件、执行、观察和恢复 | 不绕过 Host 建立另一套受管操作账本 |
| 工作台外壳 | 窗口、布局、焦点、视图托管和通用呈现连接 | 不成为科学能力必须经过的执行入口 |
| 外部 Agent 平台 | 模型、对话、规划、上下文组织、工具循环、任务调度和自身记忆 | 使用已授权的公开能力，不因读取内容获得新权限 |
| 默认工作区组合 | 选择插件、实例、环境和可选视图 | 配置产品体验，不赋予某个包核心特权 |

文件字节、R 内存、文档草稿、环境、远程任务分别有自己的 Owner。
Owner 提供原生身份与状态证据；Host 保存受管操作及其提交记录。
不引入一个试图原子回滚所有系统的全局科学状态或全局版本号。

Query 是有界观察，不为读取而启动、恢复或执行计算。Control 处理已有工作的明确控制。
Operation 处理受管副作用，保留原请求、目标、前置条件和结果。
原生执行与账本提交是两个边界；丢失回执时检查原操作，不能通过重跑猜测结果。
取消请求、确认停止、终态与回滚分别表达。

核心足够简约的判据是：新增科研能力主要修改相应插件；只有确实缺少共同机制时才修改 Host。
通用机制也需要明确范围，不能把所有未来需求提前变成核心框架。

## 仓库与开发入口

采用三个源码仓库、一个日常开发入口。当前本地目录为 Rho-core、Rho-plugins 和 Rho；实际验收范围见 Status。

| 仓库职责 | 内容 | 维护边界 |
| --- | --- | --- |
| 核心 | 通用 Host、Operation、身份与权限、持久化、公开协议与 SDK、通用接入 | 低频更新；声明支持的协议与消费者兼容性；不依赖具体科研插件或工作台页面 |
| 官方插件 | 运行时、资源服务、编辑工具、管理工具及各自的领域契约、方法和视图 | 暂放同一插件仓库；插件可以独立版本化和交付，只使用公共核心接口 |
| 应用组装 | 工作台外壳、启动器、默认场景、示例、组件选择、产品集成与交付 | 作为日常开发入口；精确锁定核心和插件产物，不拥有另一套科学操作流程 |

核心的稳定指普通功能开发不必修改核心，以及声明范围内的接口兼容；不承诺永不修复或升级。
`rho-host` 仍负责运行时统一接线，应用组装负责选择交付组合。通用 HTTP/CLI/MCP 接入与
应用页面、示例的归属按职责拆开，不能机械搬动整个现有目录。公共领域契约仍归插件。

本地允许三个相邻 checkout，由应用入口统一查看状态、选择本地源码覆盖、构建指定组件和
启动开发版。发布组合记录精确源码提交、构建产物身份与摘要，不跟随各仓库的浮动分支。
本地覆盖必须可见，不能混入锁定组合。每份源码只有一个维护源，不长期双向同步。
无需先引入第四个管理仓库、插件市场或每插件一仓库。

正式发行采用独立的职责边界：Rho 负责应用源码、组件选择和组装；未来的 Rho-releases
负责把已验收的固定组合提升为正式版本，并承载签名、公证、发布产物和安装／更新入口。
产品版本独立于各组件版本。构建和验收不持有签名或发布凭据；发布阶段验证选定产物，
不重新构建，并记录签名前后的摘要。这个发布仓库不是日常开发协调仓库，目前也未创建。
到首次正式签名发行时再实施，范围和验收见 [Release](RELEASE.md#future-official-release-boundary)。

拆仓阶段已验证的独立构建与选定组合见 Status，不作为每次迭代的重复任务。
当前破坏性升级按单个仓库的新职责和公开契约交付，在该仓库构建、测试，并用最小调用方验证。
其他仓库暂时不兼容可以接受，不要求全面盘点旧消费者，不增加兼容层，也不为收尾同步迁移
插件、应用、SDK 快照或锁文件。旧实现只用于回答具体需求问题，不决定新设计。

跨仓库迁移和完整组合运行到明确的集成任务再做。届时显式选择组件与 SDK 版本，验证所选流程；
日常插件更新复用适用的核心产物，应用页面更新不重编译核心。单仓契约通过不代表组合已可运行。

拆分不承担旧布局、旧构建入口或整套历史测试的兼容负担。现有测试按其能证明的行为重新
筛选：保留有意义的 Owner/协议用例，改写仍必要但绑定旧布局的用例，删除只约束旧结构的
检查。旧套件全绿不作为拆分门槛，具体完成条件见 [Development](DEVELOPMENT.md#repository-separation-acceptance)。
组件组合回退不代表用户数据、原生副作用或 R 内存也能回滚。

## 插件类别与重要性

类别描述职责；重要性描述实施顺序和稳定性责任；权限由实际授权决定。
运行时接触状态深，Agent 调用范围可能广，编辑工具对内容版本要求细，不能压成一个权限等级。

| 类别 | 典型能力 | 主要责任 |
| --- | --- | --- |
| 运行时 | R、未来的 Python 和 Julia | 会话、队列、内存对象、输入、中断与恢复 |
| 资源服务 | Files、Git、Environment、Remote | 文件、依赖、版本与外部资源的真实操作和观察 |
| 编辑与研究工具 | 文档编辑、注释、研究记录 | 内容版本、草稿、保存、引用与冲突 |
| 交互视图 | Console、Objects、Plots、Viewer | 呈现已有资源、接受输入并调用相同接口 |
| 平台管理工具 | Manager、Plugin Studio | 插件源码、构建、预览、实例和工作区组合 |
| Agent 功能扩展 | 可选的专门 Agent 活动 | 自己承担其产品功能，不成为其他插件的必要依赖 |

一个包可以组合后端、方法资料和视图，也可以完全没有前端。
不为每个类别创建一套宿主或独立权限系统。类别可帮助发现和组织，执行由实际契约约束。

每个插件需要说清：拥有什么状态，依赖谁，能产生什么影响，存活多久，停止或替换时如何处理。
作用范围包括经其他插件产生的影响；没有后端的管理视图也可能调用有副作用的管理能力。

运行时不依赖 Console 存在，文件能力不依赖 Files 面板，文档保存不依赖模拟点击。
关闭视图不自动停止会话；释放后端也不能把未确认的工作当作已结束。

## 插件交付内容

| 内容 | 用途 |
| --- | --- |
| 能力及领域 Schema | 参数、结果、前置条件、副作用和错误语义 |
| 上下文接口 | 发现、搜索、读取、来源追查及失效信息 |
| Skills 和参考资料 | 适用场景、方法、示例、验证步骤和协作方式 |
| 偏好与配置 | 用户或项目对展示、报告、命名、输出位置等的要求 |
| 可选视图 | 人使用上述能力的一种交互方式 |
| 验证材料 | 可重复数据样例、接口用例、相关真实运行检查 |

方法资料由最了解能力的插件维护，随版本发布。简单插件可以只有清楚的工具描述。
先暴露简短目录和适用条件，需要时读取具体 Skill 和资源，不把所有说明塞进每次模型上下文。

能力和上下文经统一 MCP 或公开 Host 接口接入，不为每个插件新起一个 MCP 服务。
Skills 读取保留明确的包或项目来源、版本、授权和路径包含关系。
现有通用资源读取可作为基础；具体发现与接入方式仍需验证，不能假定完整 Skill 服务已经存在。

方法建议由 Agent 判断采用；用户当前要求覆盖相应默认，偏好应有来源和作用范围。
必须满足的会话、文档版本、文件范围等条件由执行端校验。
方法文本、配置内容和模型输出都不能扩大授权，也不引入第二次 Rho 审批。

## 动态上下文

Agent 工作的对象是一个持续变化的计算现场。上下文是一份有来源和有效性边界的观察，
包括文件、未保存草稿、选择范围、运行时、变量、队列、等待输入、输出及它们的已知关系。

观察应保留：

- 项目、资源、Provider 和必要的原生会话身份；
- 内容版本、摘要或 Owner 提供的观察引用；
- 时间、完整性、忙碌、缓存和不可用状态；
- 能够证实的来源关系，以及继续读取的入口；
- 失效条件或要求重新核对的信息。

“挖掘上下文”是沿可证实关系继续追查：从图找到生成它的运行，再找到实际执行内容与输入引用。
未知关系保持未知；文件名相似、时间接近或模型推断不能直接升级为来源事实。

工作闭环为：发现资源和方法 → 读取观察 → 理解并选择行动 → Owner 校验执行 → 核对结果与变化。
用户、外部程序和 Agent 自己都可能改变现场。已知因果关系关联原操作；来源不明时明确保留未知。

通知只提示重新检查，不能替代执行前的版本校验。多个 Owner 的先后读取不构成原子快照。
对任意 R 执行，无法精确知道影响时，可以保守地使相关会话观察失效，再按需读取。
轮询与关键节点重新观察可以先用；不把全局事件总线列为前置工程。

Agent 发出操作不代表操作已经成功。自己的动作也要读取实际结果；相关变更可以合并处理，
不能每条事件都触发一次模型行动。任务保留当时使用的上下文，新观察作为后续证据加入，
不静默改写原输入。断线后发现信息缺口，需要重新观察，而不是假定期间没有变化。

## 外部 Agent

目标架构不要求 Rho 内置模型引擎、聊天产品或 Agent 调度系统。
具备相应工具和上下文能力的外部 Agent 可以使用同一接口参与工作。
Agent 更换或断开后，Rho 中的原操作、文件、计算资源和产物仍然可以独立检查。

“某个插件的 Agent”主要是一项有明确对象和范围的任务：绑定插件版本、相关实例或源码分支，
带上用户目标、方法、偏好、上下文入口和已有授权。长期知识放在文档、问题记录、偏好和成果中，
不依赖一个长期存活的模型进程。

| 工作 | 对象 | 结果 |
| --- | --- | --- |
| 内容解读 | 当前资源、观察和来源 | 解释、注释、证据引用 |
| 协助操作 | 当前状态和授权能力 | 原 Owner 的操作与真实结果 |
| 调整体验 | 当前实例的配置和用户偏好 | 可确认的配置变化 |
| 修改插件 | 确切源码、问题证据和设计约定 | 新版本、检查和可选预览 |

内容解读不自动授权修改插件源码。修改源代码、构建、预览和应用新版本分别有明确结果。
UI 优化可以由外部 Agent 完成；需要视觉判断时，给它相应界面证据和验证工具。

当前代码仍包含普通 Agent 包、Rig 引擎，以及绑定 `org.rho.agent` 的 Studio 入口。
已决定退出内置 Agent；依赖解除、入口调整和代码退出按所属仓库分别实施，不要求同时修好
其他仓库的消费者。不迁移到 TypeScript，不建设替代聊天产品，不迁移或清理旧任务数据。
保留外部调用者身份、公开接入与受管操作；这不要求保留内置模型引擎。

## 前端分离

无界面插件交付接口、数据和行为。调用方可以直接指定项目、资源、文档版本、范围和会话，
不需要先打开窗口、创建面板或合成浏览器事件。当前带窗口的契约要通过明确的新边界调整，
不能仅删掉身份字段而失去调用者、资源或版本校验。

直接文件修改先使用 Files 的读取、补丁和校验能力，不预设 editor.open/read/edit/save。
未保存缓冲区是否需要独立文档接口，由后续真实编辑器用例决定。光标、滚动、焦点、布局和
快捷键属于前端。选择范围需要参与领域操作时，作为明确的资源与版本参数传入。

| 开发线 | 独立交付 | 验证 |
| --- | --- | --- |
| 无界面能力 | 契约、数据、状态变化、操作和恢复 | 接口用例及必要的真实 Owner、R、Host、MCP 流程 |
| 前端 | 内容呈现、输入、反馈、导航和布局 | 代表性数据、组件检查、键盘和视觉检查 |
| 集成 | 前端使用公开能力完成指定工作 | 最小真实接线和完整使用流程 |

前端以固定样例和接口替身快速开发，使用同一份真实契约。替身不能替代权限、执行与恢复验证。
能力验收不证明 UI 好用；UI 验收也不证明科研结果正确。破坏性契约变更先验收所属仓库，
已有消费者的调整和验证只在对应迁移或集成任务中进行。

视图可以独立开发和更新，多个前端可以复用同一能力。默认工作台、CLI 和外部 Agent 都是消费者。
首批能力不需要为了验收而同步建设完整前端。未来实际 UI 改动继续遵守
[已批准交互与 Paper 评审边界](RHO-DESIGN.md)。

## 语言和开发成本

| 内容 | 默认选择 |
| --- | --- |
| 稳定 Host、通信、权限、Operation、进程监督 | Rust |
| 已可靠的 R 桥接、原生文件操作 | 保留现有实现 |
| 高频上下文组织、工具适配、偏好应用、交互和呈现 | TypeScript |
| 科研方法、分析、绘图和明确执行的检查 | R 脚本或 R 包 |
| Skills、示例和配置 | Markdown 或配置文件 |

按职责、变化频率和牵动范围选择语言，不为减少 Rust 行数重写稳定实现。
公共通信封套继续使用现有协议；领域 Schema 由插件维护，不为一个领域字段增加核心枚举。
只读 R 观察的安全机制仍属于原生 Owner。方法脚本作为明确的执行内容使用，不能在 Query 中
偷偷 source 最新文件，或者用另一个 R 进程的结果替代当前会话。

TypeScript 后端试点使用同一公开协议。先实现真正需要的查询子集，不声明未实现的写入、
取消或恢复能力。候选是 Objects 上下文整理：读取指定 R Provider 的真实观察，组织结果并
保留其身份和完整性，供界面与外部 Agent 共同使用。它不建立另一份对象数据库。

Node 只选择一种明确的交付方式。开发版本、可执行入口、正式位置和打包必须实际验证，
不能假设用户机器上已有适用 Node。更换语言不改变受信任本机代码的执行边界。

## 更新与计算连续性

日常迭代使用最近的检查，复用仍有效的原生产物；协议、发布和跨边界验证按实际变化安排。
当前命令和显式版本选择以 [Development](DEVELOPMENT.md) 为准；已实现的拆仓入口不代表后续能力已实现。

更新视图、替换插件后端、执行新研究脚本是不同动作：

- 工作台开发资源可以在受支持路径上刷新；这不自动提供普通插件 HMR。
- 已导入产物保持不可变。新内容产生新版本，原任务保留实际使用的内容引用。
- 更新独立 UI 或上下文适配层时，继续绑定原来的 R Provider。
- 替换拥有 R 进程的后端能否保留内存，取决于实际生命周期；不能预先承诺无条件连续。
- 方法与 Skill 更新不静默替换已开始任务采用的版本。

衡量保存到可验证结果的完整耗时，以及 Cargo、打包、Host 重启、R 重启次数。
沿用已有运行证据，不新建性能账本，也不先承诺提速倍数。

## 首批范围与推进顺序

以下是逐步验证的能力方向，不是一期必须建齐的层次，也不构成前后端同时交付要求。

| 第一批 | 最小交付 | 必须能观察的变化 |
| --- | --- | --- |
| 文件 | 搜索、读写、内容版本、冲突与来源 | 外部修改、替换、保存结果 |
| 计算环境与运行时 | 识别并选择已有安装和环境、显式启动及连接 R | 会话身份、忙闲、重启、依赖和实际库路径 |
| 变量对象 | 目录、类型、结构、摘要、分段值 | 执行后的失效、忙碌、会话变化 |
| 交互式 Console 能力 | 代码提交、连续输出、队列、stdin、中断与结果 | 等待、执行、输入请求、取消和终态 |
| 必要编辑与结果资源 | 复用文件编辑、捕获实际执行内容、读取原始图表或文件引用 | 并发修改、实际执行版本和产物关联 |

这里的 Console 指计算会话接口，首批不包含通用操作系统 Shell 产品。
环境首批聚焦已有安装的识别与使用；安装、升级、清理和复杂环境管理分别定范围。
变量状态始终归运行时所有，不创建独立变量真相服务。

先完成下面的一期 Core 契约升级，再在各自所属仓库选择真实文件修改、计算和恢复等用例。
Agent 接口与方法资料从开始一起设计。可选前端在能力可用后独立接入。
后续再扩展研究记录、帮助与结果比较，以及其他语言、远程计算和复杂协作。

开发提速保留以下候选方向，仅在实际用例暴露相应瓶颈时选择，不作为预先建齐的路线：

| 包 | 目标 | 完成条件 |
| --- | --- | --- |
| A | 接顺局部检查和产物复用 | 选定能力或内容修改能快速验证，知道使用的是哪个版本；UI 路径只覆盖实际需要的现有视图改动 |
| B | 一个真实 TS 查询后端 | 经普通 Host 调用，Host 与 R 后端字节不变，启动与打包可复现 |
| C | 动态计算现场 | 更新适配逻辑仍保有原会话；用户或 Agent 改变对象后能重新观察并继续 |

A、B、C 服务首批能力，不以完成前端为门槛，也不触发整体语言迁移、内置 Agent 重写、
新工作流 DSL 或插件市场建设。仓库拆分按上面的独立范围推进，不以完成 A、B、C 为前提，
也不把这些新能力混入拆分验收。

## 一期：核心升级，无界面公共契约与领域解耦

### 目标与边界

实现和验收只在 Rho-core。目标动作是：外部调用方在没有浏览器、窗口和内置 Agent 的情况下，
发现普通测试插件，读取其上下文，调用一项受管操作，再通过原 Operation 检查结果。
先复用 Core 已有测试插件与公开入口跑基线，已经成立的机制不重新实现。

按破坏性升级直接切换受影响契约，不做旧接口适配或数据迁移，不主动删除用户数据。
插件、应用暂时不兼容可以接受。本期不进入这些仓库盘点或修复消费者，不要求完整 Rho 可用。

### 实施内容

- **上下文契约去窗口化。** 从 ContextSearch、ContextReference 移除强制 window 字段；
  保留 Provider、contribution、Owner 定义的 selector 及版本证据。项目、调用者和授权仍由
  可信调用上下文确定，引用不授予权限。真实视图的限制继续由 Host 持有的 ViewCallScope
  及反向调用继承，不能通过省略 window 消除。不得顺带改造 documents.*、草稿地址或存储。
- **去掉默认授权中的领域清单。** local_context 只保留 Core 通用能力所需的默认 scope，
  移除写死的 R、环境、进程、远程计算等领域授权。新增可重复的启动参数 --grant-scope，
  由可信启动端显式加入领域 scope；本地 CLI、stdio MCP 和 Workbench 的 HTTP/MCP 使用
  同一配置来源。连接已有 Host 时不能通过该参数扩权。插件声明和请求正文不能自授权限；
  不建设新的权限产品或审批流程。
- **保持外部 Agent 接入通用。** 保留 CallerKind::Agent、MCP、委托调用及按调用者隔离的
  Operation。现有 agent-connection 接口描述外部 MCP 连接，继续保留，不因名称删除。
  Core 已不依赖内置 Agent/Rig 实现；本期验证该边界，不把删除插件仓库的 Agent 包列为任务。
- **只更新 Core 自己的交付。** 更新受影响的 Rust 类型、Schema、生成 SDK 和公开示例；
  通用请求封套及 Operation 流程沿用现有机制。不提供旧 window 形状的兼容入口。
  Core 内部消费者随契约修改；需要官方 Agent/R 产物的历史集成测试不作为本期门槛。
  更新 Core README/AGENTS 的独立验收说明；仅检查本仓库生成与导出，不刷新消费仓库。

### 推进顺序与验收

1. 用已有 Core 测试插件跑通最小公开调用基线，固定身份、授权和 Operation 的预期结果。
2. 修改上下文契约与启动授权入口，只补该流程暴露的 Core 缺口；同步本仓库类型和测试。
3. 经 CLI session 和 MCP 完成无窗口上下文读取、调用和原操作查询；启动授权接线覆盖
   Workbench HTTP 的定向测试，不启动浏览器或应用资产。
4. 覆盖缺失 scope、插件企图扩大授权、跨项目/调用者、错误 Provider，以及受限视图的
   反向调用不能脱离原约束。复用相关的重复请求、断线观察和提交不确定性测试，确认不重放。
5. 在 Rho-core 串行执行受影响 crate 的定向测试、cargo build --locked、
   node scripts/check-boundaries.mjs，以及公共契约生成/导出检查。使用临时项目和 catalog，
   不依赖兄弟源码、官方科学插件、R 安装或用户运行中的 Host。

### 完成标准

Core 的通用上下文接口无需窗口，领域授权由启动端显式提供，最小外部调用流程和上述边界
检查通过；本仓库可以独立构建，生成契约与实现一致。提交 Core 变更并记录实际执行证据。

本期不交付 Editor 后端、文档模型、文件保存实现、Git 封装或大小限制重构，不删除插件仓库的
内置 Agent 产品，也不包含应用 UI、SDK 消费端同步、rho.lock.json 更新、三仓组合或正式发行。
测试插件只证明 Core 行为；真实 Files 修改和科学计算留到对应仓库或明确的集成任务验收。
