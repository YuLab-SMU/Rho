# Rho Core 职责收缩修复计划

本计划解决 Core 同时承载执行内核、插件平台、工作台状态和插件开发工具造成的职责集中。
目标是让外部调用方通过 CLI 或 MCP 完成普通插件调用时，只需要通用身份、授权、路由、
资源和 Operation 机制。默认工作台和插件开发工具按各自需要接入这些机制。

这是待实施计划。先交付 Rho-core 的新边界，再单独选择消费端迁移和应用组合任务。
每次实施只选一个下面列出的切片，不把整个计划变成单次提交的完成门槛。
原则与仓库边界沿用 [Next Version](NEXT-VERSION.md)、[Architecture](ARCHITECTURE.md)
和 [Development](DEVELOPMENT.md)。实际状态与执行证据只更新 [Status](STATUS.md)。

## 问题基线

2026-10-02 的静态统计针对 Git 跟踪的文本文件，排除构建产物，计入注释和空行。
测试文件与源码末尾的测试模块拆开计算；非测试 Rust 还包含少量示例和契约导出程序。

| 内容 | 约计物理行数 | 对本计划的意义 |
| --- | ---: | --- |
| 非测试 Rust | 30,800 | 主要观察职责、依赖和状态数量 |
| 测试和夹具 | 31,000 | 按能证明的行为保留，不作为删代码目标 |
| 生成的 SDK 类型和 Schema | 9,200 | 随真实公共契约收缩重新生成 |
| 手写 SDK、文档和配置等 | 6,200 | 由其实际职责决定归属 |

Core 仓库中的 `crates/plugins` 有约 13,200 行非测试代码，占非测试 Rust 的 43%。
其中视图、窗口、场景和草稿直接实现约 3,600 行，源码开发与构建约 860 行；
这些数字不含相关协议、集中式 handler、SDK 和测试，不能当作可直接删除的数量。
Operation 与 SQLite 适配部分合计约 5,400 行，承担原始操作和提交边界。

具体问题是 [PluginService](../../Rho-core/crates/plugins/src/service.rs)
统一组合包、实例、视图、草稿、构建与资源；
[service_handlers.rs](../../Rho-core/crates/plugins/src/service_handlers.rs)
用多组字符串分派维护 45 个能力；普通 Host 还默认注册
[测试项目管理](../../Rho-core/crates/host/src/plugin_tests.rs)。
这说明源码仓库已拆开，但运行平台的产品职责仍集中在 Core。

## 目标边界

| 职责 | 目标所有权 | Core 保留的必要责任 |
| --- | --- | --- |
| 项目、调用者、授权、发现与路由 | Core | 可信身份、scope、Provider 和资源包含关系 |
| Operation、日志、取消与提交恢复 | Core | 原请求、幂等、历史结果、提交不确定性和禁止重放 |
| 不可变包与实例 | Core | 包身份、清单和摘要校验、受授权的实例生命周期 |
| 通用资源访问与原生进程监督 | Core | 有界传输、资源身份、进程状态及确认清理 |
| 源码编辑、分支和构建工作流 | 开发工具所属 Owner | 对其真正需要的受管动作复用 Operation |
| 预览和开发测试编排 | 开发工具所属 Owner | 普通项目与实例的公共生命周期接口 |
| 布局、焦点、场景和可视组件模型 | 工作台外壳或明确的产品 Owner | 视图连接的认证、授权与安全托管边界 |
| 未保存草稿、内容历史和冲突处理 | 编辑工具所属 Owner | 受管保存动作的记录及必要的通用资源访问 |

平台管理工具的目标位置沿用官方插件仓库的职责；工作台外壳仍属于应用仓库。
消费端任务再确定具体实现。应用仓库保持现有无 Cargo workspace 的构建边界。
不因移出 Core 而新建仓库，也不预先建设一个新的服务注册、配置或文档框架。

包内保留源码用于不可变身份、来源与只读查看，和管理可编辑源码分支是两个需求。
运行时实例的权限与生命周期仍由 Core 协调；工作台 Owner 接管布局不意味着接管这些权限。
未保存草稿需要自己的内容和并发检查，不能仅凭 Git 存在就取消这些责任。

## 实施顺序

| 顺序 | 独立切片 | 直接结果 | 所属仓库 |
| --- | --- | --- | --- |
| 1 | 退出 Core 内的测试项目编排 | 普通 Host 通过公开入口运行，开发测试由外部调用方创建和管理 | Rho-core |
| 2 | 退出源码编辑与构建工作流 | Core 接收已有不可变产物，开发工具使用文件、Git 和构建工具 | Rho-core |
| 3 | 退出产品布局、场景和可视模型 | 无界面调用不承担工作台产品状态 | Rho-core |
| 4 | 收缩草稿服务的 Core 责任 | 内容模型由编辑工具拥有，Core 只承担被证明必要的共同机制 | Rho-core |
| 5 | 整理剩余能力与公共契约 | handler、校验和 SDK 与收缩后的职责一致 | Rho-core |
| 后续 | 迁移选定消费者并验证组合 | 工作台或开发工具接入已提交的新契约 | 明确选定的插件或应用 Owner |

第 3、4 项分别实施，保留各自所需的授权与已确认数据边界。第 5 项随前面已完成的切片
局部整理，不等待全部退出完成，也不提前做全库重构。每个切片的提交都可以独立验收。

## 切片 1 退出 Core 内的测试项目编排

用户动作：开发者从外部测试调用方，在临时项目和 catalog 中通过普通 Core 入口激活一个
协议测试插件，调用并检查结果，然后显式结束该测试 Host。

先用现有无界面测试流程建立基线。保留测试脚本需要的临时目录、进程等待与公共调用，
由测试调用方承担编排。随后去除生产 Host 的 `plugins.test_*` 能力、子 Host 管理、
测试项目专用持久化与专用契约；通用 Host 和实例的状态、授权与清理语义继续成立。

完成条件：

- 普通 Host 的生产代码、能力目录和新建存储中不再包含测试项目编排。
- 外部调用方通过 CLI session 和 MCP 完成查询、受管操作、原操作查询和显式退出。
- 重复请求不重放；退出等待与未确认清理分别表达，失去观察不等于执行停止。
- 测试调用方只使用公共契约，不导入科学插件或另一套私有 Host 调度流程。

这是推荐的第一个实施任务。其职责已明确，而且能用现有 Core 测试插件验收。
不增加一套仅将旧管理逻辑藏在开关后的开发模式。

## 切片 2 退出源码编辑与构建工作流

用户动作：开发者用现有文件、Git 和构建工具产生一个明确的插件产物，Core 校验其
不可变身份并通过当前授权路径接入它。检查或接入产物不会重新执行构建命令。

先列出该动作实际需要的包读取、传入与实例能力。保留必要的源码和产物身份、清单、摘要、
包含关系与只读查看；退出 Core 自己的可编辑分支、源码检查点、分支推进、构建队列和
构建目录生命周期。`plugins.preview` 与相关开发预览模型在本切片中确认其产品职责，
可独立退出；普通视图的安全托管不随开发预览一并删除。

不可变包的只读比较是否保留，由实际查看用例决定。源码历史、执行记录和包身份各自有
不同用途，不能为了减少行数把它们并成一个版本字段。开发构建需要记录受管副作用时，
由其 Owner 使用现有 Operation，而不是新增执行账本。

完成条件：Core 不执行插件构建命令，也不管理可编辑源码 head；最小测试插件的不可变
产物能够按声明的公开路径校验和接入；旧构建 Operation 仍可读取，不因能力退出而重跑。
若产物输入路径本身暴露 Core 缺口，只修复这条路径的最小问题。

## 切片 3 退出产品布局 场景与可视模型

用户动作：外部调用方不创建窗口、不选择场景，也能发现一个 Provider、读取观察并执行
受授权操作。工作台随后可以选择自己的布局和呈现数据。

退出 Core 中产品布局、窗口场景历史、场景应用和具体可视组件树的解释。保留连接身份、
受限视图授权、资源访问与断线语义；托管 HTML、JS 和资源时仍做实际边界校验。
不把 Button、Tabs 或工作台布局版本作为领域能力的前置条件。

完成条件：无界面流程与窗口状态无关；Core 不初始化布局或场景历史；真实视图调用及
反向委托不能借字段删除逃脱原授权范围。关闭连接、关闭视图和释放原生实例仍分别表达。
前端体验与旧消费者接入在后续任务验收。

## 切片 4 收缩草稿服务责任

用户动作：编辑工具在保存前检查自己的草稿版本和磁盘基线；遇到外部变化时保留草稿，
通过比较、另存或新的明确基线继续工作。领域实现和真实文件结果由对应 Owner 验收。

本切片的 Core 任务先用最小调用方核对：内容传输、版本检查和原 Operation 记录中，
哪些责任确实需要共同机制。保留被真实调用证明必要的最小资源边界，退出通用编辑器
内容模型、窗口草稿地址、上传租约与编辑历史的产品语义。普通文件编辑不要求创建草稿。

不能将现有草稿数据库仅改名为一个新 Core 文档服务。若选定 Owner 尚无必要能力，
记录其消费端缺口，并将其实施列为独立 Owner 任务。已确认的草稿字节和原保存记录
需要保留；移除接口不得触发清理或把缺失确认当成保存成功。

完成条件：Core-only 调用不要求编辑器身份；原保存记录与保留内容不被改写或删除；
受管操作和资源访问的项目、调用者及版本边界仍可验证。真实草稿合并、磁盘保存和 UI
恢复只由后续领域与消费端验收建立，不能由 Core 夹具冒充这些结果。

## 切片 5 整理剩余实现与契约

在已退出职责后，按剩余 Owner 拆小能力实现，使注册、参数规范化、绑定和执行的维护点
靠近。优先复用现有 handler trait，不创建新的能力 DSL、宏框架或全局状态服务。

逐项说明验证的边界：调用方授权、Core 公开输入、固定 Provider、Owner 回报和最终提交。
保留跨信任边界的检查；同一不可变契约的重复编译可在其实际 Owner 内复用验证器。
合并校验前用行为测试证明它没有跳过原来的授权、身份、Schema 或提交约束。

公共 SDK 只导出剩余 Core 契约。产品模型归实际 Owner，以有界引用或 Owner 定义数据
使用公共通信封套。Core 自己的 Rust 类型、Schema、生成 SDK 和示例在同一切片更新；
移除类型也同步更新导出清单，消费仓库的副本留到明确接入任务刷新。

## 验收与收尾规则

每个切片先运行现有公共流程，确认要修复或退出的实际责任。完成后核对源码、依赖、
能力目录及新建存储；同时记录测试与生成文件，避免把移动测试或格式变化算成核心简化。
不设任意减行比例，也不承诺尚未测量的启动速度或内存改善。

相关行为检查保留：项目和调用者隔离、启动授权、固定 Provider、原始请求与幂等、取消
确认、断线后的原记录读取、提交恢复、禁止重放，以及查询时间、缓存和完整性。
`Uncertain` 结束原操作生命周期；后续观察仍可增加认识，但匹配状态不能自动证明归因。
独立动作使用自己的授权与前置条件，不以整个项目证据完美为开始工作的条件。

在 Rho-core 串行运行受影响 crate 的定向测试、`cargo build --locked`、
`node scripts/check-boundaries.mjs`，并检查受影响的公共契约生成和导出。
测试使用临时项目与 catalog；不重启用户 Host 或 R 会话。保留失败和未执行的证据，
沿用仍有效的通过结果，不把旧整产品套件作为收尾门槛。

退出旧能力不等于维护兼容层或迁移旧数据。旧内容保持原样，不自动清理；涉及不兼容存储
时先声明新边界，并用新建存储验收，禁止为继续打开旧 catalog 而暗中修改它。
历史 Operation 按其原始能力身份保持可读，Owner 缺失与当前状态分别表达。

检查 diff 与仓库状态后，在实际 Owner 提交一批完整改动。源码推送沿用已授权的发布范围；
构建、SDK 消费端刷新、锁更新、应用组装及正式发行分别记录其真实结果。
计划实施期间只在行为、验证结论或下一步焦点变化时更新 Status，不另建完成事项流水账。

## 后续消费端接入

Core 切片通过后，再明确选择开发工具、编辑工具或工作台的一条用户流程及其 Owner。
消费端在自己的仓库读写自有状态，复用 Core 的公共身份、资源和受管执行。
显式选择已提交 Core 版本并刷新必要的 SDK，构建受影响组件后再锁定所选组合。

每次集成只验收已选定的真实路径。工作台布局迁移需要代表性宽度和既定交互评审；
编辑工具迁移需要真实草稿与并发文件检查；开发工具迁移需要真实产物和原操作结果。
这些结果不能由 Core 的单仓构建或无界面夹具替代。
