# Rho 产品定义与 UI/UX 设计任务书

- 日期：2026-10-16
- 版本：0.1
- 状态：交接初稿；已明确目标与待讨论事项分开记录
- 读者：产品负责人、UI/UX 设计团队、Agent 与应用工程团队

## 1. 这份任务书的用途

本次设计从场景、用户、Agent、启动、工程、结果、展示和交互重新定义产品。
本文件可独立阅读，不要求设计团队阅读旧画板或沿用既有页面、导航、面板与视觉方案。
既有设计规则不作为本次概念设计的前提；实现条件由工程团队另行提供并讨论。

本文使用三类表述：

- **已明确目标**：本轮需求明确要求保留的方向，是设计评审的依据。
- **工作假设**：为了让团队开始探索而提供的样本，仍需验证。
- **待讨论问题**：影响产品结构的未决选择，不能在原型中默认为已经确定。

## 2. 已明确的产品目标

1. **让人与 Agent 围绕真实工作持续协作。** 用户提出目标，Agent 开展工作，
   用户能查看、理解、介入和继续推进；设计需要覆盖这些动作之间的联系。
2. **让大量 Agent 工作仍然可理解、可介入。** 用户能够找到重要进展、关键结果、
   依据和需要自己处理的事情，不必逐条阅读全部输出。
3. **形成可以实际操作的交互。** 每个重要入口都应有明确的作用对象、操作反馈和
   继续路径。页面必须经得起“用户下一步做什么、操作后哪里发生变化”的检验。
4. **把可复用的系统能力作为产品基础。** 插件承载可复用能力；分析流程、研究问题
   和具体数据属于项目内容。单个分析案例不应成为产品的信息架构。
5. **从多个维度共同确定体验。** 启动、工程、Agent 工作、结果展示和人的直接操作
   需要连成一段工作，不能分别设计成互不相接的功能清单。
6. **为专业 UI/UX 团队留下设计空间。** 本任务书规定问题与体验目标，页面数量、
   导航方式、布局、控件和视觉语言由设计探索确定。

可供探索的产品定义是：**Rho 是一个人与 Agent 共同工作的空间，让用户从目标进入，
在真实材料和结果上持续理解、操作与推进。** 这句话作为方向，不预先决定产品形态。

## 3. 用户与工作场景：用于探索的工作假设

### 3.1 初始用户假设

优先以开展科研或数据分析的人为样本。他们理解自己的问题，但编程熟练程度不同；
有人希望委托 Agent 完成大部分工作，也有人需要频繁进入代码和数据。
首版核心用户及其任务频率仍待确认。

设计应允许同一个人在不同阶段切换工作方式：委托、观察、核对、亲自修改、继续委托。
不要仅根据“新手／专家”身份固定其可用操作。

### 3.2 主场景样本

用户带着数据、已有文件或脚本，想回答一个具体问题：

1. 进入新工程或已有工程，找到相关材料，表达目标和限制。
2. Agent 理解上下文，提出或选择方法，开展工作；用户能够知道工作的对象与进展。
3. 产生第一批结果。用户找到主要发现，查看图表、数据和必要依据。
4. 用户发现异常，选择相关对象并追问，或直接修改材料、参数或代码。
5. Agent 接续处理，产生回应、实际修改或新的结果，并与此前问题关联。
6. 用户核对前后变化，保留判断，继续分析或导出成果。

具体样本可以使用条件比较，也可以使用普通数据处理任务。它是检验通用能力的内容，
不是要求产品围绕某种算法、数据类型或固定步骤组织。

### 3.3 必须一起考虑的场景分支

| 场景 | 用户希望完成什么 | 设计需要回答的问题 |
| --- | --- | --- |
| 首次进入 | 理解用途并开始一件真实工作 | 从哪里开始？需要准备什么？ |
| 已有工程 | 找到材料、近期结果和未完成工作 | 我上次做到哪里？现在有什么变化？ |
| 只查看结果 | 阅读、核对或导出已有内容 | 如何查看而不意外触发新的工作？ |
| 从已有代码进入 | 修改、运行或解释其中一部分 | Agent 和用户如何继续同一份内容？ |
| 工作进行中 | 查看已有输出，同时开展其他操作 | 哪些内容可用？哪些仍在变化？ |
| 反馈后继续 | 知道反馈是否被取用、工作如何回应 | 我的反馈改变了什么？从哪里核对？ |
| 失败、断连或离开后返回 | 保留已得内容并继续 | 还剩什么？哪些状态不确定？下一步是什么？ |

## 4. 人、Agent 与产品的职责

以下是设计所需的职责边界。具体入口、自动化程度及首版支持范围仍需讨论。

| 参与者 | 核心职责 | 需要被支持的行为 |
| --- | --- | --- |
| 用户 | 提出目标、约束和判断；决定重要取舍 | 委托工作、查看依据、选择对象、提出反馈、直接修改、比较结果、决定下一步 |
| Agent | 理解任务、使用工具、处理材料、产生工作成果并解释 | 引用实际上下文，开展具体工作，承接人的修改与反馈，说明依据及仍未解决的部分 |
| Rho | 连接人、Agent 与工作对象，维持可理解的连续性 | 呈现可观察的工作和产物，保持上下文关联，支持直接操作、保存、找回与异常续接 |

Agent 的解释应当能回到相关材料、动作和结果。产品不能仅根据一句回复，
就把“已修改”“已执行”或“已验证”表现为已经发生的事实。

用户的直接修改与 Agent 的修改需要彼此可见，并有适用的比较、撤销与冲突处理。
界面应支持明确的授权边界；不能把每一次观察、反馈或继续操作都设计成审批。
授权的粒度和实际执行入口由产品与工程共同确定。

## 5. 各维度需要解决的体验问题

### 5.1 启动与进入工作

首次使用、打开已有工程和返回上次工作需要不同的起点。设计团队应探索安装、连接
Agent、选择工程与准备所需工具之间的合理顺序，使用户尽快开始真实任务。

展示配置或准备要求时，需要说明它与当前任务的关系、完成后能做什么、失败后如何继续。
Agent 尚未连接时，已有材料和结果能否查看，属于需要明确的产品选择。

### 5.2 工程与持续上下文

工作假设：工程承载一段可以持续进行的协作，包括输入材料、目标、代码、工作记录、
结果、讨论与未完成事项。工程与文件夹、会话、任务之间的关系仍待定义。

用户需要能够知道：自己在哪个工程、操作哪个对象、哪些修改已保存，以及离开后如何找回。
文件组织、搜索和内容关联应帮助用户定位工作；内部标识不应成为日常操作的必备知识。

### 5.3 结果与版本

结果可以是表格、图形、图片、代码、文档、模型或一组产物。设计需要支持打开、检查、
关联依据、继续使用和导出，并说明结果的范围与缺失部分。

设计时需要区分这些事实：Agent 已回复、程序已结束、产物已生成、检查已通过、
结论得到何种支持。区别应在影响理解或操作的位置出现。

新结果出现时，用户应理解发生了什么变化，能够找到旧结果、相关说明及讨论。
是否自动采用新版本、何时提示、如何比较，是待讨论的更新策略；不能静默把旧注释
或旧检查套用到不同内容上。

### 5.4 展示与注意力

展示应帮助用户找到当前目标、重要进展、关键结果、待处理事项与继续入口。
信息层级和呈现形式应由这些目的决定。

摘要、图表、来源、代码和过程记录需要能相互到达；用户可以按需要逐步深入。
切换表达方式时，应保留所关注的对象和工作上下文。

动态图解、动画说明和自动生成的演示属于候选表达方式。是否需要、服务哪个任务，
以及首版是否包含，都需要验证；不作为本次设计的默认核心。

### 5.5 自然语言与直接操作

自然语言和直接操作应能作用于同一份内容。用户可以先让 Agent 工作，再亲自编辑；
也可以先选择对象，再让 Agent 处理。上下文传递要让用户知道 Agent 实际获得了什么。

对话的位置、外部 Agent 客户端的使用方式、操作入口与内容呈现方式均开放探索。
设计需要检验上下文切换成本及往返路径，不预设聊天是所有操作的唯一入口。

## 6. 关键交互要求

下表描述动作与可观察反馈的关系，不规定控件或布局。

| 用户或系统触发 | 必须能够理解的反馈 | 继续工作的路径 |
| --- | --- | --- |
| 用户表达目标或追加限制 | 目标指向哪个工程和材料；Agent 是否接住任务；是否有待澄清内容 | 补充信息、调整目标或跟随工作进展 |
| Agent 开始工作或产生输出 | 正在处理的对象、已观察到的进展和已可用内容 | 查看结果、继续其他操作或按支持范围停止工作 |
| 用户选择点、行、区域或代码 | 选中了什么；相关视图如何对应；传递给 Agent 的上下文是什么 | 查看关联内容、追问或操作该对象 |
| 用户留下反馈 | 反馈附着在哪份内容；是否已提供给 Agent；后续是否存在关联工作与回应 | 继续等待、补充说明、打开回应或核对修改 |
| 用户或 Agent 修改内容 | 修改了什么、由谁修改、是否保存、是否影响已有结果 | 比较、继续编辑、撤销或处理冲突 |
| 新结果或新版本出现 | 新旧内容的关系、当前查看的版本、旧说明与检查的适用范围 | 查看新版、比较变化或继续查看当前版本 |
| 出现失败或未知状态 | 原因或已知范围、保留的材料与输出、仍不能确认的部分 | 检查原工作、修复条件、查看已有输出或明确发起新工作 |
| 用户关闭、重开或重新连接 | 已恢复什么、哪些内容仍未恢复、工作是否仍在继续 | 回到原位置或处理实际缺失内容 |

反馈闭环尤其需要分清：笔记已保存、上下文已可用、Agent 实际取用、观察到后续工作、
存在明确关联的回应。它们是不同阶段，界面不必常驻展示完整状态链，但不能用一个
笼统的“已发送”掩盖尚未发生的步骤。后续关联应有实际依据。

选择与注释需要指向明确对象。若内容版本改变、原对象不可用或无法确认对应关系，
应保留原反馈及引用并给出继续方式，避免把反馈悄悄移到别的内容。

重连、重开与查看应保持工作身份和已得输出的连续性。关闭显示内容、提出取消、
确认工作停止是不同动作；不确定的执行结果需要通过观察和处理继续，不能自动重做。

## 7. 待讨论与验证的问题

这些选择尚未确定。设计团队应记录假设、备选方案、影响及验证结果。

### 开始设计前优先明确

1. **首批核心用户是谁？** 科研人员、熟悉代码的分析者，还是更广泛的知识工作者？
   哪种任务最频繁，哪种困难最值得优先解决？
2. **第一条真实场景是什么？** 输入是什么，用户希望得到什么，什么结果算这次工作完成？
   使用什么具有代表性的材料进行原型验证？
3. **Agent 在哪里与人对话？** Rho 内、外部客户端，或两者协同？
   项目上下文、反馈和实际工作如何在入口之间连续？
4. **工程是什么？** 与文件夹、Agent 会话及任务如何对应？一个工程是否包含多个目标，
   不同工程间如何切换与隔离？
5. **产品如何启动与使用？** 主要使用环境是什么？安装、启动和连接的责任由谁承担？
   首版选择如何影响首次使用体验？

### 在原型中比较并验证

6. 哪些工作可以直接委托，哪些需要澄清、预览或明确授权？如何体现已有授权？
7. 用户通常需要同时开展多少工作？通知、后台进展与待处理事项怎样分配注意力？
8. 新版本何时采用，如何比较？历史材料、反馈与结果需要保留到什么程度？
9. 哪些对象需要直接编辑，哪些更适合只读检查或交给 Agent？代码应在何时出现？
10. 如何分享与导出？交付物是文件、可交互结果，还是包含依据的完整工作记录？
11. 第一版需要哪些展示方式？动态图解等形式是否能带来可验证的收益？
12. 首版需要支持哪些设备、宽度、输入方式和可访问性要求？如何验证中文输入及内容？

## 8. UI/UX 团队的设计任务与交付物

### 8.1 定义与探索

- 澄清核心用户、主场景、完成条件与首版范围，记录已确认决定和仍待验证的假设。
- 建立用户能够理解的对象关系与术语，说明工程、目标、工作、结果、会话如何关联。
- 对影响体验结构的未决选择提供可比较的方案，并解释取舍。
- 工程团队提供实际能力与限制；设计评审把体验目标、实现承诺及原型模拟分开记录。

### 8.2 可操作的原型

优先交付三条可点击并能连续走通的路径：

1. **开始与首次成果：** 启动 → 进入工程 → 提出目标 → Agent 工作 → 查看第一份结果。
2. **人机往返：** 选择结果中的对象 → 表达反馈 → Agent 承接 → 打开实际回应或修改 → 核对并继续。
3. **变化与续接：** 新版本、部分结果、失败或断连出现 → 理解影响 → 保留已有工作 → 继续处理。

原型需要有真实操作对象、交互反馈、返回路径和适用的等待、空、失败、冲突状态。
具体页面、布局和控件由团队选择；静态效果图不能单独证明这些路径成立。
模拟的 Agent 动作和执行结果应在评审说明中标明。

### 8.3 交接材料

- 产品概念、用户场景与信息组织的说明。
- 可操作原型及每条路径的入口、触发条件、状态变化和退出方式。
- 关键对象的选择、编辑、保存、版本、反馈与异常处理规则。
- 代表性内容、宽度、输入方式和可访问性验证记录。
- 设计决定、未决问题、用户测试发现及与工程确认的能力边界。

## 9. 设计评审与体验验证

评审应让代表性用户实际完成任务，并观察是否需要旁人解释：

- 能否开始一件工作，清楚当前工程、目标与材料？
- 能否找到 Agent 已经产生的重要成果，并区分已知事实与解释？
- 能否从结果定位相关数据或修改依据？
- 能否对具体对象反馈，并找到与该反馈关联的回应或实际变化？
- 能否直接接手编辑，并继续交给 Agent，而不形成互相覆盖的内容？
- 能否理解新旧结果的关系，继续查看原版本及其反馈？
- 能否在失败、断连或重开后找回已有内容并继续？
- 能否通过必要的键盘、文本或表格替代路径完成关键操作？

设计完成意味着：团队能够用原型和测试记录说明这些交互如何成立，并明确剩余问题。
视觉质量、实现可行性和真实应用行为分别检查；原型中的成功不计作应用能力已实现。

本文件不指定页面布局、导航结构、面板数量、技术组件或固定分析流程。
后续确认的产品决定应回写为明确结论，保留仍待讨论事项，作为设计与工程共同交接的依据。
