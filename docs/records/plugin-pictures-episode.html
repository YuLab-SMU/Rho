Seeing what a plugin looks like ​

Observed on 2026-11-07, macOS arm64, Node 22.22.3 and Chrome 156.0.8078.81. Source after Rho 0.5.6 and the plugin disclosure episode, selecting Agent 0.4.33. No npm release or change to the person's running Rho is part of this episode.

Question and first observation ​

After the disclosure pass the person reviewed the Plugins page and reported three problems in their own words:

  1. The page did not show what a plugin's UI looks like.
  2. It did not say whether a plugin is reached as a UI, a CLI or something else.
  3. The one third-party example looked very poor.

The retained screenshots from the disclosure episode confirm each point:

  • A view was a row of text: display name, description, component identity, package and "In this browser build". Nothing showed the view itself. The catalog cards showed an icon and the line "N views · N Skills · N operations".
  • Views, Skills and operations were counted, but no entry said how a plugin is reached. Documents' native Claude Code Skill and hook sat in a collapsed section. The Agent package links three command-line programs, and no page mentioned them.
  • The independent package sat above the built-in plugins, unstyled. Its view was a bare serif <h1> in a fixed 570 px white frame. Its buttons used generic borders, and the generated view.html template was an unlabelled form in system serif.

Causes ​

  • No picture of any view existed, and the page had no way to mount a view. The views already render in Studio and the file preview from real project files.
  • The kind of an entry was implicit. The owner declarations already separate components, operations, Skills, native claudeCode entries and the shared MCP descriptor. A package's command-line programs live only in its package.jsonbin, which the listing did not read.
  • The third-party section kept its first-draft CSS with fallback colours, and its frame had a fixed height. The template the CLI generates had no design at all.

Changes ​

Kinds. pluginKinds derives chips from declared or installed entries only: UI with its view count, or the owner's note (Rho page, In other views, No view); MCP tools; Skills; Claude Code; MCP server; CLI. The catalog listing now records cli, the commands an installed package links, read from its own manifest. The plugin's package version comes from the same read. Cards, the detail heading and Information's "Reached by" row show the chips. A third-party card shows UI, MCP tools and Skills from its manifest.

Pictures. scripts/plugin-previews.mjs starts this checkout's service on the shipped PA14 project, opens each view through the page's own "Show it here", and keeps what Chrome drew. web/previews/index.json records each picture's component and version, its package, the file it shows and the capture time. A picture is only matched to the same component version. A card leads with the first pictured view. A view row shows its picture and the file it was pictured with.

Live views. "Show it here" mounts the actual owner view, as Studio does, on a real file of the open project chosen by the view's declared binding. Code opens in the editor, Markdown in the reader, a CSV in the table. A plot uses a table the Agent registered with a key, and its column pickers choose the two numeric columns. The Value view shows the first value a live session holds. A view whose content the Agent supplies, or that opens from a review, says so instead of mounting. The bar says that what a person does there is real.

Third-party plugins. The section follows the built-in plugins. Each package has a mark, its state, kind chips, its source and labelled rows that name each view's and Skill's file. An opened view sits in a captioned panel. The frame follows its page's height from 200 to 900 px. Remove is marked as destructive. The page that rho plugin create generates has a heading, a labelled field, a result area, a visible failure state and a note on where the reply comes from. The disclosure fixture's two views are now small styled pages.

The service also serves .png build assets, which the pictures need.

Limits ​

The pictures show the example project at capture time, not the person's data. They must be recaptured when a view changes; an unmatched version shows no picture. Third-party packages have no pictures; their pages open live. The semantic figures episode drives the same frame. Its selectors were read against this change, but its R episode was not rerun. These checks show the paths work and the screens were read; they do not show that another researcher understands the page without help.
