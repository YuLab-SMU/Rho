This page records what happened on a date, with its observed failures and limits. It is not a requirement for the current implementation. Current behaviour is in Status.

Simulated analysis projects ​

On 2026-10-29, Rho was started from source and two disposable projects built from rho-bio-eval capsules, bix-18 and bix-41, were run through it, giving the screens real content to review. Each project held only its capsule's data and a questions file. Notebooks and gold answers were left out. Question text stayed outside every repository, so this record names capsules and question ids only. The bix-41 q3 basis stated its ratio rule, and the strain identifier was to be read as text.

The run ​

The service ran from dist/cli.js with a disposable root and state under /tmp, the debug Core binary and the system Rscript. A headless Chrome on the same loopback page took the screenshots. Projects were registered with project.open. Clicking Open folder from the headless browser once opened the native folder dialog on the person's screen, and the folder the person chose there was left alone. Conversations were started from the Agent panel with Claude Code. The person answered every native permission request; the scripts only watched.

  • bix-18: the first conversation failed because the default model was not available from the configured provider. The person chose another model, and a new conversation finished in 53 s.
  • bix-41: the conversation finished in 12 min with 110 steps and no permission requests.

Both answered every question in agreement with the capsule's gold answers (compared outside the repository). The screenshots also stay outside the repository, because they show question text.

Second pass ​

On 2026-10-30 the person looked at the changed screens and named what was still wrong. A separate Review page was not where a researcher or an Agent would go to question an answer. The Overview set things side by side without saying how they related. Commands the Agent ran had no place of their own, and a person had nowhere to run a step themselves. They suggested a Console plugin and asked whether the screens needed a layout grammar. The design agreed on was:

  • The answer is the page. A board derived from the Graph shows one message's answer with its results, the method, the run, its inputs and its report, each in a role.
  • Questions and decisions happen on the answer. A person asks about a result or a passage in place, which sends a message to the same conversation. The person's word is bound to the versions the message kept.
  • A Console records every command, the Agent's and the person's. The person can run a step, stop it and run it again.
  • Studio is the person's own arrangement. Following the Agent happens on the board.

A grammar for arbitrary layouts was not built. The board's roles are the one arrangement the runs so far called for.

Changes ​

  • Console 0.1.0 (Rho-plugins plugins/console): console.run/list/output/stop keep each command's change identity, who ran it, folder, pid, ending and head-and-tail output under .rho/plugins/console/. Stop reaches the command's whole process group. After a restart, a live command is continuing and a vanished one unknown. Rho admits console.run and console.stop from the local browser only; Agent grants may read the record (Headless).
  • Console page (web/console.tsx): newest first, each message's commands sit under it, with the person's own between them and managed runs last. A command shows its ending, duration, output and the files that changed while it ran. Run again puts an Agent's command into the prompt to check.
  • Agent 0.4.19: a command's whole text is kept, up to 8 KiB. Before, an inline Python here-document was recorded as its first line and could not be read or run again. Older records still have only that line, and say so instead of offering Run again.
  • Answer board (src/answer-board.ts, web/answer-board.tsx), which leads the Overview: the figure or table the answer names leads, and the other results sit beside or below it. The method, the run, a count of other commands (opening the Console), inputs and report follow. Ask on a result, or Ask about this on a selected passage, sends a question that names what it is about, including the exact kept version. Later questions that made no results stay with the answer under Asked since.
  • Decisions (conversation.decide): Use this answer, or Needs changes with a note that is also sent to the Agent. Each decision is bound to the versions the message kept, names results it does not cover and files changed since, and supersedes without deleting. Review is listed only while a project has review records.
  • Capture (src/conversations.ts): a file seen again with the same bytes, a key already tried, or a file with a capture still pending no longer spends the message's budget. The final collection at turn end does not count against the attempt limit.
  • Graph: a question asked in place is titled by its question. A captured observation line is dropped where another line of the message already reaches the file; the redundant lines had made ← jump to the question.
  • Studio: nothing opens there by itself. A message sent from Studio leaves the person there, and Follow goes to the board.

Process Studio ​

After the second pass the person said Studio should not be cut back to the person's own arrangement. Studio is where a person sees, in one space, how the Agent got the work done; the Overview and the Console stay as focused views. The actions, outputs and commands need their own components and a layout that holds that much. The steps of the work belong in a small aid generated as the Agent works. Time belongs down the side, beside the conversation, so that a replay plays the two together. They framed it as a layout grammar and content question as much as a visual one, and chose one Studio per conversation started in Rho.

Changes ​

  • One Studio per conversation (web/studio-process.tsx): a tab for each of the newest conversations, ahead of the person's own workspaces. The layout is derived from the conversation's record until the person arranges it. It is then saved as conversation-<id>: later files join their role's place and files the person closed stay closed (studioMerge, by the time the layout was last saved).
  • Layout by role (src/studio-layout.ts): each file takes the role the answer board gives it, from the whole record. Inputs, the code and a Commands view stack on one side; figures sit above the tables and reports on the other. Each role has one place and a limit (studioLimits); further files stay in Files. A role first appears when the work first had such a file.
  • Versions in place (web/shell/process-views.tsx): a file's view names the kept version it shows, with earlier and later. A view's properties hold only its declared title, so the file is found again from the view's id.
  • Commands (CommandPane in web/console.tsx): the conversation's commands oldest first, as a terminal reads, with the files each changed and the person's own commands and prompt below.
  • Parts of the work (src/studio-chapters.ts): a chip in the Studio bar names the part in progress, in the Agent's own words between steps or by what the steps did, with rounds of editing and running. Provider error notices open no part.
  • Time beside the conversation: a timeline down the stage's right edge, long pauses folded. Choosing a moment there, a part or another version cuts the record at that second (src/replay.ts). The views, commands, part and the conversation in the Agent panel all show it; a text file shows the version kept then, read only. At phone width the timeline is a row with play, the moment and steps.
  • Following: Follow and the topbar chip open the running conversation's Studio, which brings forward the file the Agent is on, or Commands while it runs one. Sending from the person's own workspace leaves them there.

Meaning layer ​

The person then asked for the semantics of the work: artifacts had almost no natural language description, and the Graph had only actions. They chose the project notes as the source, with provenance; a Graph that shows the meaning by default, can be followed into the process and can show either layer alone; descriptions written by the model while the work goes on; and the Agent's choices folded into choice nodes. A choice must not make the person choose: the results are prepared so the person sees what each option gives.

Changes ​

  • The notes as statements (src/notes-meaning.ts): each session's section is read by subsection into its question, data and method, findings, figures, choices with the options not taken, file descriptions and to-dos, each with the project files it links (Markdown links, or a path in inline code). A file is described by its Files entry, else a figure's description, else the data and method statement that names it first.
  • Provenance: the kept versions of project-notes.md in the Agent's record are read oldest first (meaningLimits); a statement was written by the message whose version first holds its lines, and each file it names is the version kept then. A newer kept version, or a later write on disk, is named as such; a statement in no kept version is said to be outside the record.
  • Layers (src/meaning-graph.ts, web/graph.tsx): one row per section, from the question to findings and choices, the files they rest on, and how those came about (made by, reads), taken from the process record with its basis. Meaning + process draws the meaning rows above the message rows with "kept as" and "written in" edges between them; Meaning or Process shows one. A card says who wrote it and when. Following a statement or file into the process selects and centres the kept version or the message.
  • Descriptions where files are shown: the answer board's results and method, and each file view in a conversation's Studio, carry what the notes say the file holds.
  • Choices without a decision asked for (web/choices.tsx): the option in use beside the others, each with what it gives and the files that show it, on the answer board and in the Graph. Use this instead drafts a message to the same conversation for the person to edit and send. No badge, waiting state or decision record is added.
