CI on three systems and npm ​

Updated 2026-11-02. Upstream finished Windows (Windows episode), and the user asked to start CI on the three systems and publication to npm. They chose the package name @rho-workspace/rho, an NPM_TOKEN secret for publishing, pushes to main, and CI in Rho only: Core and the Plugins add their own later. Work ran in GitHub Actions on YuLab-SMU/Rho, whose runners are free for a public repository on all four machines used here.

What CI does ​

components.json selects the Core commit (6f83226, then 8bed8ef after the sixth run) and the Plugins commit (491c440, then 0b17877 and 90e68cf after the third and fourth runs) the application is built from. On each push to main and pull request that changes more than documentation, ci.yml:

JobRunnerWhat it does
Coremacos-15, ubuntu-24.04, ubuntu-24.04-arm, windows-2022Builds the selected Core with Rust 1.97.0, dev profile without debug info: Mach-O arm64, static musl Linux x64 and arm64, MSVC Windows x64; reuses a Core commit already built
Testmacos-15, ubuntu-24.04, windows-2022Builds the selected Plugins and Rho, runs Rho's suite with that platform's Core
Figure describersmacos-15, ubuntu-24.04, windows-2022Installs ggplot2, svglite, gridGraphics, ComplexHeatmap and their companions in R, matplotlib, pandas, scipy and seaborn in Python (and XQuartz on macOS), and runs the selected Plugins' figure describer checks; a skipped check fails the job (Figure files)
Packubuntu-24.04pack:local with all four Cores; checks the platforms, Linux linkage, clean inputs and commit
Installall fourci-install-check.mjs: digest, offline install with an empty npm cache, the launcher, the packaged recovery and ordinary-project acceptances

A v* tag runs release.yml instead:

JobWhat it does
FindThe successful CI run on main for the tagged commit that still keeps its candidate
CIOnly when Find found none: ci.yml as above, in this run
Verifyrelease-check.mjs: digest, the commit and run that packed it, the four installation reports, name and the tag's version
PublishEnvironment npm: npm publish --provenance of that candidate

The installed check verifies the tarball against SHA256SUMS and its composition, installs it outside every checkout with --offline and an empty cache, and runs the rho shim's usage. The launcher must report ready with its own platform's Core and copy in the shipped project, then stop: on SIGTERM with its shutdown report, or on Windows, where a CI step cannot send Ctrl+Break, by ending its process tree with no project open. It then runs the packaged recovery acceptance and the packaged acceptance of Plugins' examples/ordinary-r-project from the installation.

The release builds nothing when CI already tested the commit. Verify checks that the candidate's composition names the tagged commit and the run it came from (build.run), that each platform's installation report passed with this tarball, and that the package is @rho-workspace/rho, not private, with the tag's version. Publish runs npm publish --provenance --access public with NPM_TOKEN, a repository secret that no other job names; its environment npm has no reviewer. A version with a prerelease suffix goes to the next dist-tag, any other to latest. Run by hand on main, the release rehearses everything but Publish.

Before the first run ​

The local main held one commit not yet pushed, the shipped example project (58d7b5fc). It was replayed over upstream's three Windows commits (55ebc49b); only Status conflicted, in wrapping.

  • The example appeared in every test service. The seed treated an unset example as on, so a service composed in code also got the project, and six browser grant checks saw two projects. The CLI passes on or off explicitly; the service now seeds only when asked (dfbc15a3).
  • The example could not be packed. The packer refuses every R file outside the kernel runner, to keep project recipes out, and the study's scripts are R. Files under example/ are allowed, nothing else (281be780).
  • What a registry needs. The staged package drops private, asks for public access and names its repository, which provenance needs; the source checkout stays private.

Sixth run and a Windows diagnosis ​

Run 41375803891 on 64d73550 passed 275/277 on macOS and Linux x64 and installed on all four platforms. Windows had three failures: the cmd-special path, MCP v2 at 30 s, and "a repair is a new identity", which took 47 to 48 s there against about 2 s on macOS and passed its 60 s limit this time. A diagnosis workflow on a temporary branch (runs 41377127229 and 41378118954, windows-2022) separated the causes:

  • R and %OS%. Node alone ran Rscript --vanilla on a script in folders named with each character cmd treats specially. R 4.5.1 and 4.6.2 both ended with 0xC0000005, an access violation, when the script's absolute path held %OS%. They ran normally with &, ^, !OS!, (1), Chinese and an emoji, and with a relative path in the %OS% folder. Core gives R the script's absolute path, so R ends the same way in such a project under Rho; Core reports Code(-1073741819). Where R misreads the path was not found. Upstream's R 4.5.1 ran the test on their own machine.
  • Rho's contract. Rho's schema of Core's exit required a code of 0 or more. Core reports an i32, and a Windows process ended by an NTSTATUS reads negative, so the service's reply failed the contract it publishes. The code now keeps Core's whole range. The test runs R in a project without % and checks its working folder; in a project whose path holds %OS% it checks that the Host found the folder as named and that the run's state follows R's code.
  • Core's Windows output. Through Rho's service, R writing 200 message() lines took 3.1 to 3.4 s on Windows and 2000 lines 20 to 35 s, against 0.2 s on macOS. Once a lookup waited 20 s and Rho read the running run as unknown. Core's Windows reader gets each write as its own read, and each was committed alone: a blob, its sync and the record. Core 5333181 commits the bytes queued since the last drain together, at most one blob chunk at a time (Core record). Its new regression failed on the old pump at the 512-chunk limit after 25.9 s and passed in 0.5 s. With that Core on the runner, 2000 lines took 0.32 s, the repair test 2.1 s alone and MCP v2 22.4 s alone. Core's full regression suite was not run on Windows.
  • MCP v2. Alone with the old Core it took 28.7 and 30.0 s on the runner. Its limit is now 90 s.

components.json selects Core 8bed8ef, the fix and its record.

Publication ​

@rho-workspace/rho@0.5.2 is published (below). A v* tag needs:

  1. The npm organization rho-workspace, owned by the account that will own the package.
  2. A granular access token that can publish to that organization's packages without a one-time password, stored as the repository secret NPM_TOKEN of YuLab-SMU/Rho. The user added the secret on 2026-11-02 and chose no reviewer: the npm environment, which GitHub creates for the first publish job, holds nothing back. Whether the organization exists and the token can publish there is not visible from GitHub; the first publication shows it.
  3. The version in package.json, pushed, and that commit tagged v<version>.

The tag's release publishes the candidate CI tested for that commit, or runs CI first when no run kept one. The 0.5.2 candidates recorded earlier were never published, and a version cannot be published twice.

Windows installation time ​

The user then asked to shorten the slow Windows installation, with another agent's analysis and issue 112 attached. That analysis put the cost on the package's file count, about 18 to 26 ms per file on Windows against 0.79 ms on macOS, and proposed removing what Node never reads, then the duplicate CommonJS builds, and installing CI's copy in an ASCII folder on the workspace volume. The issue measured 40 s for the package on a Windows 11 machine, against 91 to 134 s on the runner.

The published 0.5.2 tarball holds 5,250 files, 4,688 of them bundled dependencies: 1,722 JavaScript files, 1,261 type declarations, 645 source maps, 454 TypeScript sources (332 of them zod's), 186 Markdown files and 59 tool configurations; the MCP SDK also ships 208 example files. prune-bundled.mjs now runs in the packer after the production install. In third-party packages it removes declarations, source maps, TypeScript sources, tests, examples, documentation and dotfiles. Licenses and first-party packages stay, as do the declarations reached from Rho's own (@agentclientprotocol/sdk, ajv, fast-deep-equal, fast-uri and zod, 533 files). A file that a package names under a condition Node selects (main, bin, exports import/require/node/ default) stops the packer instead; zod and eventsource name TypeScript sources only under source conditions. Pruned the same way, the published package has 3,030 files and 22.7 MB instead of 25.0 MB.

Installed side by side on this Mac, the full and pruned packages loaded the same 327 of 343 export entries of their bundled packages; the other 16 fail in both (JSON without an import attribute, type-only paths, Deno and Bun entries, three Agent entries that need a connection).
