Project sidebar and Agent canvas ​

Updated 2026-10-31.

Later the same day the user asked for the canvas and the workspace to be one page. The Agent's files now open in the workspace the person shares with it, and the Graph shows what the Agent did; see One workspace and the Graph. The runs below describe the separate canvas as it was.

Question ​

The user tried working with the Agent inside a project and found it a poor experience. The project sidebar held almost nothing (Overview, Files, Activity), and while the Agent worked the main area stayed on the project page. They supplied a reference screen with a project block, Overview/Studio/Graph/Agent entries, a Sources section counting Data, Code, Runs, Results & figures and Notes, and a studio of code, table and figure views. They asked for a sidebar like it, and for the canvas to move with the Agent while it works.

The reference set layout weight and hierarchy, not values to copy. Rho has no Graph, so the sidebar shows none. The questions this pass answered:

  1. Can a person see what a project holds, by the kind of file they look for, from its sidebar?
  2. When the person asks the Agent for something, does the canvas show the files the Agent reads and changes, as it works, without taking over what the person chose to look at?

Setup ​

  • Real runs: a disposable air-study project (data/airquality.csv from R's airquality, scripts/analysis.R, notes.md, README.md), Claude Code 2.1.312 through Westlake HPC (westlakehpc/deepseek-v4.1-flash) over ACP, R 4.5.2, and Chrome 155.0.8059.84 at 1440 × 900 and 390 × 844. The message was typed into the Agent panel and sent with Start: read the table and the script, change the script to compute mean Ozone by Month, write results/ozone_by_month.csv and a bar chart PNG, and run it. Screens were taken every 2.5 s during the turn.
  • Script and evidence: work/agent-canvas-20261027/ (ignored by Git): episode.mjs (runs first, second, third, final) and review.mjs (four widths after a turn, without a model).

Observed before ​

  • The sidebar (screens from the earlier real ACP turn in work/agent-ui-live-20261027/real-rendered-1440.png) offered Overview, Files and Activity, the workspaces by identifier, and settings at its foot. Nothing said what the project held.
  • While the Agent read input.txt and ran ls, the main area stayed on the project page. The work showed only as rows in the 340 px Agent panel.
  • The Documents owner returned an open buffer as it was when first opened. A file the Agent changed with its own Edit or Write tool, or with a command, kept showing its old text in Rho; reopening it did not help.
  • agent.activity.capture, the browser's way to show a CSV or image as a file snapshot, located the file by walking its whole directory: a file at the project root was refused and a folder holding more than 64 files failed the scan.

Changed ​

Rho (web/project.tsx, web/main.tsx, web/sources.ts, web/canvas.ts, web/agent-now.ts, web/overview.tsx, web/shell/workspace.tsx, CSS):

  • Sidebar. "All projects" above a project block (initials, name, a menu to switch to another open project). Overview, Studio with its workspaces under it, Agent with a Working or Needs you badge, and Activity with its run count. Sources counts Data, Code, Results & figures and Notes, then Files; + adds a source folder. Counts come from one bounded walk of the project folders (48 folders, 5 levels, 4000 files); a partial walk shows + and says so. Kinds come from file names only. Tables in an output folder (results, output, figures, …) count as results; registered results count there too, file snapshots taken only to show a file do not.
  • Sources pages. Each kind lists its files across the project and its source folders, with a filter. A CSV or image opens in its table or media view, text in the editor, a registered result as its exact version. (A later pass shows them in place instead; see Browsing Sources from the sidebar.)
  • Studio. Workspaces are tabs at the top of Studio with their view counts. The Agent canvas is the workspace agent-canvas, shown as "Agent canvas".
  • Following. Sending a message from the Agent panel opens the Agent canvas and follows the running turn. Each file the Agent's steps name inside the project opens there once: a read as soon as it is reported, an edit or write once it returned. A finished command opens the project files its command line names, and an output that appears or changes on disk during the turn (or in the walk just after it) opens too, without a claim about who wrote it. Code sits on the left, data and figures on the right, at most six per side; a newer snapshot of a file replaces the older one. Every placement is one conditional layout write.
  • The Agent's place. The tab of the file the Agent last named carries Reading/Read, Editing/Edited, Writing/Wrote or Running/Ran, live while that step is the newest one running. The topbar shows the Agent and its newest action on every project page, amber when a native permission waits; clicking it follows.
  • The person's place. Choosing another tab, typing in a view or going to another page stops following; nothing then opens or moves. "Follow Claude Code" resumes and brings the newest file forward. A followed view is not held, so a replaced snapshot does not linger as a second tab.
  • The workspace's older attention bar is not shown on the Agent canvas; its own follow control would have been a second "Follow" with another meaning.
  • A tab bar keeps its tab names and moves a view's own controls to a second row when both do not fit. The sidebar is hidden by CSS below 768 px, so no frame shows it before the page knows it is narrow.

Documents 0.4.3 (Rho-plugins/plugins/documents): a buffer with no unsaved text follows its file. On open, changed disk text is adopted as one edit by the author disk, recorded as the smallest changed span, so views show the current text and history keeps the text before. Unsaved text or a pending save is never replaced. The editor labels such changes "File on disk" and highlights them with Agent edits under "Highlight changes".

Agent 0.4.12 (Rho-plugins/plugins/agent): agent.activity.capture observes only the named file: inside the project, reached without symlinks, a regular file of at most 8 MiB. expectedDigest became optional; with it the capture is of that exact version, without it of the current bytes. The output-list scan is unchanged. Annotations 0.4.4 only widens its optional Documents peer to include 0.4.3.

Limits and next questions ​

  • Following reads the conversation record, so the canvas moves at most about four times a second and can lag a short step; a file the Agent touched only between two reads still opens.
  • Command lines are matched for project file names with known extensions; a command that writes elsewhere, or by name patterns, is seen only through the folder walk. The walk sees sizes, not contents, so an output rewritten with the same size is not reopened.
  • The walk runs every 5 s at most while records change: up to 48 listings a time. A project with more folders shows partial counts.
  • Below 768 px the Agent panel is a full-screen sheet, so the canvas follows behind it; closing the panel shows where it went.
  • A CSV over 8 MiB or a file Rho has no view for (PDF, Excel, RDS) is named in a note on the canvas instead of opening.
  • The canvas shows files. It does not yet explain a change in the Agent's words next to it, show command output, or let the person answer on the view itself.

Browsing Sources from the sidebar ​

Question ​

The user opened Results & figures in their test project (six PNGs in ggplot2-demo/out) and found a page used as the directory awkward: moving from one figure to the next meant going back to the list. They asked for the sidebar to browse each kind's files directly.

Before this pass, choosing a file on a Sources page placed it as a new tab in the workspace layout and opened Studio. The next figure needed the list again, and every figure seen stayed behind as a tab.

Changed ​

Rho only (web/project.tsx, web/preview.tsx, web/sources.ts, web/canvas.ts, web/overview.tsx, web/main.tsx, web/theme.css):

  • Sidebar. A Sources row unfolds into its files and folds again. With more than one folder, files sit under folder labels: the project's top level first, then by folder and name. Long names take two lines. The sidebar holds 40 files per kind; "All N files" opens the kind's page, which keeps its filter. Unfolded kinds are remembered per project for the tab, and the kind of the file on screen stays open.
  • In place. Choosing a file shows it in the main area in its owner's view, without writing a layout. The view's own controls stay with it (Fit/100% for a figure, Save and Highlight changes for text). Above it: name, folder, size, "3 of 6" (to the kind's page), previous/next and Open in Studio.
  • Moving. ← and → switch files unless focus is in a field, a menu or tab list, or inside the view, so a table cell or the editor keeps its keys. ↑ and ↓ in the sidebar list move and show. Until the next file resolves, the last one stays dimmed instead of blanking.
  • Each showing reads the file as it is now. A CSV or image becomes a Files snapshot of its current bytes; snapshots are content-addressed, so unchanged bytes give the same one. Text opens the project's one buffer of that document.
  • The kind's page lists the same files in the same order and shows the chosen one in place. A result with several versions is listed as the one its latest run made.

Choosing the Agent and its model ​

Question ​

The user asked for settings in the Agent UI so that a person chooses the Agent and its model themselves.

Observed before ​

  • The panel's new-conversation header had one select: Configured default, Claude Code or Codex. Model, effort and permission mode came only from each Agent's own configuration, and no screen said which model answered. The failed conversation above ended on a model the gateway said may not exist; nothing in Rho could choose another.

  • ACP v1 sessions report the settings they accept. Opening a session without a message in an empty folder:

    • Claude Code (claude-agent-acp 0.97.0, 3.2 s) offered Mode (5 values), Model (101), Effort (6), Fast mode and Ultracode.
    • Codex (codex-acp 2.3.0, 0.5 s) offered Mode (4), Collaboration mode, Model (103) and Reasoning effort (6).

    Neither groups models through ACP. Names end in " · " and where the model comes from (a routing group, a provider). Descriptions carry account names; this record leaves them out and the screens show them only as tooltips.

Changed ​

Agent 0.4.13 (Rho-plugins/plugins/agent):

  • The ACP connection keeps the settings a session reports when it opens or changes them (config_option_update). The session observation carries them, bounded to 12 settings of at most 256 values each, with the rest counted.
  • The person's choices are applied once the session opens and before any message is sent. A setting or value the Agent does not offer fails that message; nothing is sent.
  • configure() changes one setting on an open session between messages.
  • inspect() opens a session, reads its settings, removes the session where the Agent supports that, and ends the process. It sends no message.

Rho (src/conversations.ts, src/protocol.ts, web/agent-settings.tsx, web/conversation.tsx, web/overview.tsx, web/agent-work.tsx, web/theme.css):

  • Four operations for the person at this machine:

    • conversation.settings.read reads one file in the service's state directory and starts nothing. The file holds the Agent for new conversations, each Agent's choices, and what each Agent last offered, from a check or from a conversation's first session opened without choices.
    • conversation.settings.update refuses a stale expectedVersion and any value the Agent did not offer.
    • conversation.settings.check runs inspect() in the project, one check per Agent at a time, bounded by connectTimeoutMs.
    • conversation.configure changes an open conversation's session now. If no session is open, it records the choice for the next one. It is refused while the Agent is answering.

    conversation.start without an Agent or settings uses the saved ones and records them on the conversation. A request holds at most 12 settings of 512 characters.

  • Agent page: a "New conversations use" card above the conversations, with:

    • Claude Code or Codex;
    • a model picker that is searchable, grouped by where each model comes from, and starts with the Agent's default named;
    • effort, mode and the other settings as compact selects, each with its default;
    • a line saying which adapter offered them and when, with Check again.

    Before any check, "Ask Claude Code" says that it starts the Agent for a few seconds and sends no message.

  • Panel: one chip under the message box names the Agent, model and effort. It opens the same picker, with the Agent switch and effort above the list. In an open conversation, the chip shows that conversation's model and effort and changes them between messages.

  • Each message's ending names the model that answered, in the panel and on the Agent page.

Arranging views: the person drags, the Agent writes ​

Question ​

On 2026-10-27 the user asked whether the Agent arranges the page freely, and said both the Agent and the person should. The person had no way to arrange views by dragging.

Observed before ​

  • Each workspace is one saved layout: a tree of groups and views, where a split group keeps its axis and weights. Both the person and the Agent change it through composition.apply against an expected version, and composition.undo reverses the last change.
  • The person could drag the dividers between panes, and Arrange views offered Split right, Split down, Move to the next or previous group, Close view and Undo. Tabs could not be dragged. The Agent panel was fixed at 340 px.
  • A Rho-started Agent's grant already holds composition.read, composition.apply, composition.undo and composition.put. Its MCP index was the only description it had of them.
  • When a person's change put a group other than the canvas's own code and data groups under the canvas root, every later file the Agent touched joined the first tab group.

Changed ​

Rho only (src/shell-layout.ts, web/shell/regions.tsx, web/shell/workspace.tsx, web/shell/shell.css, web/canvas.ts, web/main.tsx, web/theme.css):

  • Tabs drag. A tab can be dropped in three places:

    • on another group's tabs, where a line marks the place, to move or reorder it;
    • on the middle of a group, where the group is tinted, to join its tabs;
    • within a quarter of a group's side, where that half is tinted, to give the view a pane on that side.

    A pane beside one along the same axis joins that split and halves that pane's share. A pane left empty closes. Each drop is one conditional composition.apply of the saved layout, the same write the menu's commands and the Agent use. Undo reverses it. A drop where the tab already is writes nothing. Dragging stops following the Agent. Below 768 px the workspace is one tab list and nothing drags.

  • The Agent panel's edge drags, or moves 24 px per arrow key, between 280 px and 760 px (at most 60% of the window). A double-click returns it to 340 px. Each browser keeps its own width.

  • The canvas keeps its sides. The Agent's code files join the canvas's code group and its data and figures join the data group, wherever the person has moved them. A side whose group was emptied comes back at its edge of a left-to-right split.
