0.5.2 on macOS and Linux ​

Updated 2026-11-01. The 0.5.2 candidate was JavaScript plus one darwin-arm64 Core, and it refused every other platform. The user asked for this Mac and Linux first; Windows follows in another clone. This episode packs one tarball that installs on macOS arm64, Linux x64 and Linux arm64, and records what building, testing and installing it on each found.

Core: one commit for every platform ​

A package should carry each platform's Core from one Core commit. Core 7e424b3 includes the Windows port (1e95dd7), which the Windows work will build on, so it was selected. It did not compile on Unix. Once it did, its Host exited as soon as it started (the signal pipe's read end had two owners, so the first read saw EOF), Linux had lost its SO_PEERCRED peer check to a macOS-only call, and the Host no longer removed its own socket. Core c3dbeca restores 4f5bed8's Unix behavior; the Windows code is unchanged and still type-checks. See CORE-20261101-01.

Linux Cores are static musl builds (x86_64/aarch64-unknown-linux-musl), so they need no particular glibc. All three Cores are the dev profile, as tested and as 0.5.1 shipped, built with CARGO_PROFILE_DEV_DEBUG=0: with debug info a Linux Core was 26 MB, without it 7 MB. Core's own checks ran in that same configuration on each platform, and the packed binaries are the ones those runs built.

The first full x64 run did not finish: managed_run stalled for 25 minutes with most test threads waiting on a lock. Repeated under load (eight loops of 25 runs), it stalled 5/200 times as musl and 3/200 as glibc; 4f5bed8, before the port, stalled 5/200. Native arm64 never stalled (0/200 Linux, 0/200 macOS). The stall predates this work, does not depend on the C library and has only been seen under Rosetta. It has not been tried on real x86_64 hardware, so it is not known to be only an emulation effect.

What Linux exposed in Rho and the Plugins ​

The local R Notebook died at start. Node gives a child's extra descriptors as sockets. The R runner opened its answer channel as /dev/fd/3; macOS allows that, Linux refuses with ENXIO. On Debian 12 arm64 the local Notebook tests had 5 R failures (7 passed). Notebook 0.5.1 relays the answers through a cat that ignores the interrupts sent to the session's group.

Output landed out of order. With the relay an answer arrives after the text printed behind its mark, and the reader only handled the opposite case. Printed text after a mark now waits up to a second for that mark's answer. Checking this on macOS showed a second, older race: an answer held for its mark was queued while the text after the mark was placed at once, so message(); warning(); value once gave the warning after the value. Printed text now joins the answers' queue. The same cell kept its order 6/6 on macOS and 8/8 on Linux, and the local Notebook tests on Linux pass 12/12 (one skipped: Matrix absent).

Open folder said "currently supported on macOS". The home page has no other way to open a folder. On a Linux desktop Rho now shows zenity's or kdialog's folder window. With a real zenity 4.1.90 on a virtual display, selecting returned /tmp/rho picker 中文 …/project a intact and Escape returned a cancel. Without a desktop session (DISPLAY/WAYLAND_DISPLAY) it says "Rho is not running in a desktop session, so it cannot show a folder window. Open the project from your Agent."; without either program it names them. kdialog was not run.

A missing Core printed a stack trace. Startup now prints only the reason, such as "This installation has no Core for darwin-arm64; it carries linux-arm64, linux-x64. Select a Core with --core ABSOLUTE_PATH or RHO_CORE_BINARY.", and exits 1.

Packing ​

pack:local takes --core PLATFORM=BINARY once per platform. Each binary's own header must name its platform (Mach-O/ELF/PE and the machine), so a mislabelled build cannot be packed; a Linux Core's linkage is recorded. A .node addon anywhere fails packing, which keeps the rest platform-neutral. The composition (schema 2) lists platforms, packedOn and, per platform, core.artifacts[PLATFORM] with its path under vendor/core/PLATFORM/, digest, size and format. Startup selects this machine's entry and checks its digest.

On macOS the first attempt failed: the default temporary folder made the project path longer than Core's 103-byte socket limit, a documented limit; it passed under /tmp, as the older installed acceptance runs. Removing this platform from the installed composition, and changing its digest, were each refused on macOS and Debian, and the original bytes were restored. Screenshots taken right after a resize (768 and 390 px) showed a second header near the bottom on every platform; the page opened directly at 390 px has one header, so it is a stale paint in the screenshot, not the layout.

Rho passes 269/270 with the new macOS Core; the MCP v2 stdio test was again cancelled at its 30 s limit and passes alone in 25 s. Plugins pass 165/165. Contract checks pass.
