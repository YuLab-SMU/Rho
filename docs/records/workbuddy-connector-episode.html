A WorkBuddy connector for Rho ​

Updated 2026-11-10. After the outside-Agent episode the user asked whether WorkBuddy can set up Rho's experts, skills and connectors by itself, and then asked for one package made for WorkBuddy, to submit at https://open.workbuddy.cn/. This episode reads what WorkBuddy had done with Rho, how WorkBuddy 5.9.3 loads each of the three, runs WorkBuddy's own agent core on the user's requests, and builds the package: a CLI connector, adapters/workbuddy-rho.

What WorkBuddy had done ​

From WorkBuddy's own session files and its folder ~/.workbuddy on this Mac:

ConnectorIts Agent added Rho's MCP server to ~/.workbuddy/mcp.json three times (2026-11-06 and 11-07): rho-project for the airway project, rho-ggtree, rho-pa14-quorum-sensingNone ran. WorkBuddy runs a server in that file only after the person approves it under its connectors: mcp-approvals.json, keyed by a hash of the command, arguments, environment names and folder, was empty. A server an Agent writes there is shown as disabled, and a new grant changes the arguments, so the hash. Two statements of the outside-Agent episode change with this: rho-project is the airway project's server, not another project's, and the Skill was not ignored but not yet installed.

WorkBuddy's agent on the request ​

WorkBuddy's agent core is a CodeBuddy CLI inside the app (app.asar.unpacked/cli/bin/codebuddy). Run with ELECTRON_RUN_AS_NODE and a throwaway config folder it has WorkBuddy's built-in skills. Its own models need the desktop app's login, so a custom model pointing at the local gateway carried westlakehpc/glm-5.3-flash; the tools the desktop app adds (market search, connector requests, image generation) are absent there.

Asked "帮我在 WorkBuddy 里配置好 Rho 相关的专家、技能和连接器，之后我要在这个项目里用 Rho 做数据分析。" on a copy of the airway project, three runs (83–169 s) went to the market skills, recommend-experts, recommend-connectors and marketplace-skill-installer, found no market tools and stopped. None made an expert locally or ran rho; one asked whether "Rho" meant RhoA/ROCK or Spearman's rho. Those runs could not write files or run commands (an allow-list problem of the harness, fixed below), so they show where WorkBuddy looks, not what it does next.

So WorkBuddy does not reach Rho by itself: an expert is made only when named, a connector it writes does not run, and a skill comes from the market. A market connector is what WorkBuddy offers a person and installs itself.

The package ​

WorkBuddy's open platform takes a connector as a folder with connector-meta.json, either mcp.json or cli.json, an icon and optional skills/. Its mcp.json must hold one server whose arguments cannot carry a placeholder or a per-machine path, and Rho's MCP server needs the path of a project's grant file. rho tool reaches the same four tools from a shell, in the conversation, with no approval and no new conversation. Of the 312 connectors in WorkBuddy's local market cache, 46 are listed as CLI connectors, most installed by npm install -g with a Node WorkBuddy provides.

FileContent

node adapters/workbuddy-rho/build.mjs checks the fields WorkBuddy's page requires, that the runtime range is Rho's engines.node, that this Rho is at least minVersion, that statusMatch matches rho --version, that each link reaches a packaged file and that no file names the building machine's home or holds a credential, and writes work/workbuddy-rho/rho-workspace/ and rho-workspace-1.0.0.zip. test/workbuddy-connector.test.mjs runs the build and the three cli.json commands against this build. Rho's own connect reference now also tells an Agent in WorkBuddy to use rho tool and leave mcp.json alone.

Not done ​

  • Submitted: nothing. The platform has no upload API; the user submits the zip, and the connector works only once Rho 0.5.8 (with rho open and rho tool) is on npm.
  • WorkBuddy's own model and desktop app: the trials used WorkBuddy's agent core with GLM-5.3-flash, without the app's host tools or its model. Installing through the connector, its versionCheck and status, and how the app shows a CLI connector without sign-in are unobserved until the connector is installed from the market.
  • Platform rules: whether review accepts a CLI connector with no auth, and the zip's expected root, are unknown; the README gives what to tell the reviewer.
  • Windows through WorkBuddy is unobserved (rho.cmd runs in CI).
  • The user's own rho-data-analyst expert and ~/.workbuddy/skills/rho keep the older Skill; the user's mcp.json keeps three servers that never ran. Nothing in the user's WorkBuddy folder was changed.
