# Rho Automated Visual Acceptance

Status: active automated acceptance lane; replaces the human-executed manual
acceptance guide by user authorization dated 2026-08-26

Owning contract: `docs/plans/implemented-2026-08-26-visual-acceptance-automation-spec.md`.

This is the executable source of truth for Rho's consolidated development
visual acceptance lane. Exact-candidate, installer, signing, distribution,
and release GO/NO-GO gates remain owned by their release contracts. The former
`MANUAL-ACCEPTANCE.md` walkthrough is retired: its human-executed gates are
replaced by deterministic in-app assertions plus per-frame visual review
against the real application and the real Workspace R backend.

## What Runs Where

- The lane drives the debug desktop build through the acceptance bridge
  (debug-only, loopback-only, compile-gated; see the spec's Bridge Contract).
- Scenario modules live in `scripts/visual-acceptance/`; the driver is
  `scripts/visual-acceptance.mjs`; fixtures are generated by
  `tools/prepare-fixtures.mjs` (cross-platform; `prepare-manual-fixtures.ps1`
  remains the Windows-native equivalent).
- Browser/mock preview evidence remains a weaker evidence class and never
  closes these gates.

## Running The Lane

```bash
npm run rsr:build --prefix desktop  # after desktop/ui/** changes
cargo build -p rho-desktop          # after the frontend build and desktop/** changes
node scripts/visual-acceptance.mjs run --output target/visual-acceptance/<run>
# or: npm run rsr:accept:visual --prefix desktop
```

The run launches the app, generates the fixture projects, executes scenarios
S0, S1, S2, S3, S7, S8 in order. A deterministic failure stops only its
current scenario; the driver continues with the next independent scenario so
one run reports all reachable component failures. The output directory must
not already exist; evidence roots are immutable and a retry uses a fresh path.

## Evidence Model

Each run directory contains:

- `evidence.json` — the gate-level ledger. Every gate records
  `deterministic_status` (PASS/FAIL/SKIP), `visual_status`
  (PASS/FAIL/PENDING/N/A), an overall `status`, the captured screenshot, and
  its visual criteria.
- `screenshots/` — one PNG per visual gate, captured from the live window.
- `visual-review-manifest.json` — every frame with its review criteria and
  verdict slot.
- `report.md` — the human-readable summary, regenerated whenever a verdict is
  recorded.
- `app-stdout.log` / `app-stderr.log` — application logs for the run.

Visual review is recorded frame by frame; a blanket default pass is not
evidence. The reviewer inspects each frame against its criteria and writes
the verdict back:

```bash
node scripts/visual-acceptance.mjs record-review --run <run> --frame <name> \
  --verdict pass --note "layout hierarchy readable, no overlap"
node scripts/visual-acceptance.mjs finalize --run <run>
```

A run is PASS only when no deterministic gate failed, no visual verdict
failed, and no frame remains PENDING. Truthful SKIP gates (missing optional
prerequisites such as model credentials) do not block PASS but are listed in
the report.

## Removed Manual Gates (Authorized 2026-08-26)

These gates targeted UI removed by the Studio overhaul or steps that are not
machine-verifiable. They are closed by authorization, not by automated
evidence, and are recorded here so the removal is auditable. The executable
suite emits an explicit named `skipGate` with the removal reason for every
class below; a SKIP is never counted as PASS:

- Data Viewer search/sort/paging/export (no current-UI component; backend
  data-view commands remain);
- reviewable Git mutations in the UI: hunk stage/unstage, confirmed Restore,
  staging/commit flow (current `rho.git` surface is read-only);
- Human-first/Agent-first posture checks, dock-tab focus rules, and the
  dual Plots Session/History presentation;
- Windows installer human checks: SmartScreen wording, Windows Credential
  Manager contents, 125% display scaling, uninstall behavior;
- keyboard-only navigation sweeps and shortcut audits that require human
  observation.

If a removed surface returns to the product, its gate returns to the
automated suite as a real assertion rather than a `skipGate` record.

## Failure Handling

A failing gate stops only its current scenario. The driver preserves its
evidence and continues with the next independent scenario so one run reports
all reachable failures. Record each failing gate, its screenshot, and whether
project files, R state, or durable records changed before retrying. The lane
never rewrites an existing evidence root or converts a product failure to a
SKIP.

## First Local Baseline

The 2026-08-26 integrated baseline is indexed at
`docs/verification/visual-acceptance-va1-baseline.md`. Its 35 gates finalized
as 12 PASS, 15 FAIL, and 8 authorized removed-gate SKIPs, with all 17 frames
reviewed and no pending verdict. This proves the acceptance lane is executable;
it does not claim the current product passed visual acceptance. Product repairs
identified by that run remain separately authorized follow-up work.
